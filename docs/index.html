tl;dr hands-on > demos > slides

The best way to learn something is to try it yourself. So, we've turned a bunch of the demos our instructors do into Do-It-Now activities, where students can try each concept out in quick, bite-size activities.

If you are using these as part of an Instructor Led Training (ILT), make sure to listen to your instructor and coordinate your efforts with their direction.

Overview

  1. Many of these activities will cost money

Warning: Do-It-Nows tagged with $ generate significant charges if run in your personal account. We assume that you are working in lab projects with lab-provided accounts. You've been warned.

Setting up

  1. Make sure you have the BigQuery console open.
  2. In a new browser tab, open https://github.com/roitraining/gcp-demos/blob/master/bigquery/execution_details_example.sql

Run a heavyweight query

  1. Copy the -- heavyweight query query into the BigQuery editor and run it. It will take a couple of minutes; while it runs, don't touch anything, just watch the elapsed time tick.
  2. When the query completes, click on Job Information and note the Duration (elapsed time) and Bytes processed.
  3. Click on Execution Details and note the Slot time consumed, Bytes shuffled, and Bytes spilled to disk.
  4. Write down your five numbers: elapsed time, slot time consumed, bytes processed, bytes shuffled, bytes spilled to disk.

What each number means:

  • Elapsed time - what the user felt: the wall clock time waiting for results
  • Slot time consumed - the work: compute time summed across every slot
  • Bytes processed - the read: what the on-demand pricing model bills
  • Bytes shuffled - the movement: data moved between stages over the network
  • Bytes spilled to disk - the overflow: shuffle data that didn't fit in memory (0 is what healthy looks like; this query is not healthy, and the shuffle and spill activity digs into why)

Work vs. wait

  1. Divide your slot time consumed by your elapsed time (make sure both are in seconds). The result is roughly the number of slots that were working on your query at once.

Some things to think about:

  • Hours of slot time with under a minute of elapsed time is not a contradiction; it's parallelism
  • Which of the five numbers does on-demand billing care about? Which one do your users care about?

Run a lightweight query

  1. Copy the -- lightweight query query into the BigQuery editor and run it.
  2. Collect the same five numbers from Job Information and Execution Details.

Some things to think about:

  • Which of the five numbers changed the most? Why?
  • Where did all the bytes shuffled go? (Hint: what does a join do that a single-table scan doesn't?)
  • Optimization in BigQuery means driving down bytes processed, slot time, or bytes shuffled. Elapsed time follows - it is a symptom, not a lever.

Setting up

  1. Make sure you have the BigQuery console open.
  2. In a new browser tab, open https://github.com/roitraining/gcp-demos/blob/master/bigquery/shuffle_spill_example.sql

Watch nothing move

  1. Copy the -- scan and filter query query into the BigQuery editor and run it.
  2. Open Execution Details and note the Bytes shuffled.

The query read gigabytes of data, but shuffled little to none of it. Each worker read its own chunk of the table and filtered it in place. No row needed to meet any other row, so nothing moved over the network.

Move a little

  1. Copy the -- aggregation query query into the BigQuery editor and run it.
  2. Check Bytes shuffled again. It's bigger than zero this time, but still small.

Counting customers per state requires rows with the same state to meet. But each worker pre-aggregates its own chunk first, so only tiny partial counts travel through the shuffle, not the 75M customer rows.

Move a lot

  1. If you completed the five numbers activity, don't pay for that query twice: click View all jobs at the bottom of the page.
  2. Select the most recent job that shows a Slot contention insight, click View in editor, and skip to step 10.
  3. If you don't have that job, copy the -- join query query into the BigQuery editor and run it. It will take a couple of minutes.
  4. Open Execution Details and note the Bytes shuffled. Compare it to the first two queries.

A join must co-locate rows from both tables by the join key. There is no way to pre-shrink a raw join: all 75B line items and all the March orders travel through the shuffle to meet each other. That is why joins dominate the shuffle meter.

Find the guilty stage

  1. With the join query's results open, click on Execution Graph.
  2. Click through the stages and find the stage that wrote the most data to shuffle. Which table was it reading?

The check-engine light

  1. For each of your queries, check Bytes spilled to disk in Execution Details. The first two queries should show 0 B. The join query should show terabytes spilled.

Shuffle runs in a fast in-memory tier, until a stage produces more intermediate data than fits. The overflow goes to disk, and disk is orders of magnitude slower than memory. Bytes spilled > 0 is a check-engine light: a stage hit its memory ceiling. The join query lit it up, and the Slot contention insight is a related warning: the query wanted more compute than it could get. The fix is to shrink what reaches the shuffle: filter earlier, pre-aggregate before joins, or restructure the schema so the join disappears (the upcoming denormalized and nested activities do exactly that). Re-running the query changes nothing.

Some things to think about:

  • Shuffle isn't on the on-demand invoice (that's bytes processed), so why should you care about it?
  • The scan-and-filter query read 10x more data than the aggregation query, but shuffled less. What does that tell you about the relationship between bytes processed and bytes shuffled?

Setting up

  1. Make sure you have the BigQuery console open.
  2. In a new browser tab, open https://github.com/roitraining/gcp-demos/blob/master/bigquery/insights_example.sql

Trip the alarm

  1. Review the -- sales joined to price history query query. It builds two tables with GENERATE_ARRAY (so it bills zero bytes): 100,000 sales of 100 products, and a price history holding every price each product has ever had. It joins them on prod_code to compute total revenue.
  2. Copy the query into the BigQuery editor and run it.
  3. Look at the result: 100,000,000 rows came out of a 100,000 row sales table, and total revenue is in the billions for products that cost under $100.
  4. Click on Execution Graph and find the flagged stage. Click it and review the notice: This stage has join(s) that produce significantly more rows than it consumes. The rows from one join side match multiple rows from the other. The console has diagnosed the fan-out for you; BigQuery calls this insight a high-cardinality join.

Each sale should match one price. But prod_code is not unique in the price history (1,000 rows per product), so each sale matched every price the product ever had: a 1,000x fan-out. The dangerous part isn't the cost; it's that the revenue total is 1,000x wrong while looking perfectly plausible. Joining a fact table to a history or versioned dimension without picking the right version is one of the most common accidental query bombs, and the console spots it for you.

Fix what the insight named

  1. Review and run the -- sales joined to current price query query. Before joining, it reduces the price history to one row per product: the price currently in effect.
  2. Check the result: 100,000 rows (one per sale), a sane revenue total, and no flag in the Execution Graph.

The fix for a high-cardinality join is to make the key unique on one side before the join happens: pick the current version, pick the price in effect on the sale date, or pre-aggregate to the join key's grain. Which row is the right row is a business question, which is why BigQuery can only flag the problem, not fix it.

Read the diagnosis on a real query

  1. If you completed the shuffle and spill activity: click View all jobs at the bottom of the page, select the join query job with the Slot contention insight, and click View in editor.
  2. Open its Execution Graph and review the performance insights shown for that job.

The insights you may see, and what each means:

  • Slot contention - stages sat in wait; the project was out of slots
  • Insufficient shuffle quota - intermediate data outgrew the shuffle tier
  • High-cardinality join - a join emitted far more rows than it read, usually duplicate keys on both sides
  • Data input scale change - this run read much more than previous runs of the same query
  • Partition skew - a few workers got most of the data

Check insights first. If one fires, your diagnosis is done and the lever is named.

Some things to think about:

  • The alarm query billed $0 in bytes but still burned real slot time. Which pricing model would have felt that?
  • Where else does this fan-out bite? Consider joining two child tables of the same parent, like line items and shipments both keyed on order_num.
  • Ideally each sale would match the price in effect on the sale date, not just the current price. What would that join condition look like?

Read the meter before you run

  1. Copy the -- select star query query into the BigQuery editor, but do not run it.
  2. Look at the estimate in the lower left of the editor: This query will process 2.44 TB when run. That is the price of touching every column.
  3. Replace it with the -- two columns query query. The estimate drops to about 13 GB: roughly 190x cheaper for the same table and the same rows.

BigQuery storage is columnar: each column is stored as its own set of files, and you are billed for exactly the columns the query touches. Row count doesn't change the bill; column choice does.

The WHERE column counts too

  1. Replace the query with the -- filtered two columns query query. The estimate goes up slightly, even though the query returns fewer rows.

The meter counts columns touched, not columns returned. Filtering on binary means reading the binary column, so it joins the bill.

Nearly all columns, without the blob

  1. Replace the query with the -- select star except query query and check the estimate: about 15.5 GB for every column except one.

Some things to think about:

  • One column (content) holds 2.42 of the table's 2.44 TB. Which columns dominate your own tables?
  • An analyst's SELECT * exploration query pasted into a dashboard runs hundreds of times a day. What does that cost?

Setting up

  1. Make sure you have the BigQuery console open.
  2. In a new browser tab, open https://github.com/roitraining/gcp-demos/blob/master/bigquery/pruning_example.sql

This whole activity uses the query validator's estimate (lower left of the editor). You don't need to run anything.

Partition pruning

  1. Paste the -- unpartitioned table query query into the editor and read the estimate: about 112 GB to count one month's customers.
  2. Replace it with the -- partitioned table query query. Same filter, but the table is partitioned by order_date: about 9.3 GB. Eleven months of partitions were never opened.
  3. Replace it with the -- broken partition filter query query. It asks for exactly the same rows, but the estimate is back to 112 GB.

Pruning happens before execution, from partition metadata, and only when the filter compares the bare partition column against constants. Wrap the column in a function like FORMAT_DATE and BigQuery must read every row to evaluate it. The filter's shape matters, not its meaning.

Cluster pruning

  1. Paste the -- unclustered table query query and read the estimate: about 70 GB.
  2. Replace it with the -- clustered table query query. Same data, but the table is clustered on cust_state: about 1.4 GB. Within the storage, blocks that can't contain AK are skipped.
  3. Replace it with the -- broken cluster filter query query: UPPER(cust_state) turns block skipping off, and the estimate returns to about 70 GB.

Pruning is a contract with your WHERE clause: bare column on one side, constants on the other. If a table should never be scanned in full, require_partition_filter=TRUE turns "forgot the date filter" into an error instead of a 112 GB scan.

  2. Copy the query into the BigQuery editor and run it. It will take a minute or so.
  3. Open Execution Graph and look at the shape of the plan. One data source feeds its own Input stage (the 10K records edge tells you it's the product table). The other data source (the line item table) has no input stage at all: its arrow runs straight into the Join+ stage, because the 3.75B row scan happens inside the join. That is also why Join+ holds nearly all the query's slot time.
  4. Click the join stage and review the step list. The + in Join+ means extra steps were fused into the stage: this one READs, JOINs, and pre-AGGREGATEs in a single pass, which is why it outputs millions of partial results rather than billions of joined rows.
  5. Find the JOIN step in that list: it reads EACH WITH ALL.
  6. Note the Bytes shuffled in Execution Details.

When one side of a join is small, BigQuery copies the whole small table to every worker (ALL), and each worker joins its own chunk of the big table in place (EACH). One pass, and 3.75B rows never cross the network. This is why star schemas with small dimension tables stay fast with no tuning at all.

When both sides are big

  1. Review the -- hash join query query: 375M orders joined to 7.5M customers.
  2. Copy the query into the BigQuery editor and run it.
  3. Open Execution Graph: this time both tables get input stages feeding the join.
  4. Click the join stage and find the JOIN step: it reads EACH WITH EACH.
  5. Compare Bytes shuffled to the broadcast query. The hash join shuffled dozens of times more, on far less data.

The customer table is too big to copy to every worker, so BigQuery shuffles both tables by a hash of the join key: equal keys land in the same bucket, and one worker joins each bucket. Two full shuffles happen before any joining does.

Some things to think about:

  • You can't pick the join algorithm. What can you control? (Hint: how much data arrives at the join. The next activities pull exactly that lever.)
  • What could make a dimension table stop being broadcastable? What would keep it lean?

A join that cannot change the answer

  1. Review the -- join before declaring anything query query. It asks for order numbers on a single day. Look at the SELECT list: every column comes from the order table. The customer table is joined, but nothing from it is selected.
  2. Run the query and note the Slot time consumed in Execution Details.
  3. Open the Execution Graph. There is a Join stage, and about 12M customer rows arrive at it, purely to confirm that each order has a customer.

You can see the join is pointless, but BigQuery cannot. Nothing in the schema says an order always has exactly one matching customer, so dropping the join might change the row count. The optimizer has to do the work to be safe.

Tell the optimizer what you know

  1. Review the -- declare the primary key query and -- declare the foreign key query queries. These declare that cust_id uniquely identifies a customer, and that every order's cust_id points at one.
  2. Note the NOT ENFORCED on both. It is required, and it means exactly what it says: BigQuery will never check the claim.
  3. Run both statements against your own copies of the tables in the class dataset, replacing your_project. They finish almost instantly and bill nothing: no data is read or rewritten, only metadata is updated.
  4. Run the -- check what you declared query query to see the two constraints listed.

Run the same query again

  1. Run the -- join before declaring anything query query a second time, unchanged, against your declared tables.
  2. Compare the results to the first run: identical rows.
  3. Open the Execution Graph and compare it to the first run. The Join stage is gone entirely, and the customer table is never read.
  4. Compare Slot time consumed: roughly a quarter less, on a query whose text you never touched.

This is join elimination. Once the foreign key guarantees every order matches exactly one customer, and no customer column is selected, the join provably cannot change the result, so the optimizer removes it. Two lines of metadata sped up a query you did not edit, and they speed up every future query with the same shape.

What a false promise costs you

  1. Review the -- build a table pair that breaks the promise query query. Employee 3 sits in department 99, which does not exist. Run it to create the two small tables.
  2. Run the -- the honest answer query query. It returns employees 1 and 2. Employee 3 is dropped, correctly, because an inner join has nothing to match it to.
  3. Run the -- declare the false foreign key query query. It succeeds. Nothing was validated, and no warning was given.
  4. Run the -- the honest answer query query again, completely unchanged.
  5. Read the results: employee 3 is now included, in a join to a department that does not exist.

The query did not change, the data did not change, and the answer is now wrong. Because the declaration said every employee matches a department, BigQuery eliminated the join instead of performing it, and the unmatched row was never filtered out. No error, no warning, just a quietly incorrect result.

Some things to think about:

  • The habit of writing joins largest table first costs nothing and makes a good plan obvious, though the optimizer usually reorders anyway. Declared keys are the version of that idea it cannot work out for itself.
  • Where would a false foreign key come from in real life? (Hint: nobody declares one they know is false. It becomes false later, when a delete or a bad load leaves rows orphaned.)
  • If constraints are never enforced, what in your pipeline should be checking them? How would you find out you had orphaned rows before a query returned the wrong number?

Setting up

  1. Make sure you have the BigQuery console open.

  4. In a new browser tab, open https://github.com/roitraining/gcp-demos/blob/master/bigquery/autodetect_demo.sh
  5. Copy the contents of the file and paste them into your Cloud Shell terminal. This creates two daily usage drops from a vendor, plus a schema file.
  6. Look at the first few rows of Monday's file:
head -3 daily_usage_mon.csv
  1. The vendor writes N/A in the minutes column for meetings that never started. Find those rows in both files:
grep -n "N/A" daily_usage_mon.csv daily_usage_tue.csv

Monday's file has 100,000 rows with the N/A deep in the file (row 90,000). Tuesday's has 1,000 rows with the N/A at row 700. Keep that difference in mind.

The loud failure

  1. Load Monday's file, letting autodetect choose the types:
bq load --autodetect --source_format=CSV class.daily_usage daily_usage_mon.csv
  1. The load fails. Read the error: Unable to parse. Autodetect sampled the start of the file, saw only numbers in minutes, chose INTEGER, and then row 90,000 said N/A.

The silent failure

  1. Now load Tuesday's file the same way:
bq load --autodetect --source_format=CSV class.daily_usage daily_usage_tue.csv
  1. This load succeeds. Check what autodetect decided:
bq show --schema class.daily_usage
  1. Note the type of the minutes column: STRING. Tuesday's file is small enough that the N/A fell inside autodetect's sample, so it picked the only type that fits everything.
  2. In the BigQuery editor, try to use the data:
SELECT SUM(minutes) AS total_minutes FROM class.daily_usage
  1. The query fails: no version of SUM accepts a STRING.

Same bad value, two different outcomes, decided by where the value sat relative to autodetect's sample. Monday failed loudly: annoying, but you found out immediately. Tuesday failed silently: the load worked, the schema is wrong, and the damage surfaces later in every query that does math on minutes. The silent one is the one that costs you days.

Pin the schema, name the marker

  1. Look at the schema file:
cat daily_usage_schema.json
  1. Reload Monday's file, pinning the schema and telling BigQuery what the vendor means by N/A:
bq load --replace --source_format=CSV \
  --schema=daily_usage_schema.json \
  --skip_leading_rows=1 \
  --null_marker='N/A' \
  class.daily_usage daily_usage_mon.csv
  1. Load Tuesday's file the same way, without --replace (loads append by default):
bq load --source_format=CSV \
  --schema=daily_usage_schema.json \
  --skip_leading_rows=1 \
  --null_marker='N/A' \
  class.daily_usage daily_usage_tue.csv
  1. In the BigQuery editor, verify the loads:
SELECT
  COUNT(*) AS rows_loaded,
  COUNTIF(minutes IS NULL) AS null_minutes,
  SUM(minutes) AS total_minutes
FROM class.daily_usage
  1. 101,000 rows loaded, exactly two NULL minutes (the meetings that never started), and SUM works.

The cheap path to a schema file: let autodetect run once on a known-good file, dump it with bq show --schema, review and edit it, then load with --schema from then on. Note that --skip_leading_rows=1 became necessary once the schema was pinned: autodetect was skipping the header for you. Pin schemas for anything recurring.

Some things to think about:

  • What else do vendors put in numeric columns? Empty strings, null, -, missing...
  • What happens on the day the vendor adds a new column to the file?

Load the gzipped CSV

  1. Load the gzipped file, and keep an eye on the elapsed-seconds counter bq prints while it waits:
bq load --source_format=CSV \
  --skip_leading_rows=1 \
  --schema=meeting_id:STRING,user_id:STRING,minutes:INTEGER,event_date:DATE \

  gs://jwd-gcp-demos/ingest_demo/big/usage_big.csv.gz

Load the Parquet files

  1. Now load the Parquet copy of the same data. No --schema this time; Parquet files carry their own:
bq load --source_format=PARQUET \
  class.usage_history_pq \
  'gs://jwd-gcp-demos/ingest_demo/big_parquet/usage_big-*.parquet'
  1. Done in seconds, not minutes, despite being over twice the bytes.

bq show class.usage_history_csv
bq show class.usage_history_pq
  1. Both show 60,000,000 in Total Rows, and the Parquet-loaded table got the right types (INTEGER, DATE) from the files themselves.

A gzip file cannot be split: one worker has to decompress and parse it from start to finish, alone. The 100 Parquet files can be handed to 100 workers at once, and Parquet is a binary columnar format, so there is no text parsing at all. That's how "more than twice the bytes" became roughly 20x faster. For anything big, prefer Parquet or Avro; if it must be CSV or JSON, prefer many smaller files, uncompressed, over one large gzip.

Everything in this series so far moved data in batches, after the fact. This activity streams rows in one at a time, as they happen, with the Storage Write API in its simplest arrangement: JSON rows appended to a table's default stream.

Set up the stream

  1. Create the table the events will land in:
bq mk --table class.live_usage \
  meeting_id:STRING,user_id:STRING,minutes:INTEGER,event_ts:TIMESTAMP
  1. Make a working directory and move into it:
mkdir ~/stream_demo && cd ~/stream_demo
  1. Install the client library:
npm install @google-cloud/bigquery-storage
  1. Download the demo script:
curl -sO https://raw.githubusercontent.com/roitraining/gcp-demos/master/bigquery/storage_write_example.js
  1. Review the script in the browser tab you opened. It connects to the table's default stream, wraps the connection in a JSONWriter, then appends one JSON row per second for 30 seconds, as if meetings were ending live.

Watch rows arrive

  1. Run the script:
node storage_write_example.js
  1. While it prints appended once a second, switch to the BigQuery editor and run this a few times:
SELECT COUNT(*) AS so_far FROM class.live_usage
  1. The count climbs while the script runs. A row is queryable about a second after the append; there is no waiting for a batch.
  2. When the script finishes, look at the last few events:
SELECT * FROM class.live_usage ORDER BY event_ts DESC LIMIT 5

The Storage Write API speaks protocol buffers; the JSONWriter hides that by building a proto descriptor from the table's own schema and converting each JSON row for you (which is why the script passes the TIMESTAMP as microseconds since the epoch). The default stream gives at-least-once delivery, which is all most pipelines need. Application-created streams add exactly-once and transactional commits, and they're what Dataflow and the Kafka connectors use under the hood.

Unlike every load in this series, streaming is not free: ingestion bills at $0.025 per GiB, with the first 2 TiB per month free. These 30 tiny rows are far under that. The trade is cost for freshness; batch when you can, stream when the data can't wait.
