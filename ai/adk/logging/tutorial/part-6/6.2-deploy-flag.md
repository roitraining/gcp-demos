# 6.2 · Deploy A: the flag

*Part 6 · Agent Runtime*

> [!NOTE]
> **Why you are here.** 6.1 named two ways to turn telemetry on. This page
> deploys with the flag and reads back what it wrote to the deployment.

The flag writes the telemetry vars into the deployment's env and adds
`--otel_to_cloud` to the server command; the staged `.env` carries only the base
config. See
[Why stage a `.env` before deploying and remove it after?](#why-stage-a-env-before-deploying-and-remove-it-after)

**Step 1 — Stage the env file and deploy.** The deploy takes several minutes.

**Command:**

```bash
source env.sh
cp deploy/env/6.2a.env demo_agent/.env

DEPLOY_OUT=$(.venv/bin/adk deploy agent_engine \
  --project="$PROJECT_ID" \
  --region="$REGION" \
  --display_name="adk-logging-demo" \
  --otel_to_cloud \
  ./demo_agent 2>&1 | tee /dev/stderr)

export ENGINE_ID=$(printf '%s\n' "$DEPLOY_OUT" \
  | grep -oE 'reasoningEngines/[0-9]+' | tail -n1 | cut -d/ -f2)
```

The deploy prints `Ignoring GOOGLE_CLOUD_LOCATION in .env as --region was
explicitly passed`. That applies to where the engine is created; the env list in
Step 2 still carries `GOOGLE_CLOUD_LOCATION=global` for the model.

**Step 2 — Read the deployment's env list.** `gcloud ai` has no command that
reads an engine's env, so use the `vertexai` SDK.

**Command:**

```bash
.venv/bin/python - "$PROJECT_ID" "$REGION" "$ENGINE_ID" <<'PY'
import sys, vertexai
project, region, engine_id = sys.argv[1], sys.argv[2], sys.argv[3]
c = vertexai.Client(project=project, location=region)
e = c.agent_engines.get(
    name=f"projects/{project}/locations/{region}/reasoningEngines/{engine_id}"
)
for ev in e.api_resource.spec.deployment_spec.env:
    print(f"{ev.name}={ev.value}")
PY
```

**Expected output** (the flag added the last two lines):

```console
GOOGLE_GENAI_USE_VERTEXAI=TRUE
GOOGLE_CLOUD_LOCATION=global
LOG_LEVEL=info
GOOGLE_CLOUD_AGENT_ENGINE_ENABLE_TELEMETRY=true
ADK_CAPTURE_MESSAGE_CONTENT_IN_SPANS=false
```

> [!IMPORTANT]
> **What it means.** `GOOGLE_CLOUD_AGENT_ENGINE_ENABLE_TELEMETRY=true` turned
> telemetry on and `ADK_CAPTURE_MESSAGE_CONTENT_IN_SPANS=false` turned span
> content off. You wrote neither; the flag did.

**Step 3 — Send a query and read the logs back.** Agent Runtime logs lag
ingestion, so the `sleep 15` gives them time to land before the read.

**Command:**

```bash
.venv/bin/python - "$PROJECT_ID" "$REGION" "$ENGINE_ID" <<'PY'
import sys, vertexai
project, region, engine_id = sys.argv[1], sys.argv[2], sys.argv[3]
c = vertexai.Client(project=project, location=region)
a = c.agent_engines.get(
    name=f"projects/{project}/locations/{region}/reasoningEngines/{engine_id}"
)
for ev in a.stream_query(user_id="u1", message="What's the weather in London?"):
    pass
print("query sent")
PY

sleep 15

gcloud logging read \
  'resource.type="aiplatform.googleapis.com/ReasoningEngine"
   resource.labels.reasoning_engine_id="'"$ENGINE_ID"'"' \
  --project="$PROJECT_ID" \
  --limit=10 \
  --format='value(logName.basename(), textPayload)'
```

**Step 4 — Remove the staged `.env`.** Setup has no `demo_agent/.env`, and a
leftover one would apply its `LOG_LEVEL` over `--log_level` on a later local
run.

**Command:**

```bash
rm demo_agent/.env
```

**Step 5 — Tear down.**

**Command:**

```bash
.venv/bin/python - <<PY
import vertexai
vertexai.Client(project="$PROJECT_ID", location="$REGION").agent_engines.delete(
    name="projects/$PROJECT_ID/locations/$REGION/reasoningEngines/$ENGINE_ID",
    force=True)
PY
```

6.3 deploys again with the telemetry vars in `.env` instead of the flag.

## Deep dives

### Why stage a `.env` before deploying and remove it after?

A native deploy has no server script of yours, so the deployed agent reads
`LOG_LEVEL` and the telemetry settings from its environment.
`cli_deploy.py:1226-1234` reads the agent folder's `.env` into the deployment's
env vars, and the agent folder, `.env` included, is copied into the image. That
is why each deploy starts by copying a canned file from
[deploy/env/](../../deploy/env/) into `demo_agent/.env`, and ends by removing
it. The flag route here keeps `.env` to the base config and lets
`--otel_to_cloud` add the telemetry vars; 6.3 puts them in `.env` instead.
