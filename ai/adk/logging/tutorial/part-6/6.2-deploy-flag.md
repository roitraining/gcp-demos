# 6.2 · Deploy A: the flag

*Part 6 · Agent Runtime*

Copy the base env file into place, deploy with `--otel_to_cloud`, and capture the
engine id from the deploy output. The flag makes the CLI write the telemetry vars;
the `.env` carries only the base config.

**Command:**

```bash
source env.sh
cp deploy/env/6.2a.env demo_agent/.env

DEPLOY_OUT=$(.venv/bin/adk deploy agent_engine \
  --project="$PROJECT_ID" \
  --region="$REGION" \
  --display_name="adk-logging-demo" \
  --otel_to_cloud \
  ./demo_agent 2>&1 | tee /dev/stderr)

export ENGINE_ID=$(printf '%s\n' "$DEPLOY_OUT" \
  | grep -oE 'reasoningEngines/[0-9]+' | tail -n1 | cut -d/ -f2)
```

**Read the deployment's env list.** `gcloud ai` has no reasoning-engine
subcommand in every install, so use the `vertexai` SDK.

**Command:**

```bash
.venv/bin/python - "$GOOGLE_CLOUD_PROJECT" "$REGION" "$ENGINE_ID" <<'PY'
import sys, vertexai
project, region, engine_id = sys.argv[1], sys.argv[2], sys.argv[3]
c = vertexai.Client(project=project, location=region)
e = c.agent_engines.get(
    name=f"projects/{project}/locations/{region}/reasoningEngines/{engine_id}"
)
for ev in e.api_resource.spec.deployment_spec.env:
    print(f"{ev.name}={ev.value}")
PY
```

**Expected output** — the flag added the last two lines:

```console
GOOGLE_GENAI_USE_VERTEXAI=TRUE
GOOGLE_CLOUD_LOCATION=global
LOG_LEVEL=info
GOOGLE_CLOUD_AGENT_ENGINE_ENABLE_TELEMETRY=true
ADK_CAPTURE_MESSAGE_CONTENT_IN_SPANS=false
```

> [!IMPORTANT]
> **What it means.** `GOOGLE_CLOUD_AGENT_ENGINE_ENABLE_TELEMETRY=true` turned
> telemetry on and `ADK_CAPTURE_MESSAGE_CONTENT_IN_SPANS=false` set the span
> content knob safe. You wrote neither; the flag did.

**Send a query and read the logs back.** Agent Runtime logs lag ingestion, so
the `sleep 15` gives them time to land before the read.

**Command:**

```bash
.venv/bin/python - "$GOOGLE_CLOUD_PROJECT" "$REGION" "$ENGINE_ID" <<'PY'
import sys, vertexai
project, region, engine_id = sys.argv[1], sys.argv[2], sys.argv[3]
c = vertexai.Client(project=project, location=region)
a = c.agent_engines.get(
    name=f"projects/{project}/locations/{region}/reasoningEngines/{engine_id}"
)
for ev in a.stream_query(user_id="u1", message="What's the weather in London?"):
    pass
print("query sent")
PY

sleep 15

gcloud logging read \
  'resource.type="aiplatform.googleapis.com/ReasoningEngine"
   resource.labels.reasoning_engine_id="'"$ENGINE_ID"'"' \
  --project="$PROJECT_ID" \
  --limit=10 \
  --format='value(logName.basename(), textPayload)'
```

**Expected output** — the framework INFO lines, on the **stderr** log:

```console
reasoning_engine_stderr    ... - INFO - google_llm.py:255 - Sending out request, model: gemini-3.7-flash, backend: GoogleLLMVariant.VERTEX_AI, stream: False
reasoning_engine_stderr    ... - INFO - agent.py:54 - tool get_weather called for city='London'
reasoning_engine_stderr    ... - INFO - google_llm.py:327 - Response received from the model.
```

> [!IMPORTANT]
> **What Agent Runtime does NOT do, that Cloud Run did.** On Cloud Run (5.4) the
> same flag put `gen_ai.*` events in Cloud Logging. Here, with telemetry enabled
> and the env vars set, **no `gen_ai.*` log names and no Cloud Trace spans
> surfaced in our testing**, only the framework's `reasoning_engine_stderr` INFO
> lines. Where the OTel telemetry lands on a native deploy is an open question;
> see the Verification status in
> [How to choose & reference](../how-to-choose.md). What this section verifies
> is what each route writes to the deployment.

Restore the base `.env` so the deploy's `LOG_LEVEL` does not leak into a local
`adk web` run.

**Command:**

```bash
cp deploy/env/default.env demo_agent/.env
```

## Deep dives

### Why the copy and restore

`adk deploy agent_engine` copies the agent directory's `.env` into the deployment
(cli_deploy.py:1230-1234), and a native deploy has no server script of yours, so
the deployed agent reads `LOG_LEVEL` and the telemetry knobs from that `.env`.
That is why each deploy starts by copying a canned file from
[deploy/env/](../../deploy/env/) into `demo_agent/.env`, and ends by restoring
`default.env`. The flag route here keeps `.env` to the base config and lets
`--otel_to_cloud` add the telemetry vars; 6.3 puts them in `.env` instead.
