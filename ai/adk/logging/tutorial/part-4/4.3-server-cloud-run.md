# 4.3 · The same server on Cloud Run

*Part 4 · Structured logging*

> [!NOTE]
> **Why you are here.** On your laptop the JSON is text on a terminal. On Cloud
> Run, `severity` becomes a queryable level and the trace field groups a
> request. This is the fix for the blank severity you found in 1.4 and 1.5.

[deploy/deploy_cloudrun.sh](../../deploy/deploy_cloudrun.sh) containerizes
`06_custom_server.py` with `gcloud run deploy --source`, runs one turn against
the result, and fails loudly if it does not return 200. See
[Why can a successful deploy still fail every request?](#why-can-a-successful-deploy-still-fail-every-request)

**Step 1 — Deploy the server.**

**Command:**

```bash
source env.sh
./deploy/deploy_cloudrun.sh
```

**Step 2 — Send a turn.**

**Command:**

```bash
export URL=$(gcloud run services describe adk-logging-demo \
  --project="$PROJECT_ID" \
  --region="$REGION" \
  --format='value(status.url)')
curl -s \
  -X POST "$URL/chat" \
  -H 'content-type: application/json' \
  -d '{"message":"What'\''s the weather in Tokyo?"}'
```

**Step 3 — Read back the severity of your lines.**

The filter keeps entries that have a `jsonPayload.message` and a trace, which
drops uvicorn's startup lines.

**Command:**

```bash
gcloud logging read \
  'resource.type="cloud_run_revision" resource.labels.service_name="adk-logging-demo" jsonPayload.message:* trace:*' \
  --project="$PROJECT_ID" \
  --limit=20 \
  --order=asc \
  --format='table(severity, jsonPayload.message)' \
  --freshness=10m
```

**Expected output** (oldest first, trimmed to the first question, the deploy's
smoke test): a real `INFO` in the severity column, not the blank from 1.5.

```console
SEVERITY  MESSAGE
INFO      chat_request_received
INFO      llm_request
INFO      llm_response
INFO      tool_start
INFO      tool_end
INFO      llm_request
INFO      llm_response
INFO      chat_request_completed
```

Eight rows per question: the tool question calls the model twice. Each is JSON
that Cloud Logging parsed into `jsonPayload`, and its fields are columns you can
query. The framework lines are still there, as plain `textPayload`; you
filtered them out, not lost them. Cloud Logging moves the trace and
source-location fields out of each JSON line into the log entry. A line left
with only `message` is stored as `textPayload`, so the framework lines land
there even though the server wrote them as JSON.

**Step 4 — Query a plugin field.**

**Command:**

```bash
gcloud logging read \
  'resource.type="cloud_run_revision" jsonPayload.event="tool_end"' \
  --project="$PROJECT_ID" \
  --limit=5 \
  --format='table(jsonPayload.tool, jsonPayload.latency_ms, jsonPayload.status)' \
  --freshness=10m
```

**Expected output** (one row per question):

```console
TOOL         LATENCY_MS  STATUS
get_weather  0.5         ok
get_weather  0.8         ok
```

> [!IMPORTANT]
> **What it means.** No formatter change between laptop and cloud.
> `jsonPayload.status="error"` is now an alerting condition,
> `jsonPayload.latency_ms` a field you can turn into a log-based metric, and
> `severity` shows these at their real level. Because Cloud Run supplies a real
> `X-Cloud-Trace-Context` per request, clicking one line's trace in Logs
> Explorer shows the request grouped: your lines, the plugin's events, the
> `google_adk` lines, and Cloud Run's own request entry. The container's access
> line has no trace, because uvicorn writes it after the handler clears the
> trace id.

> [!WARNING]
> **Set `GOOGLE_CLOUD_LOCATION` as a real Cloud Run env var.** Without it, a
> deploy can succeed while every `/chat` returns 500.

**Step 5 — Tear down.**

**Command:**

```bash
gcloud run services delete adk-logging-demo \
  --project="$PROJECT_ID" \
  --region="$REGION" \
  --quiet
```

## Deep dives

### Why can a successful deploy still fail every request?

The model lives in `global` while the service runs in `us-central1`. If the
container resolves the wrong one, the deploy succeeds and every `/chat` returns
500 wrapping a 404 for the model. The script sets `GOOGLE_CLOUD_LOCATION` as a
real Cloud Run env var (`--set-env-vars`) so it beats any default. The smoke
test, not the deploy's exit code, is the real success check.
