# 4.4 · Callback or plugin?

*Part 4 · Structured logging*

> [!NOTE]
> **Why you are here.** The plugin is one of two ways to emit your own records;
> the other is a per-agent callback. Both sit alongside ADK's built-in logging,
> not in place of it.

To operate the agent you have to answer three questions:

1. Is the model call failing or being retried?
2. Which tool ran, with which arguments, and did it succeed?
3. How many tokens did this turn cost, and what is a session costing?

A `google_adk` level shows requests and errors at INFO, and request and
response bodies at DEBUG. Retry lines come from the separate `google_genai`
logger. None of it answers the second or third question in any form you can
query. Questions 2 and 3 are yours to collect as structured fields, and that is
what a callback or plugin is for. The rule is in addition to the framework
logger, not instead of it.

**The per-agent callback.** The same hook points exist on a single agent. Instead
of a plugin class, you attach a function:

```python
import logging

telemetry = logging.getLogger("agent.telemetry")   # your namespace, not google_adk

def log_tool(tool, args, tool_context):
    telemetry.info("tool_call", extra={
        "event": "tool_call",
        "tool": tool.name,
        "tool_args": args,
        "agent": tool_context.agent_name,
    })
    return None   # return a value instead to block or replace the call

root_agent = Agent(..., before_tool_callback=log_tool)
```

`getLogger("agent.telemetry")` returns a logger under a name you choose. You set
its level and handlers by that name in your logging config, and the logger name
is on every record. 4.3's formatter does not write it, so to filter on it in
Cloud Logging, add `entry["logger"] = record.name` to your formatter, then
filter on `jsonPayload.logger="agent.telemetry"`. Keeping it out of the `google_adk` tree
is what lets you control the two independently.

**Which to use.** The callback and the plugin run the same hooks; they differ in
scope.

| Use a plugin when... | Use a per-agent callback when... |
|---|---|
| you want uniform telemetry across every agent and tool | the logic belongs to one agent only |
| the logging carries state (a timer for latency) or config | you are prototyping and want the fewest lines |
| you want one field schema for every agent | you need to block or rewrite a step for that one agent |

A plugin registers once on the `App` and fires everywhere, which makes it the
right default for production telemetry: one place, one schema, every agent. A
per-agent callback is scoped to one agent. Reach for it when the logic is local
to one agent, or when you want a hook to short-circuit: returning a value from a
`before_*` callback blocks or replaces the step. Both run on the event loop, so keep the work cheap and non-blocking.
