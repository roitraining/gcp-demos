# 4.1 · The structured plugin

*Part 4 · Structured logging*

> [!NOTE]
> **Why you are here.** `LoggingPlugin` prints text. To query and alert on
> events, write your own plugin that emits JSON `logging` records.

A plugin's callbacks are the hook points. From
[examples/05_structured_plugin.py](../../examples/05_structured_plugin.py), the
"after model" hook records latency and token usage:

```python
class StructuredTelemetryPlugin(BasePlugin):
    async def after_model_callback(self, *, callback_context, llm_response):
        usage = getattr(llm_response, "usage_metadata", None)
        telemetry_log.info("llm_response", extra={
            "event": "llm_response",
            "agent": callback_context.agent_name,
            "latency_ms": ...,                       # measured in the plugin
            "input_tokens": getattr(usage, "prompt_token_count", None),
            "output_tokens": getattr(usage, "candidates_token_count", None),
        })
        return None   # returning None means "proceed normally"
```

**👉 Do this.** The example attaches a JSON formatter to the telemetry logger and
asks *"What's the weather in Tokyo?"*.

**Command:**

```bash
.venv/bin/python examples/05_structured_plugin.py
```

**Expected output** (one structured line per event; the tool question calls the
model twice):

```console
{"severity": "INFO", "message": "llm_request", "logger": "agent.telemetry", "event": "llm_request", "agent": "weather_agent"}
{"severity": "INFO", "message": "llm_response", "logger": "agent.telemetry", "event": "llm_response", "agent": "weather_agent", "latency_ms": 3512.1, "input_tokens": 167, "output_tokens": 16}
{"severity": "INFO", "message": "tool_start", "logger": "agent.telemetry", "event": "tool_start", "tool": "get_weather", "tool_args": {"city": "Tokyo"}}
{"severity": "INFO", "message": "tool_end", "logger": "agent.telemetry", "event": "tool_end", "tool": "get_weather", "latency_ms": 0.2, "status": "ok"}
{"severity": "INFO", "message": "llm_request", "logger": "agent.telemetry", "event": "llm_request", "agent": "weather_agent"}
{"severity": "INFO", "message": "llm_response", "logger": "agent.telemetry", "event": "llm_response", "agent": "weather_agent", "latency_ms": 2195.0, "input_tokens": 226, "output_tokens": 14}

FINAL ANSWER: The weather in Tokyo is currently 27°C and humid.
```

> [!IMPORTANT]
> **What it means.** Every line is a machine-readable event. The fields
> (`event`, `latency_ms`, `status`, `input_tokens`) become keys you can filter,
> aggregate, and alert on the moment these lines reach a log store. Nothing here
> is terminal-specific, so the same records work in the cloud once a server
> emits them. See [Why is the key `tool_args`, not `args`?](#why-is-the-key-tool_args-not-args)

4.2 runs this plugin inside a real HTTP server.

## Deep dives

### Why is the key `tool_args`, not `args`?

Keys in `extra=` must not collide with built-in `LogRecord` attributes (`args`,
`name`, `message`, `module`). `args` raises a `KeyError` inside the log call, so
the example uses `tool_args`.
