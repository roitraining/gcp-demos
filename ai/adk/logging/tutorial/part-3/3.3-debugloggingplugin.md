# 3.3 · DebugLoggingPlugin: capture one whole turn to a file

*Part 3 · Plugins*

> [!NOTE]
> **Why you are here.** When one turn misbehaves, you want the complete record to
> diff or attach to a bug report, not a stream you have to watch live.

```python
from google.adk.plugins import DebugLoggingPlugin
plugin = DebugLoggingPlugin(output_path="adk_debug.yaml")
```

Where `LoggingPlugin` prints each hook immediately, this plugin buffers the
whole turn and writes it once, as one YAML document, redacted and owner-only.
See [How does it differ from LoggingPlugin in source?](#how-does-it-differ-from-loggingplugin-in-source)

**👉 Do this.** Run the example, then open the file it writes. Each run appends
a `---` document, so delete the file first for a clean view.

**Command:**

```bash
rm -f adk_debug.yaml
.venv/bin/python examples/04_debug_plugin.py
cat adk_debug.yaml
```

Example 04 asks about a city the tool does not know, so the file includes an
error path. It passes `include_session_state=True` and
`include_system_instruction=True` explicitly. Both are the defaults, written out
so you can see the knobs exist.

**Expected output** (one YAML document per invocation: a header, then an
`entries:` list; trimmed to the first three entries, without the system
instruction):

```console
---
invocation_id: e-00436bc1-6828-4a2c-aea7-4bb6efe72cbb
session_id: eb488521-de34-481b-afa7-a02fb1e28903
app_name: debug_plugin_demo
user_id: u1
start_time: '2026-10-02T19:44:29.704847'
entries:
- timestamp: '2026-10-02T19:44:29.704863'
  entry_type: invocation_start
  invocation_id: e-00436bc1-6828-4a2c-aea7-4bb6efe72cbb
  agent_name: weather_agent
  data:
    branch: null
- timestamp: '2026-10-02T19:44:29.710546'
  entry_type: agent_start
  invocation_id: e-00436bc1-6828-4a2c-aea7-4bb6efe72cbb
  agent_name: weather_agent
  data:
    branch: null
- timestamp: '2026-10-02T19:44:29.735832'
  entry_type: llm_request
  invocation_id: e-00436bc1-6828-4a2c-aea7-4bb6efe72cbb
  agent_name: weather_agent
  data:
    model: gemini-3.7-flash
    content_count: 1
    contents:
    - role: user
      parts:
      - text: What's the weather in a city you don't know, like Paris?
    tools:
    - get_weather
```

The `entry_type` values, in order, trace the same lifecycle the terminal plugin
narrates: `invocation_start`, `agent_start`, `llm_request`, `llm_response`,
`event`, `tool_call`, `tool_response`, `event`, a second `llm_request` and
`llm_response`, `event`, `agent_end`, `session_state_snapshot`,
`invocation_end`. Unlike `LoggingPlugin`, the file has no user-message entry;
the prompt appears inside the first `llm_request`. The plugin's
`on_user_message_callback` runs before its `before_run_callback` sets up state,
so it logs `No debug state for invocation ..., skipping entry` on every run.

> [!IMPORTANT]
> **What it means.** The full turn on disk: exact prompt, system instruction,
> tool arguments, tool results, token counts, and session state. Two properties
> matter. It is buffered, so if the process dies mid-turn that turn is lost. And
> it redacts broadly: credential objects, keys with secret-like names,
> private-key blocks, and every `temp:` state key (ADK's per-question scratch
> state), so an intermediate value passed between agents under a `temp:` key
> reads as `[REDACTED]`.

The file still holds full prompt content, so it is created `0600` and should be
treated as sensitive. This is a debugging capture, not a log sink you leave
running. Example 04 also reads its output path from a `DEBUG_OUTPUT`
environment variable, which 3.4 uses to redirect the capture off the container.

## Deep dives

### How does it differ from LoggingPlugin in source?

Both subclass `BasePlugin` and override the same hooks. Almost everything else
is opposite:

| | `LoggingPlugin` | `DebugLoggingPlugin` |
|---|---|---|
| Sink | `print()` to stdout | a YAML file |
| When it writes | immediately, at every hook | buffered in memory, written once per invocation in `after_run_callback` |
| Detail | truncated; no request contents | full request contents, config, tool list, responses, session state |
| Redaction | none | credential models, secret-named keys, private-key blocks, all `temp:` state |
| File safety | not applicable | created `0600`; warns once if an existing file is wider |
| Own diagnostics | none | emits real `logging` warnings and errors |

Its constructor exposes the knobs the terminal plugin lacks, all keyword-only:

```python
def __init__(
    self,
    *,
    name: str = "debug_logging_plugin",
    output_path: str = "adk_debug.yaml",
    include_session_state: bool = True,
    include_system_instruction: bool = True,
):
```

`before_model_callback` records the request as structured data and keeps the
whole thing:

```python
request_data = {
    "model": llm_request.model,
    "content_count": len(llm_request.contents),
    "contents": [self._serialize_content(c) for c in llm_request.contents],
}
if llm_request.tools_dict:
    request_data["tools"] = list(llm_request.tools_dict.keys())
self._add_entry(callback_context.invocation_id, "llm_request", **request_data)
```

Nothing is written until the invocation ends. `after_run_callback` dumps the
buffered entries as one YAML document and creates the file readable only by its
owner:

```python
fd = os.open(self._output_path,
             os.O_WRONLY | os.O_CREAT | os.O_APPEND, _OUTPUT_FILE_MODE)  # 0o600
with os.fdopen(fd, "a", encoding="utf-8") as f:
    f.write("---\n")
    yaml.dump(output_data, f, default_flow_style=False,
              allow_unicode=True, sort_keys=False, width=120)
```
