# 1.4 · The same script on Cloud Run, and what Cloud Logging does to it

*Part 1 · The log level*

> [!NOTE]
> **Why you are here.** Once you deploy, Cloud Logging reads each line, assigns
> it a **severity**, and files it under a stream. This section shows what it
> makes of the *unmodified* Part 1 script, and the answer is not what the common
> advice says.

The script runs once and exits, so it deploys as a Cloud Run **Job**, not a
service. [deploy/deploy_job.sh](../../deploy/deploy_job.sh) builds the image,
deploys the Job, and runs it once. The level is a Job argument, so you can rerun
at a different level without rebuilding. See
[Why a Job and not a service](#why-a-job-and-not-a-service).

**👉 Do this.** Deploy and run at INFO, then run again at WARNING.

**Command:**

```bash
source env.sh
./deploy/deploy_job.sh
gcloud run jobs execute adk-logging-job \
  --project="$PROJECT_ID" \
  --region="$REGION" \
  --args=warning \
  --wait
```

Read both runs back, asking for the severity of each line.

**Command:**

```bash
gcloud logging read \
  'resource.type="cloud_run_job" resource.labels.job_name="adk-logging-job"' \
  --project="$PROJECT_ID" \
  --limit=40 \
  --format='table(severity,textPayload)' \
  --freshness=15m
```

**Expected output** — the INFO execution carries the full lifecycle, the WARNING
execution almost nothing (trimmed, most recent first):

```console
SEVERITY  TEXT_PAYLOAD
          ===== running at WARNING =====
          >>> ANSWER: The weather in Tokyo is currently 27°C and humid.
INFO      Container called exit(0).
          ===== running at INFO =====
          INFO - google_adk.google.adk.models.google_llm - Sending out request, model: gemini-3.7-flash, backend: GoogleLLMVariant.VERTEX_AI, stream: False
          INFO - demo_agent.agent - tool get_weather called for city='Tokyo'
          INFO - google_adk.google.adk.models.google_llm - Response received from the model.
          >>> ANSWER: The weather in Tokyo is currently 27°C and humid.
INFO      Container called exit(0).
```

> [!IMPORTANT]
> **What it means, finding one: the level dial works in the cloud, unchanged.**
> The WARNING execution shows the banner and the answer and no `google_adk` or
> tool lines. The INFO execution shows the five-line lifecycle from 1.1.1.

> [!IMPORTANT]
> **What it means, finding two: severity is not what you were told.** The Cloud
> Run docs, and ADK's own source comments, say a line written to stderr is
> recorded as ERROR. `logging.basicConfig` writes to stderr, so every `INFO -`
> line above should read as ERROR. It does not. Every one came through with
> **blank (Default) severity**. See
> [The stderr-means-ERROR rule](#the-stderr-means-error-rule) for the proof
> that these lines really are on stderr.

So the zero-effort deploy gets you two-thirds of the way. Your logs reach Cloud
Logging, and the level still filters them. What you do not get is queryable
severity: a severity-based query or alert cannot tell an error from a routine
step. Making severity a field you set, not a guess Cloud Run makes from the
stream, is Part 4's job.

> [!NOTE]
> Cloud Run batches burst console output, so several of the script's lines can
> arrive grouped under one Cloud Logging entry. That is a grouping artifact of
> the read, not a change to your logs.

## Deep dives

### Why a Job and not a service

The script serves no HTTP. A Cloud Run service would fail its readiness check
with no port to probe. A Job runs the container to completion, and Cloud Run
ingests its stdout and stderr into Cloud Logging automatically.

### The stderr-means-ERROR rule

Confirm the `INFO -` lines are on stderr, and check their severity again.

**Command:**

```bash
gcloud logging read \
  'resource.type="cloud_run_job" resource.labels.job_name="adk-logging-job"
   textPayload:"get_weather"' \
  --project="$PROJECT_ID" \
  --limit=1 \
  --format='value(logName,textPayload)' \
  --freshness=15m
```

The line is on stderr (`.../logs/run.googleapis.com%2Fstderr`), and its severity
is still Default, not ERROR. The rule is real in some contexts but not the
blanket law it is usually stated as, and 1.5 finds the same Default-not-ERROR
result on a Cloud Run *service*. Do not assume the severity of a plain line.
Check it.
