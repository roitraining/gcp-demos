# 1.6 · The same agent on Agent Runtime

*Part 1 · The log level*

> [!NOTE]
> **Why you are here.** Agent Runtime is the other place you deploy. This page
> deploys the agent natively with `adk deploy agent_engine`, where the platform
> runs the server, and shows that the platform then owns the log format.

There is no `--log_level` flag here. The agent reads `LOG_LEVEL` from the
environment, and the deploy script sets it for you. See
[How does the level reach the deployed agent?](#how-does-the-level-reach-the-deployed-agent)

**Step 1 — Deploy the agent.**

The deploy takes several minutes and prints the engine id on a final
`ENGINE_ID=` line, which the command captures into a variable. See
[What does the deploy script do?](#what-does-the-deploy-script-do)

**Command:**

```bash
source env.sh
export ENGINE_NATIVE=$(./deploy/deploy_agent_engine.sh | sed -n 's/^ENGINE_ID=//p')
```

> [!NOTE]
> **Back in a fresh shell, or `$ENGINE_NATIVE` empty?** The `export` above only
> ran in the terminal that deployed, so in a new shell the next steps build a
> broken URL and the platform returns a bare `400 INVALID_ARGUMENT`. Re-export
> the id from the live engine by display name instead of redeploying:
>
> ```bash
> source env.sh
> list_engine() {
>   curl -s -H "Authorization: Bearer $(gcloud auth print-access-token)" \
>     "https://$REGION-aiplatform.googleapis.com/v1/projects/$PROJECT_ID/locations/$REGION/reasoningEngines" \
>   | python3 -c "import sys,json;print(next((e['name'].split('/')[-1] for e in json.load(sys.stdin).get('reasoningEngines',[]) if e.get('displayName')=='$1'),''))"
> }
> export ENGINE_NATIVE=$(list_engine adk-logging-demo)
> echo "NATIVE=$ENGINE_NATIVE"
> ```

**Step 2 — Ask the question through the SDK.**

The query path is not a plain REST URL you can curl, so use the `vertexai` SDK.

**Command:**

```bash
: "${ENGINE_NATIVE:?set ENGINE_NATIVE first (see the note above)}"
.venv/bin/python - <<PY
import vertexai
c = vertexai.Client(project="$PROJECT_ID", location="$REGION")
agent = c.agent_engines.get(
    name="projects/$PROJECT_ID/locations/$REGION/reasoningEngines/$ENGINE_NATIVE")
for ev in agent.stream_query(user_id="u1", message="What's the weather in Tokyo?"):
    for part in ((ev or {}).get("content") or {}).get("parts", []):
        if part.get("text"):
            print(part["text"])
PY
```

> [!WARNING]
> `adk deploy agent_engine` can exit 0 when the deploy failed, so confirm with
> this query.

**Step 3 — Read the logs.**

The agent and framework lines land on `reasoning_engine_stderr` and the access
lines on `reasoning_engine_stdout`; filtering on `resource.type` catches both.

**Command:**

```bash
gcloud logging read \
  'resource.type="aiplatform.googleapis.com/ReasoningEngine"
   resource.labels.reasoning_engine_id="'"$ENGINE_NATIVE"'"' \
  --project="$PROJECT_ID" \
  --limit=30 \
  --format='table(severity,textPayload)' \
  --freshness=15m
```

**Expected output** (most recent first, trimmed to the question's lines):

```console
SEVERITY  TEXT_PAYLOAD
          2026-10-03 02:34:49,898 - INFO - google_llm.py:327 - Response received from the model.
          2026-10-03 02:34:47,929 - INFO - google_llm.py:255 - Sending out request, model: gemini-3.7-flash, backend: GoogleLLMVariant.VERTEX_AI, stream: False
          2026-10-03 02:34:47,769 - INFO - agent.py:54 - tool get_weather called for city='Tokyo'
          2026-10-03 02:34:47,633 - INFO - google_llm.py:327 - Response received from the model.
          2026-10-03 02:34:45,502 - INFO - google_llm.py:255 - Sending out request, model: gemini-3.7-flash, backend: GoogleLLMVariant.VERTEX_AI, stream: False
          INFO:     169.254.169.126:46072 - "POST /api/stream_reasoning_engine HTTP/1.1" 200 OK
```

> [!IMPORTANT]
> **What it means.** The platform, not your code, sets the format here. On Cloud
> Run (1.5) the tool line read `INFO - demo_agent.agent - tool get_weather...`.
> Here it is the ADK CLI's timestamped `file:line` format from 1.3, because the
> platform installs its own logging handler before your module runs. It decides
> the format and the destination (stderr). The level still applies.

**Step 4 — Tear down.**

**Command:**

```bash
.venv/bin/python - <<PY
import vertexai
vertexai.Client(project="$PROJECT_ID", location="$REGION").agent_engines.delete(
    name="projects/$PROJECT_ID/locations/$REGION/reasoningEngines/$ENGINE_NATIVE",
    force=True)
PY
```

Each deploy creates a new engine unless you pass `--agent_engine_id`, so delete
the engines you no longer use.

1.7 deploys your own container to Agent Runtime instead, and takes the format
back.

## Deep dives

### How does the level reach the deployed agent?

`adk deploy agent_engine` packages the agent directory and hands it to the
platform. There is no server of yours, so no `uvicorn.run` and no
`configure()` call at a `__main__`. The one hook for the log level is an
environment variable: `demo_agent/agent.py` reads `LOG_LEVEL` at import and
applies it. The deploy command's `--env_file` flag is deprecated, so it reads
the agent folder's `.env`, and
[deploy/deploy_agent_engine.sh](../../deploy/deploy_agent_engine.sh) writes
`LOG_LEVEL` into `demo_agent/.env` for the deploy. Afterward it restores your
original file, or removes it if you had none. The cleanup matters: ADK loads the
agent's `.env` at startup, so a leftover `LOG_LEVEL=warning` would override
`--log_level INFO` on a later `adk web` run.

### What does the deploy script do?

[deploy/deploy_agent_engine.sh](../../deploy/deploy_agent_engine.sh) wraps a
single `adk deploy agent_engine ./demo_agent` call in the setup that call needs.

It stages `demo_agent/.env`, because `adk deploy agent_engine` copies that file
into the deployment. That is how the model config and `LOG_LEVEL` reach the
deployed agent. A trap restores your original file on exit, or removes the
staged one if you had none:

```bash
cat > ./demo_agent/.env <<ENV
GOOGLE_GENAI_USE_VERTEXAI=TRUE
GOOGLE_CLOUD_PROJECT=${PROJECT_ID}
GOOGLE_CLOUD_LOCATION=${MODEL_LOCATION}
LOG_LEVEL=${LOG_LEVEL}
ENV
```

It then deploys. The `--otel_to_cloud` flag turns on telemetry, which Part 6
covers:

```bash
./.venv/bin/adk deploy agent_engine \
  --project="$PROJECT_ID" \
  --region="$REGION" \
  --display_name="adk-logging-demo" \
  --otel_to_cloud \
  ./demo_agent
```

It ends by printing the engine id on a machine-readable last line, which Step 1
captures into `ENGINE_NATIVE`:

```bash
printf 'ENGINE_ID=%s\n' "$ENGINE_ID"
```

### What do the `vertexai.Client` warnings mean?

The code uses `vertexai.Client`, which still works but warns;
`agentplatform.Client` is its new name.
