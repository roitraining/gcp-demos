# 5.5 · Your own server: install the exporters yourself

*Part 5 · OpenTelemetry*

> [!NOTE]
> **Why you are here.** In 5.1-5.4 the ADK CLI started the process and installed
> the Cloud exporters. Your own server (Part 4) has no CLI, so the `gen_ai.*`
> events are produced but never leave the process. This section adds the two
> lines that send them to Cloud Logging.

**The two calls.** Build the Cloud Logging exporter, then register it, the same
shape the [ADK logging docs](https://adk.dev/observability/logging/#gcp-export-setup_1)
show. In [examples/08_otel_server.py](../../examples/08_otel_server.py) they run
in the `lifespan`, before the `Runner` is built:

```python
from google.adk.telemetry.google_cloud import get_gcp_exporters
from google.adk.telemetry.setup import maybe_set_otel_providers

os.environ.setdefault("OTEL_SERVICE_NAME", "weather-agent")
hooks = get_gcp_exporters(enable_cloud_logging=True)
maybe_set_otel_providers([hooks])
```

`get_gcp_exporters` reads the project and credentials from ADC.
`OTEL_SERVICE_NAME` becomes the entry's resource `job` label in Cloud Logging.
Unlike 5.2, every `OTEL_*` variable can live in `.env` here, because the server
calls `bootstrap()` (which loads `.env`, `examples/_common.py:49-55`) before it
builds the exporters.

**Step 1 — Run the server and send one turn.** A leftover shell export of the
content knob from 5.2 would beat `.env`, so clear it first.

**Command:**

```bash
unset OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT
.venv/bin/python examples/08_otel_server.py
```

**Command** (second terminal):

```bash
curl -s -X POST localhost:8080/chat \
     -H 'content-type: application/json' \
     -d '{"message": "What is the weather in London?"}'
```

**Expected output:**

```console
{"response":"The weather in London is currently 15°C with drizzle."}
```

**Step 2 — Read the events back.** Open Logs Explorer, turn on **Show query**,
and run `logName=~"gen_ai\."` in the **Query editor**. The same `gen_ai.*`
events from 5.2-5.4 are there, from a server you wrote. They land on a
`generic_task` resource whose `job` is your `OTEL_SERVICE_NAME`
(`weather-agent`), so `resource.labels.job="weather-agent"` filters to this
server.

**Step 3 — The content knob, set through `.env`.** The server loads the tutorial
root's `.env` (`ai/adk/logging/.env`, the one beside `env.sh`, not
`demo_agent/.env`), and it carries
`OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT=true`, so the Step 1 entries
show the prompt and reply text. Comment out that `true` line if it is there, turn
content off, and opt in to the experimental semantic convention the rest of this
tutorial uses, all in the root `.env`. Restart the server and send the turn again.

**In `ai/adk/logging/.env`:**

```bash
# OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT=true
OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT=NO_CONTENT
OTEL_SEMCONV_STABILITY_OPT_IN=gen_ai_latest_experimental
```

Stop the server with Ctrl-C in terminal 1 and restart it.

**Command:**

```bash
.venv/bin/python examples/08_otel_server.py
```

Send the turn again.

**Command** (second terminal):

```bash
curl -s -X POST localhost:8080/chat \
     -H 'content-type: application/json' \
     -d '{"message": "What is the weather in London?"}'
```

Re-run `logName=~"gen_ai\."` in Logs Explorer and expand the newest entries.
Every `gen_ai.*` entry now reads `<elided>` in the content field, with no code
change and no shell export. `NO_CONTENT` is the production default; leave it
there unless you have a reviewed reason (5.6).

**Step 4 — Deploy the same server to Cloud Run.** The container runs
`python examples/08_otel_server.py` with no change to its code. This image bakes
no `.env`, so the content knob and the experimental opt-in both go in
`--set-env-vars`.

**Command:**

```bash
export PROJECT_ID="$(gcloud config get-value project)"
export REGION=us-central1

cp deploy/Dockerfile.otel_server ./Dockerfile

gcloud run deploy adk-otel-server \
  --source . \
  --project="$PROJECT_ID" \
  --region="$REGION" \
  --allow-unauthenticated \
  --set-env-vars="GOOGLE_GENAI_USE_VERTEXAI=TRUE,GOOGLE_CLOUD_PROJECT=$PROJECT_ID,GOOGLE_CLOUD_LOCATION=global,OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT=NO_CONTENT,OTEL_SEMCONV_STABILITY_OPT_IN=gen_ai_latest_experimental"

rm -f ./Dockerfile
```

`gcloud run deploy --source .` builds from `./Dockerfile`, so
[deploy/Dockerfile.otel_server](../../deploy/Dockerfile.otel_server) is copied
there for the build, the same pattern `deploy/deploy_cloudrun.sh` uses for
Part 4. Curl the service, read `gen_ai.*` back as in Step 2 (the resource `job`
is now the Cloud Run service, content `<elided>`), then tear down.

**Command:**

```bash
export URL=$(gcloud run services describe adk-otel-server \
  --project="$PROJECT_ID" --region="$REGION" --format='value(status.url)')

curl -s -X POST "$URL/chat" \
     -H 'content-type: application/json' \
     -d '{"message": "What is the weather in London?"}'

gcloud run services delete adk-otel-server --project="$PROJECT_ID" --region="$REGION" --quiet
```

To point the same server at a non-Google OTLP backend, only the exporter
changes. 5.7 has the snippet and the env-var table.
