# 5.1 · With nothing configured, `adk web` is already tracing

*Part 5 · OpenTelemetry*

> [!NOTE]
> **Why you are here.** Do not go find an exporter yet. Run the agent with no
> flags, no `OTEL_*` variables, and no code, then read the spans back in the dev
> UI. Knowing what you get for free makes the rest of this part a short list of
> deltas.

**Step 1 — Start the dev UI.** No flags of any kind.

**Command:**

```bash
adk web ./
```

**Step 2 — Send one turn.** Go to `localhost:8000`, pick **demo_agent** from the
app dropdown, start a new session or reuse one, and ask:

```
What's the weather in London?
```

The reply ends in `The weather in London is currently 15°C and drizzling.`
Nothing in the chat UI announces that anything was traced.

**Step 3 — Click the Trace tab.** Same session, same turn. The tab renders the
span tree the dev server's debug endpoint returns. The tree for this turn:

```console
invocation  (4281 ms)
  invoke_agent weather_agent  (4270 ms)
    call_llm  (2649 ms)
      generate_content gemini-3.7-flash  (2641 ms)
      execute_tool get_weather  (1 ms)
    call_llm  (1583 ms)
      generate_content gemini-3.7-flash  (1580 ms)
```

> [!IMPORTANT]
> **What it means.** The run you have watched all tutorial, in the one shape a
> log cannot give you:
>
> | Reading | Why it matters |
> |---|---|
> | Five of the 5.0 span names, all present | ADK instrumented the turn itself; you added nothing |
> | 2649 ms + 1583 ms of model time against a **1 ms** tool | the tree answers the latency question |
> | `execute_tool get_weather` is a **child of the first `call_llm`** | the tool span opens inside the model call that requested it, so a slow tool shows up as time inside that round trip |
>
> Part 1 showed this turn as five flat INFO lines. Here the nesting and the
> durations are the data.

**Step 4 — Click the `execute_tool get_weather` span.** Selecting the node opens
a panel of that span's fields:

| Field | Value here | What it is |
|---|---|---|
| Name | `execute_tool get_weather` | the standard GenAI verb plus your function's name |
| Span ID / Parent ID | `6237947…` / `9487881…` | the Parent ID is the first `call_llm` |
| Trace ID | `1.2672905…` | shared by every span in this turn, the join key across them |
| Start / End Time | `12:12:36` → `12:12:36` | the 1 ms you read off the tree, to the wall clock |
| Events → Event ID | `061fbc54…` | ADK's own event id, the join key back to the `/run` response's event list |

The panel shows durations and identity, not the tool's arguments or return
value. That is **content**, and where it lives and the knob that turns it off
is 5.2's subject.

You are not switching tracing on in 5.2; it is on. You are giving the spans
somewhere durable to go. See
[Where these spans have been living](#where-these-spans-have-been-living) and
[The endpoint behind the tab](#the-endpoint-behind-the-tab).

## Deep dives

### Where these spans have been living

Three facts explain the output above, each one place in the installed source:

1. **A real tracer provider is always installed.** The CLI's `_setup_telemetry`
   has three branches: `--otel_to_cloud`, then any `OTEL_EXPORTER_OTLP_*_ENDPOINT`
   variable, then a plain `TracerProvider` when neither applies
   (`cli/api_server.py:649-666`). You took the third branch, and it is a working
   provider, not a no-op stub.
2. **Its exporters write to process memory.** Whichever branch runs, the server
   hands it the same two: `ApiServerSpanExporter`, which stashes attributes in a
   dict keyed by event id (`cli/api_server.py:458`), and `InMemoryExporter`,
   which keeps whole spans keyed by session (`:483`). Both are passed in at the
   call site (`:1170-1178`).
3. **Nothing leaves the process.** No network exporter is registered on that
   third branch. The spans are visible only through the Trace tab and the two
   `/dev` endpoints behind it, and they are gone when you press Ctrl-C. Restart
   `adk web` and reopen the same session's Trace tab: the session still exists
   in `demo_agent/.adk/session.db`, and the spans do not.

### The endpoint behind the tab

The Trace tab is a UI over `/dev/apps/{app}/debug/trace/session/{id}`, which
returns the tree as JSON. [otel/check_local.sh](../../otel/check_local.sh) uses
it to start a plain `adk web`, run one turn, assert the five span names and
their counts, and exit non-zero if any is missing. It needs the model and
nothing else.

A narrower view at `/dev/apps/{app}/debug/trace/{event_id}`, keyed by
`gcp.vertex.agent.event_id`, returns one span's attributes rather than a tree,
and only ever sees three kinds of span: the exporter behind it keeps `call_llm`,
`send_data`, and anything starting with `execute_tool`, and drops the rest
(`cli/api_server.py:467-471`). Use the session view, or the Trace tab that reads
it, for the whole picture. `adk api_server` installs the same exporters but
serves no `/dev` routes at all (5.3).
