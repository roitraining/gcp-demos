# 5.4 · The same flag on Cloud Run: `adk deploy cloud_run --otel_to_cloud`

*Part 5 · OpenTelemetry*

> [!NOTE]
> **Why you are here.** 5.2 and 5.3 ran the flag on your laptop under your ADC
> login. This section ships the same flag to Cloud Run and reads the same
> `gen_ai.*` events back, produced by a process running under a service account.

`adk deploy cloud_run --otel_to_cloud` bakes the flag into the container's start
command (`cli/cli_deploy.py:216`), so the server inside Cloud Run installs the
same exporters it installed on your laptop. No agent code, no `OTEL_*`
variables in the deploy.

**Step 1 — Deploy.**

**Command:**

```bash
source env.sh

.venv/bin/adk deploy cloud_run \
  --project="$PROJECT_ID" \
  --region="$REGION" \
  --service_name=adk-logging-otel \
  --otel_to_cloud \
  ./demo_agent \
  -- \
  --allow-unauthenticated \
  --set-env-vars="GOOGLE_GENAI_USE_VERTEXAI=TRUE,GOOGLE_CLOUD_PROJECT=$PROJECT_ID,GOOGLE_CLOUD_LOCATION=global"
```

Everything after `--` passes straight through to `gcloud run deploy`. Watch the
build finish and note the service URL it prints. `GOOGLE_CLOUD_LOCATION=global`
must be set here because the model runs in `global`, not the service's region.
See
[Where does .env go, and why is the location repeated?](#where-does-env-go-and-why-is-the-location-repeated)

**Step 2 — Send one turn.** Grab the service URL, then curl it.

**Command:**

```bash
export URL=$(gcloud run services describe adk-logging-otel \
  --project="$PROJECT_ID" \
  --region="$REGION" \
  --format='value(status.url)')
```

```bash
curl -s \
  -X POST "$URL/apps/demo_agent/users/u1/sessions/s5-run" \
  -H 'content-type: application/json' \
  -d '{}'
```

```bash
curl -s \
  -X POST "$URL/run" \
  -H 'content-type: application/json' \
  -d '{"app_name":"demo_agent","user_id":"u1","session_id":"s5-run",
       "new_message":{"role":"user","parts":[{"text":"What'\''s the weather in London?"}]}}'
```

**Expected output** (the `/run` response holds three events; the last one's
content, trimmed):

```console
{"parts": [{"text": "The current weather in London is 15\u00b0C and drizzling.", "thoughtSignature": "AY89a18H..."}], "role": "model"}
```

If the curl errors, read the build output rather than trusting the deploy. See
[What can go wrong in the deploy?](#what-can-go-wrong-in-the-deploy)

**Step 3 — Read the events back.** In **Logs Explorer**, with **Show query** on,
run the 5.2 query in the **Query editor**:

**Query:**

```
logName=~"gen_ai\."
```

**Expected output** (eight entries for the turn; one `gen_ai.choice`, with the
resource's `task_id` trimmed):

```console
{
  "jsonPayload": {
    "content": "<elided>",
    "finish_reason": "STOP",
    "index": 0
  },
  "resource": {
    "labels": {
      "job": "adk-logging-otel",
      "location": "us-central1",
      "namespace": "",
      "project_id": "<your-project>",
      "task_id": "0010dd860722..."
    },
    "type": "generic_task"
  },
  "labels": {
    "event.name": "gen_ai.choice",
    "gen_ai.system": "vertex_ai"
  },
  "logName": "projects/<your-project>/logs/gen_ai.choice",
  "trace": "projects/<your-project>/traces/2abfbeddc26326562e9c82494f8e667d",
  "spanId": "e358a340b886745d"
}
```

> [!IMPORTANT]
> **What it means.** The same `gen_ai.system.message`, `gen_ai.user.message`,
> and `gen_ai.choice` events as 5.2 Step 3 appear, now from Cloud Run. To get
> one `operation.details` event per model call instead, add
> `OTEL_SEMCONV_STABILITY_OPT_IN=gen_ai_latest_experimental` to
> `--set-env-vars`. Event content is elided because
> `OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT` defaults to `NO_CONTENT`.
> Span content is controlled separately by `ADK_CAPTURE_MESSAGE_CONTENT_IN_SPANS`,
> which defaults to on; `adk deploy cloud_run` does not turn it off. On Cloud
> Run the exporter labels these entries with a `generic_task` resource whose
> `job` is the service name.

**Step 4 — Tear down.**

**Command:**

```bash
gcloud run services delete adk-logging-otel \
  --project="$PROJECT_ID" \
  --region="$REGION" \
  --quiet
```

5.5 is the one place in this part where the CLI is not starting the process,
so you install the exporters yourself.

## Deep dives

### Where does .env go, and why is the location repeated?

`adk deploy cloud_run` copies the whole agent folder into the container image,
including a `demo_agent/.env` if you created one. But `.env` is a file ADK
loads, and a real environment variable beats it. ADK's generated Dockerfile sets
one: `ENV GOOGLE_CLOUD_LOCATION` to the service's region, `us-central1`
(`cli/cli_deploy.py:193`). That is wrong for the model, which runs in `global`.
`GOOGLE_CLOUD_LOCATION=global` in `--set-env-vars` is also a real env var,
applied last, so it wins.

### What can go wrong in the deploy?

- `adk deploy` exits `0` even when the deploy failed
  (`cli/cli_tools_click.py:2456`). The curl in Step 2 is the real check.
- The container needs `opentelemetry-exporter-gcp-logging` and
  `opentelemetry-exporter-otlp-proto-http`, or it crashes on boot at the Cloud
  Logging import (`telemetry/google_cloud.py:272`).
  `demo_agent/requirements.txt` pins both.
