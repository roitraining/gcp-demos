# 5.8 · How this relates to Parts 1-4

*Part 5 · OpenTelemetry*

> [!NOTE]
> **Why you are here.** Parts 1-3 gave you three ways to see a turn: `google_adk`
> DEBUG lines, the `LoggingPlugin`, and your own structured logs. Part 5 added a
> fourth: OTel `gen_ai.*` events. Run one turn with the first three **and** OTel
> export on at once, and the same prompt can appear in **four places**. This
> section says which of the four are the same data, which are independent, and how
> to join them.

**One turn, four places.** Run a single turn with `google_adk` at DEBUG, a
`LoggingPlugin` attached, and the Cloud Logging exporter installed (the two calls
from 5.5). The `What's the weather in London?` turn shows up as:

| # | Place | What it looks like | From |
|---|---|---|---|
| 1 | `google_adk` **DEBUG** lines | `{"parts":[{"text":"What's the weather in London?"}],"role":"user"}` and the full request/response JSON | Part 1 (log level) |
| 2 | **`LoggingPlugin`** output | `[logging_plugin] 🏃 INVOCATION STARTING`, `Tool Name: get_weather`, `Arguments: {'city': 'London'}` | Part 3 (plugins) |
| 3 | OTel **span attribute** `gcp.vertex.agent.llm_request` | the prompt, on the `call_llm` span — **if** the span content knob is on | Part 5 (5.2, 5.6) |
| 4 | OTel **`gen_ai.*` events** | `gen_ai.client.inference.operation.details` (or the stable `gen_ai.user.message` / `gen_ai.choice`) in Cloud Logging | Part 5 (5.2-5.5) |

**Which are the same, which are independent (the part that trips people up):**

| Pair | Relationship | Why |
|---|---|---|
| Python `logging` (places 1-2) ↔ OTel (places 3-4) | **Independent** | ADK never bridges `logging` records into OTel; the DEBUG format carries no trace or span id (`cli/utils/logs.py`, no `LoggingHandler` in ADK). |
| `LoggingPlugin` ↔ OTel | **Independent** | `LoggingPlugin` `print()`s and imports no OpenTelemetry. It runs *inside* the spans, so it *could* read the current span, but the built-in does not. |
| OTel `gen_ai.*` events ↔ OTel spans | **Correlated automatically** | The OTel API stamps `trace_id`/`span_id` from the current span onto every log record, and the Cloud Logging exporter writes them as `logging.googleapis.com/trace` and `spanId`. |
| Part 4's `X-Cloud-Trace-Context` trace ↔ OTel span trace | **Different trace ids** | ADK never extracts Cloud Run's header into OTel context (`cli/fast_api.py:531-547` handles only the Agent Engine header), so the Part 4 JSON logs and the OTel spans do **not** join in one trace. |

So with everything on, one prompt is **duplicated** across up to four places, and
only two of them (spans and `gen_ai.*` events) join on their own.

**The hand-join key.** To line the independent streams up by turn, use the
invocation id. It appears in all of these under different names:

- `LoggingPlugin` prints `Invocation ID: e-59e08ed6-…` (place 2).
- Spans carry `gcp.vertex.agent.invocation_id` (`telemetry/tracing.py:622,744`) —
  the same value (place 3).
- The `gen_ai.*` events carry `gen_ai.conversation.id` = the session id
  (`telemetry/tracing.py`), which groups a session rather than one turn.

**In production, turn most of it off.** DEBUG lines and `LoggingPlugin` are
development aids — leave `google_adk` at INFO and drop the plugin in production
(Parts 1, 3). Keep OTel export on (it is the structured, queryable one), with
content off (`NO_CONTENT` and `ADK_CAPTURE_MESSAGE_CONTENT_IN_SPANS=false`) unless
you have a reviewed reason to log prompts (5.6). That leaves one place, not four.
