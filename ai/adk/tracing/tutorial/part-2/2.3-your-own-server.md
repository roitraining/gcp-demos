# 2.3 · Your own server

*Part 2 · Collect*

> [!NOTE]
> **Why you are here.** `adk web` and Cloud Run set up export for you. A
> hand-written server does not — you make the calls yourself. This page does
> that, then walks the ladder from "the agent answered" to "I can see the trace."

The example [examples/02_trace_server.py](../../examples/02_trace_server.py) is a
minimal FastAPI server that makes the two calls `adk web` makes:

```python
hooks = get_gcp_exporters(enable_cloud_tracing=True, enable_cloud_logging=True)
maybe_set_otel_providers([hooks], otel_resource=get_gcp_resource(project))
```

It exposes one `/chat` endpoint that returns the invocation's `trace_id`, so you
can read your own request back.

**Step 1 — Run it and ask.**

**Command:**

```bash
source env.sh
.venv/bin/python examples/02_trace_server.py
```

```bash
HOST=http://localhost:8080 ENDPOINT=chat ./load/turns.sh baseline 1
```

**Expected output:** one line with the trace id the server returned:

```console
baseline        turn   1  4.25s  trace=148e4d99fb043271b757e39c25b3c07d
```

**Step 2 — Read it back.**

```bash
./trace/get_trace.sh 148e4d99fb043271b757e39c25b3c07d
```

```console
trace 148e4d99fb043271b757e39c25b3c07d  (7 spans)
invocation                               4.249s
  invoke_agent weather_agent               4.240s
    call_llm                                 2.528s
      generate_content gemini-3.7-flash        2.523s
      execute_tool get_weather                 0.002s
    call_llm                                 1.682s
      generate_content gemini-3.7-flash        1.681s
```

> [!IMPORTANT]
> **What it means.** Your server exports the same tree `adk web` does, because it
> made the same two calls. Unlike the CLI, `.env` works here — `bootstrap()`
> loads it before the exporters are built, so the server reads its project from
> `.env` the way any script does.

## Deep dives

### Instrumented, recorded, exported, visible

"The agent answered" and "I can see the trace" are four steps apart, and each has
its own failure. When a trace is missing, this ladder tells you which rung broke.

| Rung | What it means | How it fails | The check |
|---|---|---|---|
| **Instrumented** | ADK opened the spans | never (2.8.0 always opens them) | the agent ran |
| **Recorded** | a real provider kept them | no span processor installed | the returned trace id is all zeros |
| **Exported** | the batch left and was accepted | endpoint down, or resource rejected | the exporter logs a failure; the read-back finds nothing |
| **Visible** | the viewer's project, service, and time range include it | wrong filter or window | the trace is there but the flyout is empty |

**Recorded.** Comment out the span processor and `maybe_set_otel_providers`
installs no provider at all (`setup.py:87`). Then `trace.get_current_span()` is a
non-recording no-op span whose trace id is `00000000000000000000000000000000`.
An all-zeros id in the `/chat` response is the tell: nothing was recorded.

**Exported, two ways it breaks.** Point the exporter at a closed port
(`export-outage`):

```bash
export TUTORIAL_TRACE_ENDPOINT=http://127.0.0.1:4318/v1/traces
.venv/bin/python examples/02_trace_server.py
```

The turn still answers and still returns a trace id, but the server logs
`Connection refused ... while exporting span batch`, and that trace id reads back
as nothing. The agent is healthy; the telemetry is not.

The second way is subtler: leave out the resource. `get_gcp_exporters` builds
exporters only; the resource is a separate argument. Drop
`otel_resource=get_gcp_resource(project)` and the provider falls back to a
resource with no `gcp.project_id` (`setup.py:71`). The Telemetry API then rejects
every batch with `400 Bad Request`, and the trace — recorded, with a real id —
is `404 NOT_FOUND` in Cloud Trace. That is why `02` passes the resource
explicitly.

**Visible.** If the ids match and the tree still will not open, the trace is
exported but filtered out: check the project, the **OpenTelemetry service**
filter (`OTEL_SERVICE_NAME`), and the time range, per the Cloud Trace
troubleshooting page. Restore the endpoint, restart, and read one clean turn back
to confirm the pipeline is whole again.
