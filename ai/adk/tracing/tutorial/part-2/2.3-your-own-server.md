# 2.3 · Your own server

*Part 2 · Collect*

> [!NOTE]
> **Why you are here.** `adk web` and Cloud Run set up export for you. A
> hand-written server does not; you make the calls yourself. This page does
> that, then names the steps between "the agent answered" and "I can see the trace."

The example [examples/02_trace_server.py](../../examples/02_trace_server.py) is a
minimal FastAPI server that makes the two calls `adk web` makes:

```python
hooks = get_gcp_exporters(enable_cloud_tracing=True, enable_cloud_logging=True)
maybe_set_otel_providers([hooks], otel_resource=get_gcp_resource(project))
```

It exposes one `/chat` endpoint that returns the invocation's `trace_id`, so you
can read your own request back.

**Step 1 — Run it and ask.** Start the server in one terminal:

**Command:**

```bash
source env.sh
.venv/bin/python examples/02_trace_server.py
```

The server runs in the foreground. In a second terminal, send one turn:

**Command:**

```bash
source env.sh
export HOST=http://localhost:8080
export ENDPOINT=chat
./load/turns.sh baseline 1
```

**Expected output:** one line with the trace id the server returned:

```console
baseline        turn   1  4.25s  trace=148e4d99fb043271b757e39c25b3c07d
```

**Step 2 — Read it back.** Replace the trace id with the one your turn printed:

**Command:**

```bash
./trace/get_trace.sh 148e4d99fb043271b757e39c25b3c07d
```

**Expected output:**

```console
trace 148e4d99fb043271b757e39c25b3c07d  (7 spans)
invocation                               4.249s
  invoke_agent weather_agent               4.240s
    call_llm                                 2.528s
      generate_content gemini-3.7-flash        2.523s
      execute_tool get_weather                 0.002s
    call_llm                                 1.682s
      generate_content gemini-3.7-flash        1.681s
```

> [!IMPORTANT]
> **What it means.** Your server exports the same tree `adk web` does, because it
> made the same two calls. Unlike the CLI, `.env` works here: `bootstrap()`
> loads it before the exporters are built, so the server reads its project from
> `.env` the way any script does.

## Deep dives

### Which step failed when a trace is missing?

"The agent answered" and "I can see the trace" are four steps apart, and each has
its own failure: instrumented, recorded, exported, and visible. When a trace is
missing, this table tells you which step broke.

| Step | What it means | How it fails | The check |
|---|---|---|---|
| **Instrumented** | ADK opened the spans | never (2.8.0 always opens them) | the agent ran |
| **Recorded** | a real provider kept them | no provider installed | the current span's trace id is all zeros (the `02` server returns a 500 first) |
| **Exported** | the batch left and was accepted | endpoint down, or resource rejected | the exporter logs a failure; the read-back finds nothing |
| **Visible** | the viewer's project, service, and time range include it | wrong filter or window | the trace is there but the trace details panel is empty |

**Recorded.** Comment out line 99 of
[examples/02_trace_server.py](../../examples/02_trace_server.py), the
`maybe_set_otel_providers` call inside `install_cloud_tracing`, and restart. No
provider is installed (`google/adk/telemetry/setup.py:87`). With no provider,
`trace.get_current_span()` returns a placeholder span whose id is all zeros. The
`02` server fails earlier, with a 500 (`'ProxyTracerProvider' object has no
attribute 'force_flush'`), because `/chat` flushes the provider. Restore the
line.

**Exported, and an extra exporter that fails.** `TUTORIAL_TRACE_ENDPOINT` adds a
second OTLP exporter beside the Google one (`export-outage`). Stop the server
(Ctrl+C), point that exporter at a closed port, and restart:

**Command:**

```bash
export TUTORIAL_TRACE_ENDPOINT=http://127.0.0.1:4318/v1/traces
.venv/bin/python examples/02_trace_server.py
```

Send a turn from the second terminal. It answers and returns a trace id, but
takes 10 to 20 s instead of 4, and the server logs `Connection refused ...
encountered while exporting span batch, retrying` until it gives up. The trace
still arrives in Cloud Trace: only the extra export failed, and the Google one
is untouched. The agent is healthy; one telemetry route is not. Stop the server,
remove the extra exporter, and restart:

**Command:**

```bash
unset TUTORIAL_TRACE_ENDPOINT
.venv/bin/python examples/02_trace_server.py
```

To see a trace that never lands, leave out the resource. `get_gcp_exporters`
builds exporters only; the resource is a separate argument. Drop
`otel_resource=get_gcp_resource(project)` from line 99 and the provider falls back
to a resource with no `gcp.project_id` (`google/adk/telemetry/setup.py:71`). The
Telemetry API then rejects every batch with `400 Bad Request`, and the trace
(recorded, with a real id) is `404 NOT_FOUND` in Cloud Trace. That is why `02`
passes the resource explicitly. Restore the line and restart.

**Visible.** If the ids match and the tree still will not open, the trace is
exported but filtered out: check the project, the **OpenTelemetry service**
filter (`OTEL_SERVICE_NAME`), and the time range, per the Cloud Trace
troubleshooting page. Read one clean turn back to confirm the pipeline is whole
again.
