# 2.4 · Agent Runtime

*Part 2 · Collect*

> [!NOTE]
> **Why you are here.** The same agent on Agent Runtime (Vertex AI Agent Engine)
> does not produce the same tree. This page deploys it there and shows the one
> structural difference: a different root span.

The `baseline` scenario, deployed to Agent Engine. Tracing is on when you deploy
with `--otel_to_cloud`.

**Step 1 — Deploy with telemetry.**

**Command:**

```bash
source env.sh
.venv/bin/adk deploy agent_engine \
  --project "$PROJECT_ID" \
  --region "$REGION" \
  --otel_to_cloud \
  demo_agent
```

`--otel_to_cloud` sets `GOOGLE_CLOUD_AGENT_ENGINE_ENABLE_TELEMETRY=true` for you.
The deploy reads env from `demo_agent/.env` (the agent folder), not the root
`.env`. The build takes several minutes.

**Step 2 — Ask, then read the tree back.** Send a London turn to the deployed
engine, then list the recent traces on the project and read the newest:

**Command:**

```bash
./trace/list_traces.sh '' 30
```

**Expected output:** a trace whose root is not `invocation`:

```console
invoke_workflow weather_agent
  invoke_agent weather_agent
    call_llm
      generate_content gemini-3.7-flash
```

> [!IMPORTANT]
> **What it means.** The root is `invoke_workflow weather_agent`, not
> `invocation`. Agent Engine sets `GOOGLE_CLOUD_AGENT_ENGINE_ID`, which selects
> telemetry schema v2 (`_schema_version.py:72-91`), and v2 wraps the run in an
> `invoke_workflow` root carrying `gen_ai.workflow.name`. So the same agent files
> under a different root span here than on Cloud Run. Every span is tagged
> `service.name=<engine id>`, and the Agent Platform console's **Traces** tab is
> just Cloud Trace filtered by that id.

> [!NOTE]
> On 2.8.0, v2 changes the root but keeps `call_llm` — the schema-v2 removal of
> `call_llm` has not shipped, so the tree below `invoke_agent` looks as it does
> everywhere else.

**Step 3 — Tear down.** Delete the engine so it stops billing:

**Command:**

```bash
.venv/bin/python -c "import vertexai; vertexai.init(project='$PROJECT_ID', location='$REGION'); [e.delete(force=True) for e in vertexai.agent_engines.list()]"
```

## Deep dives

### Two deploy gotchas worth knowing

Two things surprised us deploying to Agent Engine, both harmless to the trace but
worth flagging. First, `adk deploy agent_engine` rewrites the pushed
`requirements.txt`, turning `google-adk[otel-gcp]` into `google-adk[a2a]`, so the
GenAI SDK instrumentor is not in the image and the engine logs `Unable to import
GoogleGenAiSdkInstrumentor`. Native ADK span tracing still works — the tree above
came out complete — but the extra instrumentor spans do not. Second, the trace
appears even when the model call fails: a model unavailable in your region 404s
every `call_llm`, and ADK still emits the full span tree, so a trace is not proof
the turn succeeded. That distinction between trace evidence and task outcome is
what [Part 4](../part-4/index.md) is about.
