# 2.4 · Agent Runtime

*Part 2 · Collect*

> [!NOTE]
> **Why you are here.** The same agent on Agent Runtime (Vertex AI Agent Engine
> in the console) does not produce the same tree. This page deploys it there and
> shows the one structural difference: a different root span.

The `baseline` scenario, deployed to Agent Runtime. Tracing is on when you
deploy with `--otel_to_cloud`.

**Step 1 — Deploy with telemetry.** The deploy reads env from `demo_agent/.env`
(the agent folder), not the root `.env`, and passes it to the engine. Create
that file with the model location, then deploy. `tee` saves the deploy's output
to `out/deploy.txt` so Step 2 can read the engine id from it:

**Command:**

```bash
source .venv/bin/activate
source env.sh
echo "GOOGLE_CLOUD_LOCATION=global" > demo_agent/.env
adk deploy agent_engine \
  --project "$PROJECT_ID" \
  --region "$REGION" \
  --otel_to_cloud \
  demo_agent \
  | tee out/deploy.txt
```

**Expected output** (the line that names the engine; the build takes several
minutes):

```console
Deployed to Agent Platform: projects/376236993953/locations/us-central1/reasoningEngines/4456927008038846464
```

> [!IMPORTANT]
> **What it means.** Without `GOOGLE_CLOUD_LOCATION=global` the engine calls the
> model in `us-central1`, where it is not served, and every turn fails with a
> 404. The deploy also prints `Ignoring GOOGLE_CLOUD_LOCATION in .env as
> --region was explicitly passed`; that line is about where the engine runs, and
> the variable still reaches the engine. `--otel_to_cloud` sets
> `GOOGLE_CLOUD_AGENT_ENGINE_ENABLE_TELEMETRY=true` for you.

> [!NOTE]
> `--otel_to_cloud` on Agent Runtime also sets
> `ADK_CAPTURE_MESSAGE_CONTENT_IN_SPANS=false`
> (`google/adk/cli/cli_deploy.py:1281-1282`), the opposite of
> [1.3](../part-1/1.3-attributes-and-content.md)'s default, so the engine's
> spans carry `gcp.vertex.agent.llm_request` as `{}`. Set the variable in
> `demo_agent/.env` to keep content.

**Step 2 — Ask.** Read the engine id, the number at the end of the
`reasoningEngines/` resource name, from the saved deploy output, then send a
London turn:

**Command:**

```bash
export ENGINE_ID=$(awk -F/ '/Deployed to Agent Platform/ {print $NF}' out/deploy.txt)
python - <<'PY'
import asyncio, os, vertexai
from vertexai import agent_engines

vertexai.init(project=os.environ["PROJECT_ID"], location=os.environ["REGION"])
engine = agent_engines.get(
    f"projects/{os.environ['PROJECT_ID']}/locations/{os.environ['REGION']}"
    f"/reasoningEngines/{os.environ['ENGINE_ID']}"
)

async def main():
    async for event in engine.async_stream_query(
        user_id="u1", message="What's the weather in London?"
    ):
        for part in event.get("content", {}).get("parts", []):
            if "text" in part:
                print("AGENT:", part["text"])

asyncio.run(main())
PY
```

**Expected output:**

```console
AGENT: The current weather in London is 15°C with drizzle.
```

**Step 3 — Read the tree back in the console.** Every span from the engine
carries `service.name=<engine id>`, so filter Trace Explorer by that id
(`echo "$ENGINE_ID"` prints it). A new trace takes a minute or two to appear.
In the Google Cloud console:

- Open **Trace Explorer**.
- In the **Span filters** pane, under **OpenTelemetry service**, check your engine id.
- Under **Span name**, check `invoke_workflow weather_agent` (click **Show more** if it is not listed).
- Select the most recent row to open the trace details panel.
- Expand every span in the waterfall.

**Expected output:** a trace whose root is not `invocation` (captured from the
Trace API for this run):

```console
trace c786594017662aff55302df141130b23  (7 spans)
invoke_workflow weather_agent            4.224s
  invoke_agent weather_agent               4.009s
    call_llm                                 2.193s
      generate_content gemini-3.7-flash        1.859s
      execute_tool get_weather                 0.003s
    call_llm                                 1.708s
      generate_content gemini-3.7-flash        1.509s
```

> [!IMPORTANT]
> **What it means.** The root is `invoke_workflow weather_agent`, not
> `invocation`. Agent Runtime sets `GOOGLE_CLOUD_AGENT_ENGINE_ID`, which selects
> telemetry schema v2 (`google/adk/telemetry/_schema_version.py:72-91`), and v2
> wraps the run in an `invoke_workflow` root carrying `gen_ai.workflow.name`.
> So the same agent files under a different root span here than on Cloud Run.
> Every span is tagged `service.name=<engine id>`, and the engine's **Traces**
> tab in the console is Cloud Trace filtered by that id.

> [!NOTE]
> On 2.8.0, v2 changes the root but keeps `call_llm`: the schema-v2 removal of
> `call_llm` has not shipped, so the tree below `invoke_agent` matches
> [2.2](2.2-cloud-run.md)'s.

**Step 4 — Tear down.** Delete the engine this page created, so it stops
billing. Deleting it by its full name leaves any other engine in the project
alone:

**Command:**

```bash
python -c "import os, vertexai; from vertexai import agent_engines; vertexai.init(project=os.environ['PROJECT_ID'], location=os.environ['REGION']); agent_engines.get(f\"projects/{os.environ['PROJECT_ID']}/locations/{os.environ['REGION']}/reasoningEngines/{os.environ['ENGINE_ID']}\").delete(force=True)"
rm demo_agent/.env out/deploy.txt
unset ENGINE_ID
```

**Expected output** (last line):

```console
Agent Engine deleted. Resource name: projects/jwd-gcp-demos/locations/us-central1/reasoningEngines/4456927008038846464
```

[2.5 · Sampling](2.5-sampling.md) goes back to the local server and keeps only
some of the traces.

## Deep dives

### What else differs when you deploy to Agent Runtime?

Two things, both harmless to the trace. First, `demo_agent/` has no
`requirements.txt`, so the deploy creates one with only the Agent Platform SDK
and `google-adk[a2a]`; the root `requirements.txt` is never sent. The GenAI SDK
instrumentor is not in the image, and the engine logs `Unable to import
GoogleGenAiSdkInstrumentor`. ADK's own spans still work (the tree above came out
complete), but the extra instrumentor spans do not. Second, a trace appears even
when the model call fails: with the model location wrong, every `call_llm` gets a
404, and ADK still emits a four-span tree that ends at the failed
`generate_content`. A trace is not proof the turn succeeded. That distinction
between trace evidence and task outcome is what [Part 4](../part-4/index.md) is
about.
