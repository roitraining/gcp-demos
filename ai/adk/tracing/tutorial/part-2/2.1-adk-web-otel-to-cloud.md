# 2.1 · adk web --otel_to_cloud

*Part 2 · Collect*

> [!NOTE]
> **Why you are here.** Part 1's tree lived in one process. This page turns on
> the one flag that ships it to Cloud Trace, runs a slow turn, and reads the same
> tree back from the cloud.

The `slow-tool` scenario is a forecast turn, so the tool has real duration to see
in the waterfall. Ship it with `--otel_to_cloud`.

**Step 1 — Start with export on.**

**Command:**

```bash
source env.sh
adk web --otel_to_cloud .
```

`env.sh` set `OTEL_SERVICE_NAME=adk-tracing`, which becomes the trace's service
label in Cloud Trace. `--otel_to_cloud` installs a `BatchSpanProcessor` that
ships each batch over OTLP to `telemetry.googleapis.com`. You added no exporter
code; the flag did it (`google/adk/cli/api_server.py:680-719`).

**Step 2 — Ask the slow question.** In the dev UI, ask **What's the three-day
forecast for London?** The turn answers as before. This time the tree also left
the process.

**Step 3 — Read it back in the console.** A new trace takes a minute or two to
appear. In the Google Cloud console:

- Open **Trace Explorer**.
- Set **OpenTelemetry service** to `adk-tracing`.
- Add a **Span name** filter for `invoke_agent weather_agent`.
- Select the most recent row to open the trace details panel.
- Expand every span in the waterfall.

**Expected output:** the same tree from Part 1, now served by Cloud Trace. The
waterfall shows these rows (captured from the Trace API for this run):

```console
trace 8e95a681a60feb53048d0e6c106858a0  (7 spans)
invocation                               4.220s
  invoke_agent weather_agent               4.209s
    call_llm                                 2.610s
      generate_content gemini-3.7-flash        2.053s
      execute_tool get_forecast                0.524s
    call_llm                                 1.560s
      generate_content gemini-3.7-flash        1.554s
```

> [!IMPORTANT]
> **What it means.** Seven spans, the same parent chain, the tool at 0.524 s:
> Cloud Trace now holds the same seven spans and parent chain you read locally in
> Part 1; only the ids and durations differ.

> [!NOTE]
> The `adk web` terminal logs repeated `Failed to export metrics batch ... 400`
> lines. They concern metrics, not traces, and are harmless here.

[2.2 · Cloud Run](2.2-cloud-run.md) does the same thing with the server running
on Cloud Run instead of your laptop.

## Deep dives

### `--trace_to_cloud` is not `--otel_to_cloud`

There are two flags, and the older one is easy to pick by mistake.
`--trace_to_cloud` (deprecated) installs a `CloudTraceSpanExporter` that writes
to the Cloud Trace API v2 and reads its project from the agent's `.env`
(`google/adk/cli/fast_api.py:314-331`). `--otel_to_cloud` installs the OTLP
exporter to `telemetry.googleapis.com` and reads the project from the
environment. If you pass both, `--otel_to_cloud` silently wins
(`google/adk/cli/fast_api.py:314`, guarded `if trace_to_cloud and not
otel_to_cloud`). The codelab you may have seen uses `--trace_to_cloud`; use
`--otel_to_cloud`, which is the path the rest of this tutorial takes and the one
that also ships logs for [Part 3](../part-3/index.md).
