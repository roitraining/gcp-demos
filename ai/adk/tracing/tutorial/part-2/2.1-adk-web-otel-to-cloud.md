# 2.1 · adk web --otel_to_cloud

*Part 2 · Collect*

> [!NOTE]
> **Why you are here.** Part 1's tree lived in one process. This page turns on
> the one flag that ships it to Cloud Trace, runs a slow turn, and reads the same
> tree back from the cloud.

The `slow-tool` scenario is a forecast turn, so the tool has real duration to see
in the waterfall. Ship it with `--otel_to_cloud`.

**Step 1 — Start with export on.**

**Command:**

```bash
source env.sh
.venv/bin/adk web --otel_to_cloud .
```

`env.sh` set `OTEL_SERVICE_NAME=adk-tracing`, which becomes the trace's service
label in Cloud Trace. `--otel_to_cloud` installs a `BatchSpanProcessor` that
ships each batch over OTLP to `telemetry.googleapis.com`. You added no exporter
code; the flag did it (`api_server.py:679-719`).

**Step 2 — Ask the slow question.** In the dev UI, ask **What's the three-day
forecast for London?** The turn answers as before. This time the tree also left
the process.

**Step 3 — Read it back.** Take the trace id from the dev UI's **Trace** tab (or
the debug endpoint) and read the tree from Cloud Trace with the capture script:

**Command:**

```bash
./trace/get_trace.sh 8e95a681a60feb53048d0e6c106858a0
```

**Expected output:** the same tree from Part 1, now served by Cloud Trace:

```console
trace 8e95a681a60feb53048d0e6c106858a0  (7 spans)
invocation                               4.220s
  invoke_agent weather_agent               4.209s
    call_llm                                 2.610s
      generate_content gemini-3.7-flash        2.053s
      execute_tool get_forecast                0.524s
    call_llm                                 1.560s
      generate_content gemini-3.7-flash        1.554s
```

> [!IMPORTANT]
> **What it means.** Seven spans, the same parent chain, the tool at 0.524 s —
> the tree you read locally in Part 1 is byte-for-byte the tree Cloud Trace now
> holds. In the **Trace Explorer**, filter **Span name** `invoke_agent
> weather_agent`, open the **Details** flyout, and the waterfall is the same
> picture. The script is the capture; the console is the same data.

> [!NOTE]
> The script retries for ~90 s the first time: a freshly exported trace takes a
> minute or two to index before the v1 API can read it. That is normal; the
> retry loop waits it out.

[2.2](2.2-cloud-run.md) does the same thing without you running the server at
all — a deployed Cloud Run service.

## Deep dives

### `--trace_to_cloud` is not `--otel_to_cloud`

There are two flags, and the older one is a trap. `--trace_to_cloud`
(deprecated) installs a `CloudTraceSpanExporter` that writes to the Cloud Trace
API v2 and reads its project from the agent's `.env` (`fast_api.py:312-331`).
`--otel_to_cloud` installs the OTLP exporter to `telemetry.googleapis.com` and
reads the project from the environment. If you pass both, `--otel_to_cloud`
silently wins (`fast_api.py:312`, guarded `if trace_to_cloud and not
otel_to_cloud`). The codelab you may have seen uses `--trace_to_cloud`; use
`--otel_to_cloud`, which is the path the rest of this tutorial takes and the one
that also ships logs for [Part 3](../part-3/index.md).
