# 2.6 · Other backends

*Part 2 · Collect*

> [!NOTE]
> **Why you are here.** The tree is plain OpenTelemetry, so Google is not the
> only place it can go. This reference page shows the one variable that sends it
> to any OTLP collector, and lists the agent-observability vendors that read it.

ADK reads the standard OTLP environment variables. Set an endpoint and the SDK
adds a generic `OTLPSpanExporter` alongside whatever else is configured
(`setup.py:124-153`):

```bash
export OTEL_EXPORTER_OTLP_TRACES_ENDPOINT=https://your-collector:4318/v1/traces
```

| Fact | Detail |
|---|---|
| Protocol | HTTP/protobuf only (`otlp-proto-http`). The gRPC exporter is not wired in. |
| Additive | This route is added to the GCP route, not instead of it. Set `--otel_to_cloud` **and** the OTLP endpoint and the tree is exported to both — dual export. |
| Headers | Auth and other headers go through `OTEL_EXPORTER_OTLP_HEADERS`, the standard variable. |
| Content | The `gcp.vertex.agent.*` content attributes travel too; the [1.3](../part-1/1.3-attributes-and-content.md) knob still governs them. |

Because the spans follow the OpenTelemetry GenAI convention, the
agent-observability vendors on the adk.dev integrations list read them without a
translation layer:

| Vendor | What it is |
|---|---|
| Phoenix (Arize) | open-source LLM tracing and evaluation |
| AgentOps | agent-run session replay and cost tracking |
| MLflow | experiment tracking with a tracing view |
| Honeycomb | general OTLP backend with strong trace querying |

Point the endpoint at the vendor's OTLP collector and the same tree you sent to
Cloud Trace arrives there. This tutorial stays on the Google path; the rest of it
assumes `--otel_to_cloud`.

[Part 3](../part-3/index.md) leaves the collect problem behind and takes up
correlation: getting every log line of a request to show up inside the right
span.
