# 2.2 · Cloud Run

*Part 2 · Collect*

> [!NOTE]
> **Why you are here.** On your laptop you started the server. This page deploys
> the agent to Cloud Run and asks whether a managed service traces without any
> extra work — and records one fact Part 3 needs.

The `baseline` scenario, this time against a deployed service. Deploy the agent
with tracing on.

**Step 1 — Deploy.**

**Command:**

```bash
source env.sh
.venv/bin/adk deploy cloud_run \
  --project "$PROJECT_ID" \
  --region "$REGION" \
  --service_name adk-trace \
  --otel_to_cloud \
  .
```

The build packages the agent's `requirements.txt`, so the OTel exporters ride
into the image. Set `OTEL_SERVICE_NAME` on the service so its traces file under a
name; the deploy prints the service URL when the revision is ready.

> [!WARNING]
> If the revision crashes on boot with a missing-module error, the exporter
> dependencies did not make it into the image. Confirm `requirements.txt` pins
> `google-adk[otel-gcp]` and the OTLP exporter, and is in the directory you
> deployed.

**Step 2 — Ask, then read back.** Send one London turn to the service URL, take
its trace id, and read the tree:

**Command:**

```bash
./trace/get_trace.sh 0000cb104b9c2e8d4039729a40d46eb0
```

**Expected output:**

```console
trace 0000cb104b9c2e8d4039729a40d46eb0  (7 spans)
invocation
  invoke_agent weather_agent
    call_llm
      generate_content gemini-3.7-flash
      execute_tool get_weather
    call_llm
      generate_content gemini-3.7-flash
```

> [!IMPORTANT]
> **What it means.** The same tree, from a service you deployed and never
> instrumented. Cloud Run's resource detector filled in `cloud.platform`,
> `cloud.region`, `gcp.project_id`, and the `faas.*` labels with no config, so
> the trace files under `OTEL_SERVICE_NAME` in the **Service/workload** column
> and carries where it ran. Deployed tracing is the flag plus the exporter in the
> image; nothing more.

**Step 3 — Tear down.**

**Command:**

```bash
gcloud run services delete adk-trace --region "$REGION" --quiet
```

## Deep dives

### Two trace ids for one request

Look at the same request two ways and you get two different trace ids:

| Source | Trace id |
|---|---|
| the ADK spans (the `/chat` body, Cloud Trace) | `0000cb104b9c2e8d4039729a40d46eb0` |
| the Cloud Run request log (`run.googleapis.com/requests`) | `18cb1a68232775b83979db6b5bf7fcca` |

They differ because ADK does not read the inbound trace header. Cloud Run stamps
its ingress request with its own trace id (in both `X-Cloud-Trace-Context` and
`traceparent`), but ADK ignores it and opens a fresh trace inside the process. So
one HTTP request is described by two traces that never meet: the request log
under Cloud Run's id, the spans under ADK's. That split is exactly the problem
[Part 3](../part-3/index.md) closes — page 3.4 makes ADK's root a child of the
request so the two become one.
