# 2.2 · Cloud Run

*Part 2 · Collect*

> [!NOTE]
> **Why you are here.** On your laptop you started the server. This page deploys
> a server to Cloud Run, checks that the same tree lands, and records one fact
> Part 3 needs.

The `baseline` scenario, this time against a deployed service. The service is
[examples/02_trace_server.py](../../examples/02_trace_server.py), a minimal
FastAPI server that installs the Cloud Trace exporter itself and returns each
turn's trace id from `/chat`. [2.3 · Your own server](2.3-your-own-server.md)
walks through its code. The container recipe is
[deploy/Dockerfile.trace_server](../../deploy/Dockerfile.trace_server).

**Step 1 — Deploy.** `gcloud run deploy --source` builds from a file named
`Dockerfile`, so copy the recipe to the folder root, deploy, then delete the
copy:

**Command:**

```bash
source env.sh
cp deploy/Dockerfile.trace_server Dockerfile
gcloud run deploy adk-trace \
  --source . \
  --project "$PROJECT_ID" \
  --region "$REGION" \
  --no-allow-unauthenticated \
  --set-env-vars "GOOGLE_GENAI_USE_VERTEXAI=TRUE,GOOGLE_CLOUD_PROJECT=$PROJECT_ID,GOOGLE_CLOUD_LOCATION=global,OTEL_SERVICE_NAME=$OTEL_SERVICE_NAME"
rm Dockerfile
```

**Expected output** (the last lines; the build takes a few minutes):

```console
Service [adk-trace] revision [adk-trace-00001-7b9] has been deployed and is serving 100 percent of traffic.
Service URL: https://adk-trace-376236993953.us-central1.run.app
```

> [!IMPORTANT]
> **What it means.** The image holds no `.env`, so `--set-env-vars` gives the
> service its model settings. `GOOGLE_CLOUD_LOCATION=global` matters: the model
> is not served from `us-central1`, and a turn there fails with a 404.
> `OTEL_SERVICE_NAME` names the service in Trace Explorer. The image installs
> `requirements.txt`, which pins the exporters, so the revision boots.

**Step 2 — Ask, then read back.** The service accepts only callers with an
identity token (`--no-allow-unauthenticated`), so the `curl` sends yours:

**Command:**

```bash
export SERVICE_URL=$(gcloud run services describe adk-trace \
  --project "$PROJECT_ID" \
  --region "$REGION" \
  --format='value(status.url)')
curl -s -X POST "$SERVICE_URL/chat" \
  -H "Authorization: Bearer $(gcloud auth print-identity-token)" \
  -H 'content-type: application/json' \
  -d '{"text":"What'\''s the weather in London?"}'
```

**Expected output:**

```console
{"response":"The weather in London is currently 15°C and drizzling.","trace_id":"dfe665b9bb7bfd8842f8d7c0b2a59ca4"}
```

Replace the trace id with the one your turn returned:

**Command:**

```bash
./trace/get_trace.sh dfe665b9bb7bfd8842f8d7c0b2a59ca4
```

**Expected output:**

```console
trace dfe665b9bb7bfd8842f8d7c0b2a59ca4  (7 spans)
invocation                               5.558s
  invoke_agent weather_agent               5.324s
    call_llm                                 2.252s
      generate_content gemini-3.7-flash        2.249s
      execute_tool get_weather                 0.002s
    call_llm                                 2.982s
      generate_content gemini-3.7-flash        2.980s
```

> [!IMPORTANT]
> **What it means.** The same seven-span tree you get on your laptop, with no
> code change for Cloud Run. The resource detector filled in `cloud.platform`,
> `cloud.region`, `gcp.project_id`, and the `faas.*` labels with no config, so
> the trace files under `OTEL_SERVICE_NAME` in the **Service/workload** column
> and records where it ran. Deployed tracing is the exporter in the image;
> Cloud Run adds nothing you configure.

To see the second trace id this request produced, run the deep dive's command
now, before you tear down. See [Two trace ids for one
request](#two-trace-ids-for-one-request).

**Step 3 — Tear down.** Delete the service, its image, and the uploaded
source:

**Command:**

```bash
gcloud run services delete adk-trace \
  --project "$PROJECT_ID" \
  --region "$REGION" \
  --quiet
gcloud artifacts docker images delete "$REGION-docker.pkg.dev/$PROJECT_ID/cloud-run-source-deploy/adk-trace" \
  --delete-tags \
  --quiet
gcloud storage rm -r "gs://run-sources-$PROJECT_ID-$REGION/services/adk-trace/"
unset SERVICE_URL
```

[2.3 · Your own server](2.3-your-own-server.md) runs the same server on your
laptop and shows how it turns export on.

## Deep dives

### Two trace ids for one request

Cloud Run writes its own request log entry for every call, with a `trace`
field. Read it for the `/chat` call:

**Command:**

```bash
gcloud logging read 'resource.type="cloud_run_revision" AND resource.labels.service_name="adk-trace" AND httpRequest.requestUrl:"/chat"' \
  --project="$PROJECT_ID" \
  --limit=1 \
  --format='value(trace)'
```

**Expected output:**

```console
projects/jwd-gcp-demos/traces/977d9a9cebfd411d0e436abdbdb8d394
```

So the same request has two different trace ids:

| Source | Trace id |
|---|---|
| the ADK spans (the `/chat` body, Cloud Trace) | `dfe665b9bb7bfd8842f8d7c0b2a59ca4` |
| the Cloud Run request log (`run.googleapis.com/requests`) | `977d9a9cebfd411d0e436abdbdb8d394` |

They differ because the `02` server does not read the inbound trace header.
Cloud Run stamps its ingress request with its own trace id (in both
`X-Cloud-Trace-Context` and `traceparent`), but nothing in the process extracts
it, so ADK opens a fresh trace. One HTTP request is described by two traces
that never meet: the request log under Cloud Run's id, the spans under ADK's.
That split is the problem [Part 3](../part-3/index.md) closes:
[3.4 · One trace per request](../part-3/3.4-one-trace-per-request.md) makes
ADK's root a child of the request so the two become one.
