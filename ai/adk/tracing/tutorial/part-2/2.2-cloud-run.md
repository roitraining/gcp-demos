# 2.2 · Cloud Run

*Part 2 · Collect*

> [!NOTE]
> **Why you are here.** 2.1 exported from `adk web` on your laptop. This page
> deploys the same agent to Cloud Run with `adk deploy`, passes the same flag,
> and checks that the same tree lands.

The `baseline` scenario, this time against a deployed service. `adk deploy
cloud_run` generates a Dockerfile that runs ADK's API server, the same server
`adk web` runs minus the dev UI. You write no server code.

**Step 1 — Deploy.** The agent folder holds a
[requirements.txt](../../demo_agent/requirements.txt), which `adk deploy`
installs into the image. Everything after `--` goes to `gcloud run deploy`:

**Command:**

```bash
source env.sh
adk deploy cloud_run \
  --project "$PROJECT_ID" \
  --region "$REGION" \
  --service_name adk-trace \
  --otel_to_cloud \
  demo_agent \
  -- \
  --no-allow-unauthenticated \
  --set-env-vars "GOOGLE_CLOUD_LOCATION=global,OTEL_SERVICE_NAME=$OTEL_SERVICE_NAME"
```

**Expected output** (the last lines; the build takes a few minutes):

```console
Service [adk-trace] revision [adk-trace-00001-l5v] has been deployed and is serving 100 percent of traffic.
Service URL: https://adk-trace-754549205293.us-central1.run.app
```

> [!IMPORTANT]
> **What it means.** `--otel_to_cloud` is the flag from 2.1, now baked into
> the container's `adk api_server` command. The generated Dockerfile sets
> `GOOGLE_CLOUD_LOCATION` to your region, where the model is not served, so
> `--set-env-vars` overrides it with `global`. `OTEL_SERVICE_NAME` names the
> service in Trace Explorer. See [What the generated image
> lacks](#what-the-generated-image-lacks).

**Step 2 — Send a turn.** The service accepts only callers with an identity
token. ADK's API server needs a session before it takes a turn, so create one,
then send the London question to `/run`:

**Command:**

```bash
export SERVICE_URL=$(gcloud run services describe adk-trace \
  --project "$PROJECT_ID" \
  --region "$REGION" \
  --format='value(status.url)')
export TOKEN=$(gcloud auth print-identity-token)
curl -s -X POST "$SERVICE_URL/apps/demo_agent/users/u1/sessions/s1" \
  -H "Authorization: Bearer $TOKEN" \
  -H 'content-type: application/json' \
  -d '{}'
curl -s -X POST "$SERVICE_URL/run" \
  -H "Authorization: Bearer $TOKEN" \
  -H 'content-type: application/json' \
  -d '{"app_name":"demo_agent","user_id":"u1","session_id":"s1","new_message":{"role":"user","parts":[{"text":"What'\''s the weather in London?"}]}}' \
  | jq '.[-1].content.parts[0].text'
```

**Expected output:** the session, then the answer:

```console
{"id":"s1","appName":"demo_agent","userId":"u1","state":{},"events":[],"lastUpdateTime":1791059270.6122434}
"The current weather in London is 15°C and drizzling."
```

**Step 3 — Read it back in the console.** A new trace takes a minute or two to
appear. In the Google Cloud console:

- Open **Trace Explorer**.
- Set **OpenTelemetry service** to `adk-tracing`.
- Add a **Span name** filter for `invoke_agent weather_agent`.
- Select the most recent row to open the trace details panel.
- Expand every span in the waterfall.
- Select `invocation` and open **Attributes**.

**Expected output:** the waterfall shows these rows (captured from the Trace
API for this run):

```console
trace a512da51efd6f41b468ad1b65711646f  (7 spans)
invocation                               3.088s
  invoke_agent weather_agent               3.011s
    call_llm                                 1.661s
      generate_content gemini-3.7-flash        1.527s
      execute_tool get_weather                 0.003s
    call_llm                                 1.220s
      generate_content gemini-3.7-flash        1.218s
```

> [!IMPORTANT]
> **What it means.** The same seven-span tree you got from `adk web`, from the
> same flag. The **Attributes** list shows `cloud.platform` `gcp_cloud_run`,
> `cloud.region`, and the `faas.*` labels: the resource detector filled them in
> with no config, so the trace records where it ran.

Note the trace id at the top of the panel. The deep dive compares it with a
second id for the same request; open it now, before you tear down. See [Two
trace ids for one request](#two-trace-ids-for-one-request).

**Step 4 — Tear down.** Delete the service, its image, and the uploaded
source:

**Command:**

```bash
gcloud run services delete adk-trace \
  --project "$PROJECT_ID" \
  --region "$REGION" \
  --quiet
gcloud artifacts docker images delete "$REGION-docker.pkg.dev/$PROJECT_ID/cloud-run-source-deploy/adk-trace" \
  --delete-tags \
  --quiet
gcloud storage rm -r "gs://run-sources-$PROJECT_ID-$REGION/services/adk-trace/"
unset SERVICE_URL TOKEN
```

`adk deploy` wrote the server for you. [2.3 · Your own server](2.3-your-own-server.md)
writes it yourself and shows the calls that turn export on.

## Deep dives

### What the generated image lacks

The generated Dockerfile installs `google-adk[a2a]` only. That extra carries
none of the exporters `--otel_to_cloud` builds, so without the agent's
`requirements.txt` the container fails at boot. The Dockerfile also sets
`GOOGLE_GENAI_USE_ENTERPRISE=1` and `GOOGLE_CLOUD_PROJECT` from `--project`, so
the image needs no `.env`; only the location needs overriding
(`google/adk/cli/cli_deploy.py:190-216`).

### Two trace ids for one request

Cloud Run writes its own request log entry for every call, with a `trace`
field. Find it for the `/run` call:

- Open **Logs Explorer**.
- Paste this query and click **Run query**:

```
resource.type="cloud_run_revision"
resource.labels.service_name="adk-trace"
httpRequest.requestUrl:"/run"
```

- Expand the newest entry and read its `trace` field.

**Expected output** (captured with `gcloud logging read` for this run):

```console
projects/jwd-dev-2/traces/a9febcac58f1c18504346514663611d8
```

So the same request has two different trace ids:

| Source | Trace id |
|---|---|
| the ADK spans (Trace Explorer) | `a512da51efd6f41b468ad1b65711646f` |
| the Cloud Run request log (`run.googleapis.com/requests`) | `a9febcac58f1c18504346514663611d8` |

They differ because ADK's API server does not read the inbound trace header on
Cloud Run; its propagation middleware runs only for Gemini Enterprise
(`google/adk/cli/fast_api.py:456`, `:543-553`). Cloud Run stamps its ingress
request with its own trace id, but nothing in the process extracts it, so ADK
opens a fresh trace. One HTTP request is described by two traces that never
meet. That split is the problem [Part 3](../part-3/index.md) closes:
[3.4 · One trace per request](../part-3/3.4-one-trace-per-request.md) makes
ADK's root a child of the request so the two become one.
