# 3.1 · The free join

*Part 3 · Correlate*

> [!NOTE]
> **Why you are here.** Some log lines are already inside the trace, and they
> arrived there with no work from you. This page finds them and names the field
> that put them there.

Run the `02` server from [2.3 · Your own server](../part-2/2.3-your-own-server.md),
which enables Cloud Logging alongside tracing. If a server from Part 2 is still
running, stop it (Ctrl+C) first; all three servers use port 8080.

**Command:**

```bash
source .venv/bin/activate
source env.sh
python examples/02_trace_server.py
```

The server runs in the foreground. In a second terminal, send one London turn:

**Command:**

```bash
cd "$(git rev-parse --show-toplevel)/ai/adk/tracing"
source env.sh
export HOST=http://localhost:8080
export ENDPOINT=chat
./load/turns.sh baseline 1
```

Then open the turn's trace and read the logs attached to its spans. A new trace
takes a minute or two to appear. In the Google Cloud console:

- Open **Trace Explorer**.
- Click **Trace ID** in the toolbar.
- Paste the trace id your turn printed and search.
- Expand every span in the waterfall.
- Select the first `generate_content` span (not its parent `call_llm`).
- Open **Logs & Events**.
- Repeat for the second `generate_content` span.

**Expected output:** the model's own messages, each with content `<elided>`:

| Span | **Logs & Events** |
|---|---|
| first `generate_content` | `gen_ai.system.message`, `gen_ai.user.message`, `gen_ai.choice` |
| second `generate_content` | `gen_ai.system.message`, three `gen_ai.user.message`, `gen_ai.choice` |

> [!IMPORTANT]
> **What it means.** These `gen_ai.*` entries are the model's inputs and outputs,
> and every one carries the `spanId` of the call that produced it. The turn makes
> two model calls, so each call's `gen_ai.choice` sits on its own
> `generate_content` span. ADK emitted them through the same Cloud Logging
> exporter that carries the field, so the join is free: you turned on nothing.

The content reads `<elided>` because message content in these events is off by
default; [1.3](../part-1/1.3-attributes-and-content.md)'s deep dive names the
variable, `OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT`.

Now go the other way, from the trace to the logs. In the trace details panel:

- Click **View logs**.

**Expected output:** Logs Explorer opens with `trace="projects/…/traces/…"`
prefilled and lists the same entries, each linking back to the trace.

> [!IMPORTANT]
> **What it means.** The round trip works because both ends carry the same trace
> id.

Every stream that follows in this part is about getting your *other* log
lines (the ones that do not carry the field yet) to join the same way.
[3.2](3.2-your-tools-log-line.md) starts with the one you most want: your tool's.

## Deep dives

### Which fields make the join, and must they share a project?

A `LogEntry` joins a span through two fields, `trace` and `spanId`. The
exporter writes them, plus a third, from the log record
(`opentelemetry/exporter/cloud_logging/__init__.py:360-367`):

| Field | Value | Role |
|---|---|---|
| `trace` | `projects/PROJECT_ID/traces/TRACE_ID` | which trace |
| `spanId` | 16 hex chars | which span within it |
| `traceSampled` | bool | whether the trace was kept (not part of the match) |

The match is exact and same-project: the log's `trace` and `spanId` must name a
span stored in the same project. A `spanId` with no matching span, or a matching
span in another project, shows nothing in the trace details panel. That is why
the lines that look correlated in
[3.3](3.3-framework-and-server-logs.md) fail in the specific ways they do.
