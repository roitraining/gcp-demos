# 3.1 · The free join

*Part 3 · Correlate*

> [!NOTE]
> **Why you are here.** Some log lines are already inside the trace, and they
> arrived there with no work from you. This page finds them and names the field
> that put them there.

Run the `02` server from [2.3](../part-2/2.3-your-own-server.md), which enables
Cloud Logging alongside tracing, and send one London turn. Then read every log
entry that carries the turn's trace id:

**Command:**

```bash
gcloud logging read 'trace="projects/'"$PROJECT_ID"'/traces/ae6b5c659c9cc62c3b664ad5d464b234"'
```

**Expected output:** the model's own messages, each carrying a `spanId`:

```console
logName=gen_ai.system.message   spanId=27e2f78b3037b5c0   content=[the system instruction]
logName=gen_ai.user.message     spanId=27e2f78b3037b5c0   content=[what's the weather...]
logName=gen_ai.choice           spanId=27e2f78b3037b5c0   content=[the model's reply]
```

> [!IMPORTANT]
> **What it means.** These `gen_ai.*` entries are the model's inputs and outputs,
> and every one carries a `spanId`. That `spanId` is the `generate_content` span
> under `call_llm`, so in the **Trace Explorer**, select `call_llm`, open the
> **Logs & Events** tab, and these entries are listed under it. ADK emitted them
> through the same Cloud Logging exporter that carries the field, so the join is
> free — you turned on nothing.

In the flyout, **View logs** opens Logs Explorer with `trace="…"` prefilled, and
each entry links back to the trace. The round trip works because both ends carry
the same trace id.

> [!NOTE]
> On 2.8.0 the `gen_ai.*` events attach to the `generate_content` span, a child of
> `call_llm`, not to `call_llm` itself. Either way they appear under the model
> call in the tree.

Every stream that follows in this part is about getting your *other* log
lines — the ones that do not carry the field yet — to join the same way.
[3.2](3.2-your-tools-log-line.md) starts with the one you most want: your tool's.

## Deep dives

### The three fields, and the same-project rule

A `LogEntry` joins a span through three fields the exporter writes from the log
record (`cloud_logging/__init__.py:360-367`):

| Field | Value | Role |
|---|---|---|
| `trace` | `projects/PROJECT_ID/traces/TRACE_ID` | which trace |
| `spanId` | 16 hex chars | which span within it |
| `traceSampled` | bool | whether the trace was kept |

The match is exact and same-project: the log's `trace` and `spanId` must name a
span stored in the same project. A `spanId` with no matching span, or a matching
span in another project, shows nothing in the flyout. That is why the negative
controls in [3.3](3.3-framework-and-server-logs.md) fail in the specific ways
they do.
