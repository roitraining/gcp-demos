# 3.4 · One trace per request

*Part 3 · Correlate*

> [!NOTE]
> **Why you are here.** [2.2](../part-2/2.2-cloud-run.md) found two trace ids for
> one Cloud Run request: the request log under Cloud Run's, the spans under ADK's.
> This page makes them one, and names the trap that comes with it.

The `04` server ([examples/04_propagated_server.py](../../examples/04_propagated_server.py))
adds three things to `03`: `FastAPIInstrumentor.instrument_app(app)` for a server
span that extracts the inbound trace context, a composite propagator that reads
both header formats, and an always-on sampler.

**Step 1 — Tag a request.** Send a turn with a `traceparent` header and read the
returned trace id:

**Command:**

```bash
curl -s -X POST localhost:8080/chat \
  -H 'content-type: application/json' \
  -H 'traceparent: 00-0af7651916cd43dd8448eb211c80319c-b7ad6b7169203331-01' \
  -d '{"text":"What'\''s the weather in London?"}'
```

**Expected output:**

```console
{"response":"The weather in London is currently 15°C and drizzling.",
 "trace_id":"0af7651916cd43dd8448eb211c80319c"}
```

The returned trace id **equals the header's**. Read the tree back and the reason
is visible in the parent chain:

```console
POST /chat                       parent → (the inbound header's span)
  invocation                     parent → POST /chat
    invoke_agent weather_agent
      call_llm → generate_content, execute_tool
```

> [!IMPORTANT]
> **What it means.** ADK's `invocation` is now a child of the `POST /chat` server
> span, and the server span sits under the inbound header. So the whole request,
> from the `POST /chat` server span and the `chat request received` line to the full ADK tree,
> is one trace under one id: the id the caller sent.

On Cloud Run, the same `04` server
([deploy/Dockerfile.trace_server](../../deploy/Dockerfile.trace_server)) takes its
`traceparent` from Cloud Run's frontend, and a sampled request gains one level on
top: the frontend's own `/chat` span.

**Expected output** (captured on Cloud Run, the London turn):

```console
trace 7411a4c4483e219a5730a9083c71b16e  (12 spans)
/chat
  POST /chat
    POST /chat http receive
    invocation
      invoke_agent weather_agent
        call_llm
          generate_content gemini-3.7-flash
          execute_tool get_weather
        call_llm
          generate_content gemini-3.7-flash
    POST /chat http send
    POST /chat http send
```

> [!IMPORTANT]
> **What it means.** This merges the two trace ids from 2.2. The request log's
> trace, the returned `trace_id`, the spans, and the bridged app log lines all
> carry `7411a4c4…`, and the request log's span id is the `/chat` span's. Because
> the entries share a trace, Logs Explorer's **Correlate by** `request_log` has
> what it groups on. An unsampled request has no `/chat` span; `POST /chat` then
> sits under a parent that is not in the trace.

## Deep dives

### Why did propagation make my traces disappear?

Turn propagation on carelessly and you can lose almost every trace. The default
sampler is `ParentBased(ALWAYS_ON)`: for a request with a parent, it does what the
parent decided. Cloud Run samples its own request traces at a low rate and marks
the rest unsampled (`traceparent` flags `00`). A propagated unsampled parent means
`ParentBased` keeps **nothing** for that request. Since most Cloud Run requests
arrive unsampled, that is the common case, not the edge.

Reproduce it with a `00`-flag header:

```bash
curl -s -X POST localhost:8080/chat \
  -H 'traceparent: 00-11111111111111111111111111111111-2222222222222222-00' \
  -d '{"text":"What'\''s the weather in London?"}'
```

With the default sampler, that request records **zero** spans. The fix is the
line `04` sets before it builds the provider:

```bash
export OTEL_TRACES_SAMPLER=always_on
```

With `always_on`, the same `00`-flag request records the full tree under the
header's id. Always set the sampler when you turn propagation on, or the feature
that was supposed to unify your traces deletes them instead.

> [!NOTE]
> On Cloud Run the W3C `traceparent` alone is enough, because Cloud Run always
> sends it.
> The composite propagator also reads `X-Cloud-Trace-Context`, which matters only
> for GCP-only callers that send that header without `traceparent`.
