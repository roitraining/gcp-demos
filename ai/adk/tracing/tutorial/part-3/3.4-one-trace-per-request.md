# 3.4 · One trace per request

*Part 3 · Correlate*

> [!NOTE]
> **Why you are here.** [2.2](../part-2/2.2-cloud-run.md) found two trace ids for
> one Cloud Run request: the request log under Cloud Run's, the spans under ADK's.
> This page makes them one, and shows how propagation can stop traces from being
> recorded.

The `04` server ([examples/04_propagated_server.py](../../examples/04_propagated_server.py))
adds three things to `03`: `FastAPIInstrumentor.instrument_app(app)` for a server
span that extracts the inbound trace context, a composite propagator (the part
that reads the trace id from an incoming header) that understands both header
formats, and an always-on sampler.

**Step 1 — Start the `04` server.** Stop the `03` server (Ctrl+C), clear the
error gate from 3.2, and start `04`:

**Command:**

```bash
unset TUTORIAL_CLASSIFY_ERRORS
.venv/bin/python examples/04_propagated_server.py
```

**Step 2 — Tag a request.** In the second terminal, send a turn with a
`traceparent` header and read the returned trace id:

**Command:**

```bash
curl -s -X POST localhost:8080/chat \
  -H 'content-type: application/json' \
  -H 'traceparent: 00-0af7651916cd43dd8448eb211c80319c-b7ad6b7169203331-01' \
  -d '{"text":"What'\''s the weather in London?"}'
```

**Expected output:**

```console
{"response":"The weather in London is currently 15°C and drizzling.",
 "trace_id":"0af7651916cd43dd8448eb211c80319c"}
```

The returned trace id equals the header's. Read the tree back and the reason
is visible in the parent chain.

**Expected output** (illustrative, trimmed; the real tree has 11 spans,
including a `POST /chat http receive` span and two `POST /chat http send` spans
under `POST /chat`):

```console
POST /chat                       parent → (the inbound header's span)
  invocation                     parent → POST /chat
    invoke_agent weather_agent
      call_llm → generate_content, execute_tool
```

> [!IMPORTANT]
> **What it means.** ADK's `invocation` is now a child of the `POST /chat` server
> span, and the server span sits under the inbound header. So the whole request,
> from the `POST /chat` server span and the `chat request received` line to the
> full ADK tree, is one trace under one id: the id the caller sent.

On Cloud Run the same server takes its `traceparent` from Cloud Run's frontend,
so the request log joins the trace too. See [What does the Cloud Run trace look
like?](#what-does-the-cloud-run-trace-look-like)

## Deep dives

### What does the Cloud Run trace look like?

Deployed with [deploy/Dockerfile.trace_server](../../deploy/Dockerfile.trace_server)
and `SERVER=examples/04_propagated_server.py`, a sampled request gains one level
on top: the frontend's own `/chat` span. This was captured on Cloud Run for the
London turn; this page does not ask you to deploy it.

```console
trace 7411a4c4483e219a5730a9083c71b16e  (12 spans)
/chat
  POST /chat
    POST /chat http receive
    invocation
      invoke_agent weather_agent
        call_llm
          generate_content gemini-3.7-flash
          execute_tool get_weather
        call_llm
          generate_content gemini-3.7-flash
    POST /chat http send
    POST /chat http send
```

This merges the two trace ids from 2.2. The request log's trace, the returned
`trace_id`, the spans, and the bridged app log lines all carry `7411a4c4…`, and
the request log's span id is the `/chat` span's. Because the entries share a
trace, Logs Explorer's **Correlate by** `request_log` has what it groups on. An
unsampled request has no `/chat` span; `POST /chat` then sits under a parent
that is not in the trace.

### Why did propagation make my traces disappear?

Propagation can silently stop your traces from being recorded. The default
sampler is `ParentBased(ALWAYS_ON)`: keep every root span, and follow the
parent's decision for a span with a parent. Cloud Run samples its own request
traces at a low rate and marks the rest unsampled (`traceparent` flags `00`). A
propagated unsampled parent means `ParentBased` records nothing for that
request. Since most Cloud Run requests arrive unsampled, that is the common case,
not the edge.

The `04` server already avoids this: it sets the sampler before it builds the
provider ([examples/04_propagated_server.py:42](../../examples/04_propagated_server.py)):

```python
os.environ.setdefault("OTEL_TRACES_SAMPLER", "always_on")
```

To see the problem, override it with the default. Stop `04` (Ctrl+C) and
restart it:

**Command:**

```bash
export OTEL_TRACES_SAMPLER=parentbased_always_on
.venv/bin/python examples/04_propagated_server.py
```

In the second terminal, send a request whose header is unsampled, then try to
read its trace:

**Command:**

```bash
curl -s -X POST localhost:8080/chat \
  -H 'content-type: application/json' \
  -H 'traceparent: 00-5c0ffee5c0ffee5c0ffee5c0ffee5c0f-2222222222222222-00' \
  -d '{"text":"What'\''s the weather in London?"}'
./trace/get_trace.sh 5c0ffee5c0ffee5c0ffee5c0ffee5c0f
```

**Expected output:** the turn answers, but after two minutes of retries the
trace does not exist (trimmed):

```console
{"response":"The weather in London is currently 15°C and drizzling.","trace_id":"5c0ffee5c0ffee5c0ffee5c0ffee5c0f"}
...
    "message": "Trace not found: 5c0ffee5c0ffee5c0ffee5c0ffee5c0f",
    "status": "NOT_FOUND"
...
gave up after ~2 min; the trace may still be indexing
```

Stop the server, `unset OTEL_TRACES_SAMPLER`, and restart: with `always_on`, the
same `00`-flag request records the full tree under the header's id. Always set
the sampler when you turn propagation on, or the feature that was supposed to
unify your traces stops them from being recorded.

> [!NOTE]
> On Cloud Run the W3C `traceparent` alone is enough, because Cloud Run always
> sends it.
> The composite propagator also reads `X-Cloud-Trace-Context`, which matters only
> for GCP-only callers that send that header without `traceparent`.
