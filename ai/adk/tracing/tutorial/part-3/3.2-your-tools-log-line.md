# 3.2 · Your tool's log line is missing

*Part 3 · Correlate*

> [!NOTE]
> **Why you are here.** The model's messages joined for free. Your tool's warning
> did not. This page shows the gap, then closes it with one bridge — the payoff
> for the whole part.

Run the `02` server on the `classified-error` scenario, so the failing tool span
is red:

```bash
export TUTORIAL_CLASSIFY_ERRORS=1
```

Send the Atlantis turn. In the Trace Explorer, select `execute_tool get_weather`:
`error.type=lookup_failed` is in **Attributes**, the bar is red — and the **Logs &
Events** tab is **empty**. The tool logged a WARNING (`weather lookup failed for
'Atlantis'`), but it is nowhere near the span.

> [!IMPORTANT]
> **What it means.** ADK installs no bridge from Python's `logging` to the trace.
> Your tool's WARNING went to the console with no trace id, so no span lists it.
> The one piece of evidence that the tool failed is disconnected from the red span
> that says it failed.

**👉 Close the gap.** Switch to the `03` server
([examples/03_correlated_server.py](../../examples/03_correlated_server.py)),
which adds one bridge — an OTel `LoggingHandler` on the root logger — and rerun
the same turn. Now read the WARNING back:

**Command:**

```bash
gcloud logging read 'trace="projects/'"$PROJECT_ID"'/traces/ae6b5c659c9cc62c3b664ad5d464b234" AND severity=WARNING'
```

**Expected output:**

```console
severity:     WARNING
trace:        projects/jwd-gcp-demos/traces/ae6b5c659c9cc62c3b664ad5d464b234
spanId:       9d20dbf0a73c5cf5
traceSampled: True
message:      weather lookup failed for 'Atlantis': no data
```

> [!IMPORTANT]
> **What it means.** `spanId=9d20dbf0a73c5cf5` is the `execute_tool get_weather`
> span — the red one. Select it in the Trace Explorer now and its **Logs &
> Events** tab shows the WARNING, its severity beside `error.type=lookup_failed`.
> The failure and its evidence are finally in one place. That is the payoff
> [4.3](../part-4/index.md) reads back to diagnose a failed step.

## Deep dives

### What the bridge captures, and what the exporter writes

The `LoggingHandler` reads the current span at the moment the record is created
and copies its `trace_id`, `span_id`, and `trace_flags` onto the log record.
Because the tool runs inside its `execute_tool` span (a `with
start_as_current_span`), the current span *is* `execute_tool`, so the WARNING gets
that span's ids. The `CloudLoggingExporter` then writes them out
(`cloud_logging/__init__.py:360-367`): `trace_id` becomes the `trace` field,
`span_id` becomes `spanId`. Nothing in the tool changed — the same
`logger.warning` call now carries the ids because a handler on the root logger
adds them. The bridge is one line of setup, done once at startup.
