# 3.2 · Your tool's log line is missing

*Part 3 · Correlate*

> [!NOTE]
> **Why you are here.** The model's messages joined for free. Your tool's warning
> did not. This page shows the gap, then closes it with one bridge that the rest
> of the part reuses.

**Step 1 — Send a failing turn to the `02` server.** Stop the `02` server from
3.1 (Ctrl+C) and restart it with the `classified-error` gate, so the failing
tool span is red:

**Command:**

```bash
source .venv/bin/activate
export TUTORIAL_CLASSIFY_ERRORS=1
python examples/02_trace_server.py
```

In the second terminal, send one Atlantis turn:

**Command:**

```bash
cd "$(git rev-parse --show-toplevel)/ai/adk/tracing"
source env.sh
export HOST=http://localhost:8080
export ENDPOINT=chat
./load/turns.sh classified-error 1
```

**Expected output:** the turn's trace id, and in the server's terminal, the
tool's WARNING:

```console
classified-error turn   1  7.23s  trace=ee002a29867d64eca15b81a164b486e5
```

```console
weather lookup failed for 'Atlantis': no data
INFO:     127.0.0.1:50972 - "POST /chat HTTP/1.1" 200 OK
```

**Step 2 — Look for the WARNING in the trace.** A new trace takes a minute or
two to appear. In the Google Cloud console:

- Open **Trace Explorer**.
- Click **Trace ID** in the toolbar.
- Paste the trace id your turn printed and search.
- Expand every span in the waterfall.
- Select the red `execute_tool get_weather` span.
- Open **Logs & Events**.
- Select each `generate_content` span and open **Logs & Events** again.

**Expected output:** the tool span's **Logs & Events** is empty. The trace's
only logs are the model's `gen_ai.*` events from [3.1](3.1-the-free-join.md), on
the two `generate_content` spans.

> [!IMPORTANT]
> **What it means.** The `execute_tool get_weather` span carries
> `error.type=lookup_failed`, yet no log in the trace is a WARNING and none sits
> on that span. ADK installs no bridge from Python's `logging` to the trace, so the
> WARNING printed to the server's terminal as a bare line, with no trace or span
> id, and never reached Cloud Logging. The one piece of evidence that the tool
> failed is disconnected from the red span that says it failed.

**Step 3 — Close the gap.** Switch to the `03` server
([examples/03_correlated_server.py](../../examples/03_correlated_server.py)),
which adds one bridge (an OTel `LoggingHandler` on the root logger). Stop the
`02` server (Ctrl+C) and start `03` in the same terminal;
`TUTORIAL_CLASSIFY_ERRORS=1` is still set there:

**Command:**

```bash
python examples/03_correlated_server.py
```

In the second terminal, send the same turn:

**Command:**

```bash
./load/turns.sh classified-error 1
```

The server's terminal no longer prints the tool's WARNING. That is expected: the
log now goes to Cloud Logging. Open the new trace in the console:

- In **Trace Explorer**, click **Trace ID** and search for the trace id this turn
  printed.
- Expand every span in the waterfall.
- Select the red `execute_tool get_weather` span.
- Open **Logs & Events**.

**Expected output:** one WARNING entry on the tool span,
`weather lookup failed for 'Atlantis': no data`.

> [!IMPORTANT]
> **What it means.** The WARNING now carries the red `execute_tool get_weather`
> span's id, so it sits beside `error.type=lookup_failed`. The
> failure and its evidence are finally in one place, which is what
> [4.3 · The failed step](../part-4/4.3-the-failed-step.md) reads back to
> diagnose a failed step.

## Deep dives

### What the bridge captures, and what the exporter writes

The `LoggingHandler` reads the current span at the moment the record is created
and copies its `trace_id`, `span_id`, and `trace_flags` onto the log record.
Because the tool runs inside its `execute_tool` span (a `with
start_as_current_span`), the current span *is* `execute_tool`, so the WARNING gets
that span's ids. The `CloudLoggingExporter` then writes them out
(`opentelemetry/exporter/cloud_logging/__init__.py:360-367`): `trace_id` becomes the `trace` field,
`span_id` becomes `spanId`. Nothing in the tool changed: the same
`logger.warning` call now carries the ids because a handler on the root logger
adds them. The bridge is three lines of setup, done once at startup
([examples/03_correlated_server.py:81-83](../../examples/03_correlated_server.py)):

```python
handler = LoggingHandler(level=logging.INFO, logger_provider=get_logger_provider())
logging.getLogger().addHandler(handler)
logging.getLogger().setLevel(logging.INFO)
```
