# 3.5 · Three ways to stamp

*Part 3 · Correlate*

> [!NOTE]
> **Why you are here.** This part used one bridge. There are three, and which one
> fits depends on where your logs go. This reference page lays them side by side.

All three read the trace id from the current OpenTelemetry span (which, inside a
tool, is `execute_tool`). They differ in where the log ends up and whether that
works from a laptop.

| Way | What it is | Where logs go | Works locally? |
|---|---|---|---|
| **A** (this part) | OTel `LoggingHandler` on the root logger | the same `CloudLoggingExporter` the `gen_ai.*` events use, log name `adk-otel` (or `GOOGLE_CLOUD_DEFAULT_LOG_NAME`) | **yes**, via the Logging API |
| **B** | `google-cloud-logging`'s `CloudLoggingHandler` | Logging API, or stdout JSON | yes, for the API handler |
| **C** | a JSON formatter to stdout | Cloud Run's stdout ingestion, via the `logging.googleapis.com/*` keys | **no** — stdout does not reach Cloud Logging from a laptop |

This tutorial chose **way A** because it reuses the exporter `get_gcp_exporters`
already installs, works on a laptop so no page needed a deploy, and the
correlation is written by the same exporter that stamps the framework's `gen_ai.*`
events — which is the lesson.

## When to reach for each

- **Way A** — the default. One handler at startup, no second client library, one
  export path for framework and application logs alike.
- **Way B** — when you already depend on `google-cloud-logging` for its structured
  logging or its resource detection. It reads the span the same way; it just adds
  a second library for the same result. It also reads a `traceparent` or
  `X-Cloud-Trace-Context` header when no span is current
  (`logging_v2/handlers/_helpers.py:226-260`), which way A does not.
- **Way C** — Cloud Run only, when you want structured stdout and no Logging API
  calls. The logging tutorial's `CloudRunJsonFormatter` is this, reading
  `trace.get_current_span()` instead of the request header. It does nothing on a
  laptop, because a laptop's stdout is not ingested.

The `ContextVar` trick some servers use to carry a trace id across a request is
not needed with any of these: the span **is** the context, so the current span is
always available wherever the record is created.

[Part 4](../part-4/index.md) leaves correlation behind and uses the joined trace
to answer the on-call questions.
