# 3.3 · Framework and server logs

*Part 3 · Correlate*

> [!NOTE]
> **Why you are here.** The bridge from 3.2 does not only stamp your logs; it
> stamps every log line emitted inside a span. This page confirms that for the
> framework's logs, and shows what a line that only *looks* correlated does.

The same `03` server, with `google_adk` logging at INFO. Send a `slow-tool`
(forecast) turn and read the trace's logs. The framework's lines join too:

**Command:**

```bash
gcloud logging read 'trace="projects/'"$PROJECT_ID"'/traces/497cc8ea3c440f6696053290428686f9" AND logName="projects/'"$PROJECT_ID"'/logs/adk-tracing"' \
  --format='value(severity,spanId,textPayload)'
```

**Expected output:** the bridged records, which land under log name
`adk-tracing` (set by `GOOGLE_CLOUD_DEFAULT_LOG_NAME`), newest first:

```console
INFO	181261a0d84f913a	Response received from the model.
INFO	181261a0d84f913a	Sending out request, model: gemini-3.7-flash, backend: GoogleLLMVariant.VERTEX_AI, stream: False
INFO	97859d0f07ab07f3	fetched 3-day forecast for London
INFO	598d358422a88224	Response received from the model.
INFO	598d358422a88224	Sending out request, model: gemini-3.7-flash, backend: GoogleLLMVariant.VERTEX_AI, stream: False
```

> [!IMPORTANT]
> **What it means.** The four `google_adk` lines carry the ids of the two
> `generate_content` spans, and the tool's own INFO line (`fetched 3-day
> forecast`) carries the `execute_tool get_forecast` id: the same bridge stamps
> all of them, because each was emitted inside a span. One line is missing: the
> server prints `"POST /chat HTTP/1.1" 200 OK`, but it never reaches Cloud
> Logging. `uvicorn.access` does not propagate to the root logger, so the bridge
> never sees it, and it runs *outside* any ADK span anyway. That access log is
> exactly what [3.4](3.4-one-trace-per-request.md) puts inside the trace.

## Deep dives

### Negative controls: four lines that only look correlated

A bridge stamps whatever span is current when the record is created. Four entries
resemble correlation and are not; the flyout shows nothing under a span for any of
them.

| # | The entry | Why it does not join |
|---|---|---|
| 1 | `03`'s startup line, logged before any request | no current span at startup, so no `trace` field; found by nothing |
| 2 | a hand-written entry with only `jsonPayload.trace_id` | a text search finds it; `trace=` does not, and no span lists it. The field must be the top-level `trace`, not a payload key |
| 3 | an entry with `trace` but no `spanId` | `trace=` returns it and the trace-level **View logs** shows it, but no single span's **Logs & Events** does |
| 4 | `concurrent` turns fired in parallel | each bridged line carries the span of *its own* request; none crosses into another request's span |

Control 1 is built into the `03` server: it logs `trace server starting up (no
span here)` at startup, and that line has no `trace` field. Controls 2 and 3 turn
on the rule the Python client documents: fields set by hand override the active
span, so a half-set entry joins halfway or not at all. Control 4 is the one that
matters in production: run `turns.sh concurrent 4` and confirm no bridged line
appears under another request's span. The span *is* the context, so overlap does
not confuse it.
