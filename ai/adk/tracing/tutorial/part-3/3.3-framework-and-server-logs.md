# 3.3 · Framework and server logs

*Part 3 · Correlate*

> [!NOTE]
> **Why you are here.** The bridge from 3.2 does not only stamp your logs; it
> stamps every log line emitted inside a span. This page confirms that for the
> framework's logs, and shows what a line that only *looks* correlated does.

The same `03` server from 3.2, which also bridges `google_adk`'s INFO lines. In
the second terminal, send two `slow-tool` turns. The first asks for London, the
second for the forecast:

**Command:**

```bash
./load/turns.sh slow-tool 2
```

**Expected output:**

```console
slow-tool       turn   1  4.61s  trace=0100c38f3ae4e8854882e7cfe553af6b
slow-tool       turn   2  5.65s  trace=d6453e74ead05871ef53324e69810ad2
```

Read the second turn's bridged logs. Replace the trace id with the one your
second turn printed:

**Command:**

```bash
gcloud logging read 'trace="projects/'"$PROJECT_ID"'/traces/d6453e74ead05871ef53324e69810ad2" AND logName="projects/'"$PROJECT_ID"'/logs/adk-tracing"' \
  --project="$PROJECT_ID" \
  --format='value(severity,spanId,textPayload)'
```

**Expected output:** the bridged records, which land under log name
`adk-tracing` (set by `GOOGLE_CLOUD_DEFAULT_LOG_NAME`), newest first:

```console
INFO	7ac1d669f7589a4f	Response received from the model.
INFO	7ac1d669f7589a4f	Sending out request, model: gemini-3.7-flash, backend: GoogleLLMVariant.VERTEX_AI, stream: False
INFO	653f32f6ab01c3b7	fetched 3-day forecast for London
INFO	f114e76f0fbcf305	Response received from the model.
INFO	f114e76f0fbcf305	Sending out request, model: gemini-3.7-flash, backend: GoogleLLMVariant.VERTEX_AI, stream: False
```

> [!IMPORTANT]
> **What it means.** The four `google_adk` lines carry the ids of the two
> `generate_content` spans, and the tool's own INFO line (`fetched 3-day
> forecast`) carries the `execute_tool get_forecast` id: the same bridge stamps
> all of them, because each was emitted inside a span. One line is missing: the
> server prints `"POST /chat HTTP/1.1" 200 OK`, but it never reaches Cloud
> Logging. `uvicorn.access` does not propagate to the root logger, so the bridge
> never sees it, and it runs outside any ADK span anyway. Cloud Run's request log
> is a separate entry, and [3.4](3.4-one-trace-per-request.md) puts that one in
> the trace. The uvicorn access line stays out of Cloud Logging.

## Deep dives

### Which lines look correlated but aren't?

A bridge stamps whatever span is current when the record is created. Four entries
resemble correlation and are not; the trace details panel shows none of them
under a span.

| # | The entry | Why it does not join |
|---|---|---|
| 1 | `03`'s startup line, logged before any request | no current span at startup, so no `trace` field; no span query returns it |
| 2 | a hand-written entry with only `jsonPayload.trace_id` | a payload search finds it; `trace=` does not, and no span lists it. The field must be the top-level `trace`, not a payload key |
| 3 | an entry with `trace` but no `spanId` | `trace=` returns it and the trace-level **View logs** shows it, but no single span's **Logs & Events** does |
| 4 | `concurrent` turns fired in parallel | each bridged line carries the span of its own request; none crosses into another request's span |

Control 1 is built into the `03` server: it logs `trace server starting up (no
span here)` at startup, and that line has no `trace` field. Controls 2 and 3 turn
on the rule the Python client documents: fields set by hand override the active
span, so a half-set entry joins halfway or not at all. Write both entries to a
scratch log, using the forecast turn's trace id:

**Command:**

```bash
export TRACE_ID=d6453e74ead05871ef53324e69810ad2
curl -s -X POST https://logging.googleapis.com/v2/entries:write \
  -H "Authorization: Bearer $(gcloud auth print-access-token)" \
  -H 'content-type: application/json' \
  -d '{"entries":[
    {"logName":"projects/'"$PROJECT_ID"'/logs/adk-tracing-neg","resource":{"type":"global"},"jsonPayload":{"message":"control 2: payload key only","trace_id":"'"$TRACE_ID"'"}},
    {"logName":"projects/'"$PROJECT_ID"'/logs/adk-tracing-neg","resource":{"type":"global"},"trace":"projects/'"$PROJECT_ID"'/traces/'"$TRACE_ID"'","jsonPayload":{"message":"control 3: trace, no spanId"}}
  ]}'
```

After a few seconds, search by the `trace` field, then by the payload key:

**Command:**

```bash
gcloud logging read 'logName="projects/'"$PROJECT_ID"'/logs/adk-tracing-neg" AND trace="projects/'"$PROJECT_ID"'/traces/'"$TRACE_ID"'"' \
  --project="$PROJECT_ID" \
  --format='value(jsonPayload.message,spanId)'
gcloud logging read 'logName="projects/'"$PROJECT_ID"'/logs/adk-tracing-neg" AND jsonPayload.trace_id="'"$TRACE_ID"'"' \
  --project="$PROJECT_ID" \
  --format='value(jsonPayload.message,spanId)'
```

**Expected output:** the `trace` search finds only control 3, with an empty
`spanId`; only the payload search finds control 2:

```console
control 3: trace, no spanId
control 2: payload key only
```

Control 4 is the one that matters in production. Fire four overlapping turns,
then read each trace's bridged lines:

**Command:**

```bash
./load/turns.sh concurrent 4 | tee out/concurrent.txt
for t in $(grep -o '[0-9a-f]\{32\}' out/concurrent.txt); do
  echo "== $t"
  gcloud logging read "trace=\"projects/$PROJECT_ID/traces/$t\" AND logName=\"projects/$PROJECT_ID/logs/adk-tracing\"" \
    --project="$PROJECT_ID" \
    --format='value(spanId,textPayload)'
done
```

**Expected output** (trimmed to two of the four turns):

```console
== 9c38ed1be3f3556a3a3b13724b296b5a
27ecc5475f1c3419	Response received from the model.
27ecc5475f1c3419	Sending out request, model: gemini-3.7-flash, backend: GoogleLLMVariant.VERTEX_AI, stream: False
8ea1f277e1d3e5b7	Response received from the model.
8ea1f277e1d3e5b7	Sending out request, model: gemini-3.7-flash, backend: GoogleLLMVariant.VERTEX_AI, stream: False
== b42456013a19513fc960599cfc895198
c96660d5941ce140	Response received from the model.
c96660d5941ce140	Sending out request, model: gemini-3.7-flash, backend: GoogleLLMVariant.VERTEX_AI, stream: False
ddfe3ab397f09c59	fetched 3-day forecast for London
301995bd7b969ffb	Response received from the model.
301995bd7b969ffb	Sending out request, model: gemini-3.7-flash, backend: GoogleLLMVariant.VERTEX_AI, stream: False
```

Only the forecast turns hold a `fetched 3-day forecast` line, and every span id
appears under one trace only. The current span carries the ids, so overlap does
not confuse the bridge. Delete the scratch log when you are done:

**Command:**

```bash
gcloud logging logs delete adk-tracing-neg \
  --project="$PROJECT_ID" \
  --quiet
unset TRACE_ID
```
