# 3.3 · Framework and server logs

*Part 3 · Correlate*

> [!NOTE]
> **Why you are here.** The bridge from 3.2 does not only stamp your logs; it
> stamps every log line emitted inside a span. This page confirms that for the
> framework's logs, and shows what a line that only *looks* correlated does.

The same `03` server from 3.2, which also bridges `google_adk`'s INFO lines. In
the second terminal, send two `slow-tool` turns. The first asks for London, the
second for the forecast:

**Command:**

```bash
./load/turns.sh slow-tool 2
```

**Expected output:**

```console
slow-tool       turn   1  4.61s  trace=0100c38f3ae4e8854882e7cfe553af6b
slow-tool       turn   2  5.65s  trace=d6453e74ead05871ef53324e69810ad2
```

Open each turn's trace and read the logs on its spans. A new trace takes a
minute or two to appear. In the Google Cloud console:

- Open **Trace Explorer**.
- Click **Trace ID** in the toolbar.
- Paste the trace id your first turn printed and search.
- Expand every span in the waterfall.
- Select each `generate_content` span and open **Logs & Events**.
- Select the `execute_tool` span and open **Logs & Events**.
- Repeat for the second turn's trace id.

**Expected output:** beside 3.1's `gen_ai.*` events, these bridged lines, all
under log name `adk-tracing` (set by `GOOGLE_CLOUD_DEFAULT_LOG_NAME`):

| Turn | Span | Bridged lines in **Logs & Events** |
|---|---|---|
| 1 (London weather) | each `generate_content` | INFO `Sending out request, model: gemini-3.7-flash, …` and INFO `Response received from the model.` |
| 1 | `execute_tool get_weather` | none |
| 2 (forecast) | each `generate_content` | the same two INFO lines |
| 2 | `execute_tool get_forecast` | INFO `fetched 3-day forecast for London` |

> [!IMPORTANT]
> **What it means, finding one: the bridge stamps framework lines.** The
> `google_adk` lines sit on the `generate_content` spans in both turns, and the
> forecast tool's own INFO line sits on its `execute_tool` span. The same bridge
> stamps all of them, because each was emitted inside a span.

> [!IMPORTANT]
> **What it means, finding two: an empty span means nothing was logged.** Turn
> 1's `execute_tool get_weather` span is empty because `get_weather` logs only
> on failure (`demo_agent/agent.py:80`), not because the bridge missed a line.
> Compare the two turns before blaming the bridge.

One line never reaches Cloud Logging at all: the server prints `"POST /chat
HTTP/1.1" 200 OK`, but `uvicorn.access` does not propagate to the root logger, so
the bridge never sees it, and it runs outside any ADK span anyway. Cloud Run's
request log is a separate entry, and [3.4](3.4-one-trace-per-request.md) puts
that one in the trace.

## Deep dives

### Which lines look correlated but aren't?

A bridge stamps whatever span is current when the record is created. Four entries
resemble correlation and are not; the trace details panel shows none of them
under a span.

| # | The entry | Why it does not join |
|---|---|---|
| 1 | `03`'s startup line, logged before any request | no current span at startup, so no `trace` field; no span query returns it |
| 2 | a hand-written entry with only `jsonPayload.trace_id` | a payload search finds it; `trace=` does not, and no span lists it. The field must be the top-level `trace`, not a payload key |
| 3 | an entry with `trace` but no `spanId` | `trace=` returns it and the trace-level **View logs** shows it, but no single span's **Logs & Events** does |
| 4 | `concurrent` turns fired in parallel | each bridged line carries the span of its own request; none crosses into another request's span |

Control 1 is built into the `03` server: it logs `trace server starting up (no
span here)` at startup, and that line has no `trace` field. Controls 2 and 3 turn
on the rule the Python client documents: fields set by hand override the active
span, so a half-set entry joins halfway or not at all. Write both entries to a
scratch log, using the forecast turn's trace id:

**Command:**

```bash
export TRACE_ID=d6453e74ead05871ef53324e69810ad2
curl -s -X POST https://logging.googleapis.com/v2/entries:write \
  -H "Authorization: Bearer $(gcloud auth print-access-token)" \
  -H 'content-type: application/json' \
  -d '{"entries":[
    {"logName":"projects/'"$PROJECT_ID"'/logs/adk-tracing-neg","resource":{"type":"global"},"jsonPayload":{"message":"control 2: payload key only","trace_id":"'"$TRACE_ID"'"}},
    {"logName":"projects/'"$PROJECT_ID"'/logs/adk-tracing-neg","resource":{"type":"global"},"trace":"projects/'"$PROJECT_ID"'/traces/'"$TRACE_ID"'","jsonPayload":{"message":"control 3: trace, no spanId"}}
  ]}'
```

After a few seconds, reopen the forecast turn's trace in **Trace Explorer**:

- Select each span in turn and open **Logs & Events**.
- In the trace details panel, click **View logs**.

**Expected output:** no span's **Logs & Events** lists either control. The
Logs Explorer that **View logs** opens lists `control 3: trace, no spanId`
among the turn's entries, with an empty `spanId`, and does not list control 2.

> [!IMPORTANT]
> **What it means.** Control 3 joins the trace but no span, because it has
> `trace` and no `spanId`. Control 2 joins nothing: its id sits in
> `jsonPayload.trace_id`, which only a payload search such as
> `jsonPayload.trace_id="…"` in Logs Explorer finds.

Control 4 is the one that matters in production. Fire four overlapping turns:

**Command:**

```bash
./load/turns.sh concurrent 4
```

Open two of the four printed trace ids in **Trace Explorer**, one a weather
turn and one a forecast turn. In each, select every `generate_content` and
`execute_tool` span and open **Logs & Events**.

**Expected output:** each trace's `generate_content` spans hold the two
framework INFO lines, and only the forecast turn's `execute_tool get_forecast`
span holds `fetched 3-day forecast for London`. No span shows a line from
another turn.

The current span carries the ids, so overlap does not confuse the bridge.
Delete the scratch log when you are done:

**Command:**

```bash
gcloud logging logs delete adk-tracing-neg \
  --project="$PROJECT_ID" \
  --quiet
unset TRACE_ID
```
