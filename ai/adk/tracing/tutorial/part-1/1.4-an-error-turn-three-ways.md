# 1.4 · An error turn, three ways

*Part 1 · What a trace is*

> [!NOTE]
> **Why you are here.** A tool can fail three different ways, and only two of
> them leave a mark on the span. This page runs the same failing turn three times
> so you can see which failures a trace records — and which one it misses.

Ask the agent for a city it does not know: **What's the weather in Atlantis?**
`get_weather` cannot answer. What that does to the trace depends entirely on how
the tool reports the failure.

**Step 1 — The plain tool.** Run the Atlantis turn with no gates set:

**Command:**

```bash
.venv/bin/python examples/01_console_spans.py "What's the weather in Atlantis?"
```

**Expected output:** the model answers, and `execute_tool get_weather` in
`out/spans.json` looks like a success:

```console
AGENT: I do not have weather data for Atlantis.
```

```json
{ "name": "execute_tool get_weather", "status": { "status_code": "UNSET" } }
```

> [!IMPORTANT]
> **What it means.** The tool returned `{"status": "error", ...}` and logged a
> WARNING to the terminal, but the span is `UNSET` — no `error.type`, no event,
> no red bar. A plain `FunctionTool` does not read a returned status. The whole
> tree is green, the model politely reports no data, and the only sign anything
> went wrong is a log line that is nowhere near the trace. That gap is what
> [Part 3](../part-3/index.md) closes.

**Step 2 — Classify the failure.** Turn on the tool wrapper and rerun the same
turn:

**Command:**

```bash
export TUTORIAL_CLASSIFY_ERRORS=1
.venv/bin/python examples/01_console_spans.py "What's the weather in Atlantis?"
unset TUTORIAL_CLASSIFY_ERRORS
```

**Expected output:** the same span, now red:

```json
{
  "name": "execute_tool get_weather",
  "status": { "status_code": "ERROR", "description": "lookup_failed" },
  "attributes": { "error.type": "lookup_failed" }
}
```

> [!IMPORTANT]
> **What it means.** The gate wraps the tool in a `StatusAwareTool`, whose
> `_detect_error_in_response` hook maps the failure status to `lookup_failed`.
> Now the span is `ERROR` and carries `error.type`, so a status filter in Cloud
> Trace will find it ([4.3](../part-4/index.md)). The user's answer is
> unchanged — the model still says "no data" — but the trace now *knows*. The
> parents (`invoke_agent`, `invocation`) stay `UNSET`: one tool failing is not
> the turn failing.

You changed one condition (the hook, off then on) and the same failure went from
invisible to recorded. That is the lesson: **whether a returned failure reaches
the trace is a choice you make in the tool.**

## Deep dives

### The tool that raises

There is a third way a tool fails: it raises. Run the Atlantis turn with the
raising gate:

```bash
export TUTORIAL_RAISE_ON_UNKNOWN=1
.venv/bin/python examples/01_console_spans.py "What's the weather in Atlantis?"
unset TUTORIAL_RAISE_ON_UNKNOWN
```

Now `get_weather` raises `LookupError` instead of returning a status, and the
failure does not stop at the tool:

```console
execute_tool get_weather     status=ERROR   error.type=LookupError   events=[exception, exception]
invoke_agent weather_agent   status=ERROR   error.type=None          events=[exception]
invocation                   status=ERROR   error.type=None          events=[exception]
```

Three spans go red, each with an `exception` event carrying the traceback, and
the turn fails with no answer. `error.type` is the class name, chosen by
`resolve_error_type` (`tracing.py:177-192`); the exception **message** never
lands on the span, so the city name does not leak. The tool span carries **two**
exception events on 2.8.0 — the raised `LookupError` plus the
`DynamicNodeFailError` ADK wraps around it as it propagates. The script's
`try/finally` means `flush_spans()` runs even though the turn raised, so these
spans still reach the file.

### Three failures, three marks

| Tool behavior on the Atlantis turn | `execute_tool` status | `error.type` | Exception event | Parents |
|---|---|---|---|---|
| returns `{"status": "error", ...}` (plain `FunctionTool`) | UNSET | none | none | OK; model answers "no data" |
| returns `{"error": ...}` (plain `FunctionTool`) | ERROR | `TOOL_ERROR` | none | OK |
| same status through `StatusAwareTool` | ERROR | `lookup_failed` | none | OK; same answer |
| raises `LookupError` | ERROR | `LookupError` | two | both ERROR; request fails |

The second row is worth knowing: a plain tool returning a dict with an `error`
key gets `error.type=TOOL_ERROR` for free (`function_tool.py:355-359`). The demo
returns a `status` dict because that is what the sibling tutorials do, so the
hook is the lesson — but if your tools already return `{"error": ...}`, the
trace records them without any wrapper.
