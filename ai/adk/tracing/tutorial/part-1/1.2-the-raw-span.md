# 1.2 · The raw span

*Part 1 · What a trace is*

> [!NOTE]
> **Why you are here.** The dev UI drew the tree as bars. This page exports the
> same tree as JSON so you can read one span field by field, and see the ids that
> make it a tree.

The `baseline` scenario, again, but this time as a script. The example
[examples/01_console_spans.py](../../examples/01_console_spans.py) installs a
console span exporter, asks one London question, and flushes. The exporter writes
every span ADK opened during the turn to `out/spans.json`.

**👉 Do this.**

**Command:**

```bash
.venv/bin/python examples/01_console_spans.py
```

The agent's answer prints to the console, and the script writes the span tree to
`out/spans.json`. Open it in your editor to read it. In VS Code:

```bash
code out/spans.json
```

**Expected output:** the file holds all seven spans, each a JSON object. Here is
the `execute_tool get_weather` span, with the fields this page uses:

```console
AGENT: The weather in London is currently 15°C and drizzling.
(spans written to out/spans.json)
```

```json
{
  "name": "execute_tool get_weather",
  "context": {
    "trace_id": "0x19eedd6c5197ac5e69f1d7664715f63a",
    "span_id": "0x614a067938f5e0c0"
  },
  "kind": "SpanKind.INTERNAL",
  "parent_id": "0x2bda7bf0716efc76",
  "start_time": "2026-09-07T03:47:50.617342Z",
  "end_time": "2026-09-07T03:47:50.619067Z",
  "status": { "status_code": "UNSET" },
  "attributes": {
    "gen_ai.operation.name": "execute_tool",
    "gen_ai.tool.name": "get_weather",
    "gen_ai.tool.type": "FunctionTool",
    "gcp.vertex.agent.tool_call_args": "{\"city\": \"London\"}",
    "gcp.vertex.agent.tool_response": "{\"status\": \"ok\", \"report\": \"...\"}"
  },
  "events": [],
  "links": [],
  "resource": { "attributes": {} }
}
```

## What you are looking at

| field | value | what it is |
|---|---|---|
| `name` | `execute_tool get_weather` | The operation the span measures. The tool name is part of it, so the tree reads without opening anything. |
| `context.trace_id` | `0x19ee…f63a` | The id of the whole turn. Every span in this tree carries the same one. This is the key Part 3 stamps on log lines. |
| `context.span_id` | `0x614a…e0c0` | This span's own id. Unique within the trace. |
| `parent_id` | `0x2bda…fc76` | The `span_id` of the span this one sits under — here, the first `call_llm`. `parent_id` is what builds the tree. The root `invocation` has none. |
| `start_time` / `end_time` | two timestamps | The span's window. Their difference is the bar you saw in 1.1 (here ~1.7 ms). |
| `status` | `UNSET` | Whether the operation failed. `UNSET` means it ran fine. [1.4](1.4-an-error-turn-three-ways.md) turns this to `ERROR`. |
| `attributes` | `gen_ai.*`, `gcp.vertex.agent.*` | Everything else known about the operation: the tool name, its arguments, its result. [1.3](1.3-attributes-and-content.md) reads these. |
| `events` / `links` | empty here | Timestamped notes on the span (the exception on a raised tool, 1.4) and pointers to other spans. |

> [!IMPORTANT]
> **What it means.** A span is one operation with a start, an end, a status, and
> a bag of attributes, plus two ids: its own and its parent's. Give every span a
> `trace_id` and a `parent_id` and the flat list becomes the tree from 1.1. There
> is no tree object anywhere — the tree is reconstructed from the ids, which is
> exactly what Cloud Trace does when the spans arrive over the wire in
> [Part 2](../part-2/index.md).

Read the seven spans' `name`, `span_id`, and `parent_id` and you can redraw the
1.1 tree by hand. The `status` and `attributes` are what the next two pages are
about.

## Deep dives

### Why does the script need to flush?

The example calls `flush_spans()` before it returns. A batching exporter holds
spans in memory and ships them on an interval; a script that exits right after
its turn would exit before that interval and lose the batch. `flush_spans()`
calls `force_flush()` on the tracer provider, which drains it first. The console
exporter this page uses is a `SimpleSpanProcessor`, which exports each span the
moment it ends, so the file is already complete — but the flush is harmless, and
the [Part 2](../part-2/index.md) scripts that batch to the cloud depend on it. A
long-running server never needs it; its processor keeps exporting on the
interval.
