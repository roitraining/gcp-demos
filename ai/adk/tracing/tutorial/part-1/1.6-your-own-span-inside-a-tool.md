# 1.6 · Your own span inside a tool

*Part 1 · What a trace is*

> [!NOTE]
> **Why you are here.** So far every span was ADK's. This page adds one of your
> own inside a tool, so the tree shows not just that the tool was slow but *where*
> inside it the time went.

In [1.1](1.1-the-tree-you-already-have.md) the forecast tool's span was slow but
opaque: `execute_tool get_forecast` owned 0.4 s and told you nothing about what
happened in there. The tool does one thing worth naming (a call to
`_fetch_forecast()`), so wrap that call in a span.

The demo already has the code, behind a gate. It is four lines
([demo_agent/agent.py](../../demo_agent/agent.py)):

```python
tracer = trace.get_tracer(__name__)
# inside get_forecast:
with tracer.start_as_current_span("fetch_forecast") as span:
    span.set_attribute("forecast.days", days)
    report = _fetch_forecast(city, days)
```

**👉 Do this.** Run the forecast turn with the custom-span gate on:

**Command:**

```bash
export TUTORIAL_CUSTOM_SPAN=1
python examples/01_console_spans.py "What's the three-day forecast for London?"
unset TUTORIAL_CUSTOM_SPAN
```

**Expected output:** a new span, `fetch_forecast`, nested under the tool span
(drawn from `out/spans.json`, trimmed to the tool's branch):

```console
invoke_agent weather_agent          (5.15s)
├─ call_llm
│  └─ execute_tool get_forecast     0.700s
│     └─ fetch_forecast             0.695s   forecast.days=3
└─ call_llm
```

> [!IMPORTANT]
> **What it means.** `fetch_forecast` owns 0.695 s of the tool's 0.700 s, so the
> tree now says the time is in the fetch, not in ADK's tool machinery. You did
> not pass a tracer in or wire up a provider: `trace.get_tracer(__name__)`
> resolves against whatever provider is installed, and `start_as_current_span`
> nests under whatever span is current, which inside a tool body is
> `execute_tool`. Your span is a first-class child, with its own attribute
> (`forecast.days`) describing the work.

That is the whole technique for instrumenting your own code: get a tracer, open a
span around the work, set an attribute or two. In [Part 2](../part-2/index.md)
this same `fetch_forecast` span rides the export to Cloud Trace with the rest of
the tree.

## Deep dives

### Why does the span nest, and where will it not?

`start_as_current_span` reads the current span from the OpenTelemetry context and
makes the new span its child. Inside a tool body the current span is
`execute_tool`, because ADK opened it with `start_as_current_span` too
(`google/adk/telemetry/_instrumentation.py:509`) and the tool runs inside that `with`. So nesting is
automatic: you never name the parent.

The one place it breaks is work on another thread, such as `threading.Thread`
or `loop.run_in_executor`. A span opened there does not see the current span,
so it becomes a new root, not a child. Capture the context with
`ctx = contextvars.copy_context()` before you hand the work off, and run it as
`ctx.run(...)` on the other thread. `asyncio.create_task` and
`asyncio.to_thread` already copy the context. For the straight-line call this
tool makes, nothing special is needed.

### Why no `gen_ai.` prefix?

`fetch_forecast` and `forecast.days` carry no `gen_ai.` prefix, deliberately.
That prefix belongs to the GenAI semantic convention: spans and attributes ADK
opens to a shared schema. A span you open for your own code is yours to name;
keep it out of the `gen_ai.` namespace so a reader can tell your instrumentation
from the framework's.
