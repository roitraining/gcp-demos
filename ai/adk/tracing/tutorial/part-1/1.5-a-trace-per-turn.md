# 1.5 · A trace per turn, a session across traces

*Part 1 · What a trace is*

> [!NOTE]
> **Why you are here.** It is tempting to think a trace is a conversation. It is
> not: a trace is one turn. This page runs five turns in one session so you can
> see where the boundary really is, and which id ties the turns together.

The `multi-turn` scenario asks five questions in a single session. Each turn is
its own trace; what links them is an attribute, not a trace id.

**👉 Do this.** Run five turns in one session and read the roots. (This uses a
short variant of the console example that keeps one session across the loop.)

```console
invocation spans (turns):                    5
distinct trace ids across invocations:       5
distinct gen_ai.conversation.id:             1
```

> [!IMPORTANT]
> **What it means.** Five turns produced five `invocation` roots with five
> different trace ids. A trace does not span a conversation — it spans one
> request. What ties the five together is `gen_ai.conversation.id`, an attribute
> equal to the session id, carried on the `invoke_agent` span of every turn.

So there are two keys, and they answer two questions:

| Key | Groups | You use it to |
|---|---|---|
| `trace_id` | the spans of one turn | open a single request's tree |
| `gen_ai.conversation.id` | the turns of one session | pull a whole conversation back together |

The dev UI hides this by keying its **Trace** tab on the session, so it looks
like one conversation is one trace. In Cloud Trace there is no such grouping for
free: to see a whole conversation you filter on the `gen_ai.conversation.id`
attribute, which is what [4.2](../part-4/index.md) does.

## Deep dives

### The ids on a turn, and where each appears

A turn carries several ids, and it helps to know which is which
(`tracing.py:622-627`):

| Id | Scope | Lives as |
|---|---|---|
| `trace_id` | one turn | the span context on every span |
| `gen_ai.conversation.id` | the session | an attribute (equals the session id) |
| `invocation_id` | one turn | `gcp.vertex.agent.invocation_id` |
| `event_id` | one ADK event | `gcp.vertex.agent.event_id` |

`trace_id` is the one Part 3 stamps on log lines to join logs to spans;
`gen_ai.conversation.id` is the one Part 4 filters on to find a user's session.
The other two identify a turn and an event inside ADK's own model and rarely
leave it.
