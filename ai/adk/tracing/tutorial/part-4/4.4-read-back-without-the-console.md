# 4.4 · Read-back without the console

*Part 4 · Consume*

> [!NOTE]
> **Why you are here.** Every cloud capture in this tutorial came from
> `trace/get_trace.sh`. This page opens it, and its sibling
> `trace/list_traces.sh`, so you can pull a tree into a script, a CI check, or a
> support ticket.

Both scripts call the Cloud Trace v1 REST API with `curl` and your Application
Default Credentials. The `baseline` scenario gives them one trace to read.

**Step 1 — Run one turn.**

Start the correlated server from Part 3 in one shell.

**Command:**

```bash
source env.sh
.venv/bin/python examples/03_correlated_server.py
```

In a second shell, send one London turn.

**Command:**

```bash
source env.sh
export HOST=http://localhost:8080
export ENDPOINT=chat
./load/turns.sh baseline 1
```

**Expected output:**

```console
baseline        turn   1  8.06s  trace=41e103ad363024ebd258ef42ce05f762
```

**Step 2 — Read the tree.**

**Command:**

```bash
./trace/get_trace.sh 41e103ad363024ebd258ef42ce05f762
```

**Expected output:** run within seconds of the turn.

```console
trace not indexed yet (attempt 1/12), retrying in 10s...
trace 41e103ad363024ebd258ef42ce05f762  (7 spans)
invocation                               7.390s
  invoke_agent weather_agent               7.384s
    call_llm                                 5.087s
      generate_content gemini-3.7-flash        5.085s
      execute_tool get_weather                 0.001s
    call_llm                                 2.271s
      generate_content gemini-3.7-flash        2.270s
```

> [!IMPORTANT]
> **What it means.** This is the seven-span tree from
> [1.1](../part-1/1.1-the-tree-you-already-have.md), with `execute_tool` under
> the first `call_llm`, the same tree the Trace Explorer waterfall draws. The
> first request got a 404 because the trace was not indexed yet; the script
> retries every 10 s for two minutes instead of failing.

The script makes one call, `GET /v1/projects/PROJECT/traces/TRACE_ID`, and
renders the flat span list it returns. The fields it reads:

| field | value | what it is |
|---|---|---|
| `spanId` | `3615242328282881677` | The span's id, as a **decimal** uint64. In hex, as a log entry's `spanId` writes it, it is `322bebbe4241de8d`. |
| `parentSpanId` | `4726224848304331767` | The parent's id, also decimal. Absent on the root. The script builds the tree from these two. |
| `name` | `execute_tool get_weather` | The span name. |
| `startTime` / `endTime` | RFC 3339 timestamps | The script prints their difference. |
| `labels` | `gen_ai.tool.name`, `service.name`, … | The span's attributes plus resource attributes, all as strings. |

**Step 3 — Find traces by attribute.**

`list_traces.sh` takes a v1 filter and a look-back window in minutes. The
`invoke_agent` span carries the session id as `gen_ai.conversation.id`, so filter
on the one from this turn.

**Command:**

```bash
./trace/list_traces.sh 'gen_ai.conversation.id:42e24c76-65f3-43ce-93bc-4f5c500d95f1' 30
```

<!-- Captured with trace/list_traces.sh patched to pass the curl response as an
argument (see verification/stage4-44-read-back.txt); the committed script reads
an empty stdin. Remove this note once the fix lands. -->

**Expected output:**

```console
(1 traces)
41e103ad363024ebd258ef42ce05f762  7 spans
```

> [!IMPORTANT]
> **What it means.** One conversation, one turn, one trace. A label filter is
> `key:value` on any span in the trace. Span names need quotes when they
> contain a space: `'span:"execute_tool get_weather"'` matches, and the
> unquoted form matches nothing. See
> [What does the v1 filter accept?](#what-does-the-v1-filter-accept)

**Step 4 — Stop the server.**

Press **Ctrl+C** in the server's shell. The page created no cloud resources.

[4.5](4.5-traces-logs-metrics-rows.md) sets traces beside logs, metrics, and
rows, and names the id that joins each pair.

## Deep dives

### What does the v1 filter accept?

From the [trace filters](https://docs.cloud.google.com/trace/docs/trace-filters)
doc. Terms are space-separated and case-sensitive, and the syntax does not apply
to the Trace Explorer page.

| Filter | Matches a trace with |
|---|---|
| `root:invocation` | a root span whose name starts with `invocation` |
| `+root:invocation` | a root span named exactly `invocation` |
| `span:"execute_tool get_forecast"` | any span whose name starts with that |
| `gen_ai.tool.name:get_weather` | a span carrying that label value |
| `latency:5s` | a duration of at least 5 s |

Pass a filter every time. An unfiltered list can return an empty first page with
a `nextPageToken`, and the script reads one page only.

### Why v1, when ADK writes over OTLP?

ADK exports through the Telemetry API (`telemetry.googleapis.com`), the OTLP
endpoint Google
[recommends for writing](https://docs.cloud.google.com/trace/docs/migrate-to-otlp-endpoints).
You read them back through the Cloud Trace API, and v1 returns OTLP-written
spans like any others. This tutorial's first cloud run confirmed it: all seven
spans came back through v1 with the full parent chain. The ingestion delay
varies; that run waited 90 to 120 s, this one about 20 s.

### How long can you read a trace back?

Thirty days. Spans in the `_Trace` bucket are retained for 30 days
([quotas and limits](https://docs.cloud.google.com/trace/docs/quotas)), so a
trace id in a support ticket stops resolving after a month. Reads also have a
quota of 300 per minute per project. A 429 body contains `"error"`, so
`get_trace.sh` retries it like the indexing 404.
