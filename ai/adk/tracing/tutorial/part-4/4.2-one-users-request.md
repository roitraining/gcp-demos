# 4.2 · One user's request

*Part 4 · Consume*

> [!NOTE]
> **Why you are here.** A user reports a bad answer. This page finds their whole
> conversation by session id, then one turn by the trace id the server returned.

[1.5](../part-1/1.5-a-trace-per-turn.md) showed the two keys: a trace is one turn,
and `gen_ai.conversation.id` ties a session's turns together. Now you use both to
search Cloud Trace.

**Step 1 — Run a five-turn conversation.** The `multi-turn` scenario reuses one
session, which needs the `/run` and sessions endpoints of `adk web`. Start it with
export on, as in [2.1](../part-2/2.1-adk-web-otel-to-cloud.md):

**Command:**

```bash
source env.sh
adk web --otel_to_cloud .
```

In a second terminal, fire five turns. Point `turns.sh` at `adk web` explicitly, in
case `HOST` and `ENDPOINT` are still set from 4.1:

**Command:**

```bash
source env.sh
export HOST=http://localhost:8000
export ENDPOINT=run
./load/turns.sh multi-turn 5
```

**Expected output:**

```console
multi-turn      turn   1  http=200  5.69s  session=84b1d220-ef3a-4ad2-9cf0-a260e56ab34f
multi-turn      turn   2  http=200  5.17s  session=84b1d220-ef3a-4ad2-9cf0-a260e56ab34f
multi-turn      turn   3  http=200  5.81s  session=84b1d220-ef3a-4ad2-9cf0-a260e56ab34f
multi-turn      turn   4  http=200  4.92s  session=84b1d220-ef3a-4ad2-9cf0-a260e56ab34f
multi-turn      turn   5  http=200  5.72s  session=84b1d220-ef3a-4ad2-9cf0-a260e56ab34f
```

> [!IMPORTANT]
> **What it means.** Five turns, one session id. That session id is what a
> support ticket can carry when the user cannot give you anything else.

**Step 2 — List the conversation.** Wait about two minutes for indexing, then ask
the Trace v1 API for every trace whose spans carry the session id. Replace the
value with the session your run printed:

**Command:**

```bash
export SESSION_ID=84b1d220-ef3a-4ad2-9cf0-a260e56ab34f
curl -s -G "https://cloudtrace.googleapis.com/v1/projects/$PROJECT_ID/traces" \
  -H "Authorization: Bearer $(gcloud auth application-default print-access-token)" \
  --data-urlencode "filter=gen_ai.conversation.id:$SESSION_ID" \
  | grep traceId
```

**Expected output:**

```console
      "traceId": "3197d337d895d5c2e9bec80888b01327"
      "traceId": "54b58646bb1b174b759829688268218e"
      "traceId": "ae9e769d9a666cd774c858d4471c3d6e"
      "traceId": "b27dd13b8d601abf6ec89fd2bf262c14"
      "traceId": "e1612d7caee028fa7e1d96930de00e84"
```

> [!IMPORTANT]
> **What it means.** Exactly five traces, one per turn, found by an attribute
> rather than a trace id. The list is ordered by id, not time. A made-up session
> id returns none. Empty output with no error usually means the API's per-minute
> read quota said 429; run it again.

The console does the same with a filter
([Trace Explorer filter bar](https://docs.cloud.google.com/trace/docs/finding-traces#use-filter-bar)).
These console steps follow Google's docs; the command above confirms the same
fact:

- Open **Trace Explorer**.
- Click **Add filter**, then **Add attribute filter**.
- Set the key to `gen_ai.conversation.id` and the value to your session id.

Stop `adk web` with Ctrl+C.

**Step 3 — Find one turn by the id the server returned.** The
[examples/03_correlated_server.py](../../examples/03_correlated_server.py)
server's `/chat` puts the trace id in its response, so `turns.sh` prints it:

**Command:**

```bash
source env.sh
python examples/03_correlated_server.py
```

In the second terminal, send one turn, then read back the trace id it printed in
place of the one shown:

**Command:**

```bash
export HOST=http://localhost:8080
export ENDPOINT=chat
./load/turns.sh baseline 1
```

```bash
./trace/get_trace.sh c08c0533c67260b367d03af4ce8a5cb3
```

**Expected output:**

```console
baseline        turn   1  6.21s  trace=c08c0533c67260b367d03af4ce8a5cb3
trace c08c0533c67260b367d03af4ce8a5cb3  (7 spans)
invocation                               5.814s
  invoke_agent weather_agent               5.807s
    call_llm                                 2.072s
      generate_content gemini-3.7-flash        2.070s
      execute_tool get_weather                 0.001s
    call_llm                                 3.706s
      generate_content gemini-3.7-flash        3.705s
```

> [!IMPORTANT]
> **What it means.** The id in the response opens exactly the user's turn, with no
> time window or filter to guess. See [Which id goes in the ticket?](#which-id-goes-in-the-ticket)

In the console
([search for a trace](https://docs.cloud.google.com/trace/docs/finding-traces#filter_traces),
[Find in Trace](https://docs.cloud.google.com/trace/docs/finding-traces#search-trace)),
following Google's docs:

- Click **Search for trace** in the **Trace Explorer** toolbar.
- Paste the trace id. The trace details panel opens.
- Type `London` in **Find in Trace** to jump to spans whose attributes mention it.

**Step 4 — Tear down.** Stop the server with Ctrl+C, then:

**Command:**

```bash
unset ADK_CAPTURE_MESSAGE_CONTENT_IN_SPANS HOST ENDPOINT SESSION_ID TRACE_ID
```

[4.3](4.3-the-failed-step.md) finds the turn that failed and reads why.

## Deep dives

### Which id goes in the ticket?

Both, because they answer different questions:

| Key | Where the user gets it | Opens |
|---|---|---|
| trace id | your response body, as `03` returns it | one turn's tree, by **Search for trace** |
| session id | your app's session, `gen_ai.conversation.id` | every turn, by **Add attribute filter** |

Return the trace id with every response and show it in the UI or error page, so
a ticket can quote it. When the user has only "it went wrong this afternoon",
the session id still finds the conversation, and its five traces narrow to the
turn. `adk web`'s `/run` returns neither, which is why Step 1 read the session
id from `turns.sh` and Step 3 switched to `03`.

### Can you still find the user with content off?

Yes. The prompt sits on each `call_llm` span as `gcp.vertex.agent.llm_request`.
On the fifth turn of the Step 1 conversation (`e1612d7c…` in Step 2's list),
it holds the full prompt:

**Command:**

```bash
export TRACE_ID=e1612d7caee028fa7e1d96930de00e84
curl -s "https://cloudtrace.googleapis.com/v1/projects/$PROJECT_ID/traces/$TRACE_ID" \
  -H "Authorization: Bearer $(gcloud auth application-default print-access-token)" \
  | grep -oE '"gcp.vertex.agent.(llm_request|tool_call_args)": ".{0,60}'
```

**Expected output:**

```console
"gcp.vertex.agent.llm_request": "{\"model\": \"gemini-3.7-flash\", \"config\": {\"http_option
"gcp.vertex.agent.llm_request": "{}",
"gcp.vertex.agent.tool_call_args": "{\"city\": \"London\"}",
"gcp.vertex.agent.llm_request": "{\"model\": \"gemini-3.7-flash\", \"config\": {\"http_option
```

(The `{}` is on the tool span, which never carries the prompt.) Google
documents an **Inputs/Outputs** tab for GenAI spans
([generative AI events](https://docs.cloud.google.com/trace/docs/finding-traces#generative-events));
this tutorial has not checked how it renders these attributes. Now stop the
`03` server, restart it with content capture off, and send one turn with
`./load/turns.sh baseline 1` from the second terminal:

**Command:**

```bash
export ADK_CAPTURE_MESSAGE_CONTENT_IN_SPANS=false
python examples/03_correlated_server.py
```

Wait two minutes, then read the new turn's content attributes, replacing the
trace id with the one it printed:

**Command:**

```bash
export TRACE_ID=d6bb0f3641be911bbd812cba28d8b961
curl -s "https://cloudtrace.googleapis.com/v1/projects/$PROJECT_ID/traces/$TRACE_ID" \
  -H "Authorization: Bearer $(gcloud auth application-default print-access-token)" \
  | grep -E 'llm_request|llm_response|tool_call_args|conversation.id'
```

**Expected output:**

```console
        "gen_ai.conversation.id": "b1e59e35-7b63-42ce-954b-cabae89849ce",
        "gcp.vertex.agent.llm_request": "{}",
        "gcp.vertex.agent.llm_response": "{}",
        "gen_ai.conversation.id": "b1e59e35-7b63-42ce-954b-cabae89849ce",
        "gcp.vertex.agent.llm_request": "{}",
        "gcp.vertex.agent.tool_call_args": "{}",
        "gcp.vertex.agent.llm_response": "{}",
        "gcp.vertex.agent.llm_response": "{}",
        "gcp.vertex.agent.llm_request": "{}",
        "gen_ai.conversation.id": "b1e59e35-7b63-42ce-954b-cabae89849ce",
```

> [!IMPORTANT]
> **What it means.** The content is gone and the keys stayed. On the fifth
> turn above, the same `llm_request` held the full prompt and `tool_call_args`
> read `{"city": "London"}`. You can still find this user's session and turn;
> you just cannot read what they said.

Stop the server with Ctrl+C and run Step 4's `unset` line.
