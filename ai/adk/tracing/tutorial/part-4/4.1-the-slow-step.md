# 4.1 · The slow step

*Part 4 · Consume*

> [!NOTE]
> **Why you are here.** Forecast turns feel slower than weather turns, and the
> forecast tool calls a slow dependency. This page puts both kinds of turn under
> load and asks the trace whether that dependency is to blame.

You run `slow-tool` with the 1.6 custom span on, so the dependency's time has
its own `fetch_forecast` span, and compare durations across the run before
opening one trace.

**Step 1 — Start the server with the custom span on.**

**Command:**

```bash
source env.sh
export TUTORIAL_CUSTOM_SPAN=1
python examples/03_correlated_server.py
```

**Expected output:**

```console
Exporting spans and bridged logs to Cloud in project 'jwd-gcp-demos'.
INFO:     Application startup complete.
```

**Step 2 — Generate load.** In a second terminal, send five `baseline` turns and
twenty `slow-tool` turns, half of them forecasts.

**Command:**

```bash
source env.sh
export HOST=http://localhost:8080
export ENDPOINT=chat
./load/turns.sh baseline 5
./load/turns.sh slow-tool 20
```

**Expected output:** trimmed.

```console
baseline        turn   1  8.10s  trace=b43d1806d570087130db4983d3f0f12a
baseline        turn   2  5.16s  trace=5b61975fbe3d3289c73090bbd4556a9c
…
slow-tool       turn   1  6.24s  trace=30e0a720f64638cba2fd9d2da4ef2096
slow-tool       turn   2  7.32s  trace=f430f9b62e0404dc0712a97acfb8e457
…
slow-tool       turn  18  8.77s  trace=63c8dcc42e6f0a18eba78f1b3e085a44
slow-tool       turn  19  4.92s  trace=34aa64bda9e802b968debbdd8a0727e7
slow-tool       turn  20  6.42s  trace=36904fbfa834ddac97c71b3ef003c3e6
```

**Step 3 — List the forecast traces.** Allow about two minutes for ingestion.
Set `START` to a UTC time just before Step 2. The Trace v1 filter splits terms on
spaces, so the span name goes in double quotes (`%22` in the URL).

**Command:**

```bash
export START=2026-10-02T17:21:50Z
curl -s -H "Authorization: Bearer $(gcloud auth application-default print-access-token)" \
  "https://cloudtrace.googleapis.com/v1/projects/$PROJECT_ID/traces?view=MINIMAL&startTime=$START&pageSize=100&filter=span:%22execute_tool%20get_forecast%22" \
  | grep traceId
```

**Expected output:** trimmed.

```console
      "traceId": "2c08a6b0715a19f56bcd8d438d05f156"
      "traceId": "36904fbfa834ddac97c71b3ef003c3e6"
      "traceId": "63c8dcc42e6f0a18eba78f1b3e085a44"
…
      "traceId": "f430f9b62e0404dc0712a97acfb8e457"
```

> [!IMPORTANT]
> **What it means.** All ten forecast turns came back. Unquoted,
> `span:execute_tool get_forecast` matches nothing. The list gives ids, not
> durations.

**Step 4 — Compare span durations across the run.** In the console:

- Open **Trace Explorer**.
- Set **OpenTelemetry service** to `adk-tracing`.
- Set **Chart view** to **Span duration (percentile)**.
- Open the **Grouped** tab, which groups spans by name.
- Sort by the duration header.
- Add a **Span name** filter for `execute_tool get_forecast` to chart the tool alone.

See [Find and explore traces](https://docs.cloud.google.com/trace/docs/finding-traces).
These console steps follow Google's docs; the statistics below, computed from
this run's Trace v1 read-back, confirm the same ranking:

| Span name | Spans | p50 | p95 |
|---|---|---|---|
| `invoke_agent weather_agent` | 25 | 5.70 s | 7.78 s |
| `call_llm` | 50 | 2.92 s | 4.52 s |
| `generate_content gemini-3.7-flash` | 50 | 2.84 s | 4.08 s |
| `execute_tool get_forecast` | 10 | 1.06 s | 1.45 s |
| `fetch_forecast` | 10 | 1.06 s | 1.45 s |
| `execute_tool get_weather` | 15 | 0.001 s | 0.001 s |

> [!IMPORTANT]
> **What it means.** Ranked by duration, the model spans sit above the tool, so
> the tool is not the biggest step. Read `generate_content`, not `call_llm`: the
> first `call_llm` parents the tool, so its time includes it. The tool is the
> step that differs. The median forecast turn took 1.67 s longer than the
> median weather turn, and the median tool call took 1.06 s; the rest is model
> time, which varies turn to turn. One slow model call can swamp the tool's
> second, so compare medians, not means. The tool owned a median 16% of forecast
> `invoke_agent` time, 24% at most.

**Step 5 — Read the slowest turn and the slowest tool call.**

**Command:**

```bash
trace/get_trace.sh 63c8dcc42e6f0a18eba78f1b3e085a44
trace/get_trace.sh 36904fbfa834ddac97c71b3ef003c3e6
```

**Expected output:**

```console
trace 63c8dcc42e6f0a18eba78f1b3e085a44  (8 spans)
invocation                               8.517s
  invoke_agent weather_agent               8.516s
    call_llm                                 4.048s
      generate_content gemini-3.7-flash        2.958s
      execute_tool get_forecast                1.087s
        fetch_forecast                           1.086s
    call_llm                                 4.464s
      generate_content gemini-3.7-flash        4.463s
trace 36904fbfa834ddac97c71b3ef003c3e6  (8 spans)
invocation                               6.075s
  invoke_agent weather_agent               6.074s
    call_llm                                 4.403s
      generate_content gemini-3.7-flash        2.927s
      execute_tool get_forecast                1.474s
        fetch_forecast                           1.472s
    call_llm                                 1.667s
      generate_content gemini-3.7-flash        1.665s
```

> [!IMPORTANT]
> **What it means.** The slowest turn (8.5 s) was slow because its second model
> call took 4.5 s; its tool took an ordinary 1.1 s. The slowest tool call
> (1.47 s) sat in a 6.1 s turn. In both, `fetch_forecast` covers its
> `execute_tool` span to within 2 ms, so the time inside the tool is the
> dependency, not your code around it.

To see the same tree as a waterfall:

- In **Trace Explorer**, search for trace `63c8dcc42e6f0a18eba78f1b3e085a44`.
- Open the trace details panel.
- Expand the first `call_llm` and select `fetch_forecast`.
- Open **Attributes** and find `forecast.days`, which the read-back shows as `3`.

**Step 6 — Stop the server.** Press Ctrl+C in the server terminal, then clear
the variables this page set, which would change how 4.2 and 4.3 behave:

**Command:**

```bash
unset TUTORIAL_CUSTOM_SPAN HOST ENDPOINT START
```

The answer: the dependency explains why forecast turns are slower, but the model
owns most of every turn. [4.2](4.2-one-users-request.md) moves from many turns
to one user's.

## Deep dives

### Can the API rank traces by duration?

Only by the root span. The v1 list takes `orderBy=duration desc` and a
`latency:7s` filter term; on this run they put `63c8dcc4…` (8.517 s) first. For
per-span percentiles, use the **Grouped** tab.
