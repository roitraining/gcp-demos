# 4.3 · The failed step

*Part 4 · Consume*

> [!NOTE]
> **Why you are here.** A user says the agent "had no data." This page finds the
> step that failed, the WARNING it logged, and the answer the user got, all from
> one trace. It is the `classified-error` scenario that 1.4 set up and 3.2
> correlated.

You run the
[examples/03_correlated_server.py](../../examples/03_correlated_server.py)
server from 3.2 with the error hook on, send one failing turn,
and read it back three ways: by status, by log, and by answer.

**Step 1 — Start the server with the hook on.**

**Command:**

```bash
source env.sh
export TUTORIAL_CLASSIFY_ERRORS=1
.venv/bin/python examples/03_correlated_server.py
```

**Expected output:**

```console
Exporting spans and bridged logs to Cloud in project 'jwd-gcp-demos'.
INFO:     Application startup complete.
```

**Step 2 — Send the failing turn.** In a second terminal:

**Command:**

```bash
source env.sh
export HOST=http://localhost:8080
export ENDPOINT=chat
./load/turns.sh classified-error 1
```

**Expected output:**

```console
classified-error turn   1  5.97s  trace=92972bbfa279dff73a557b8aa0c6a036
```

The turn succeeded as HTTP. Nothing in this line says a step failed.

**Step 3 — Find the failed span.** Allow about two minutes for ingestion. In
the console:

- Open **Trace Explorer**.
- In **Span filters**, set **Span status** to error.
- Open the trace and select `execute_tool get_weather`.
- Open the **Attributes** tab and find `error.type`.

These console steps follow Google's docs, which say the latency bar's color
reflects the span's status and that **Attributes** lists the span's attributes
([Find and explore traces](https://docs.cloud.google.com/trace/docs/finding-traces)).
The commands below confirm the same facts.
From a script, the v1 API has no status filter, so filter on the attribute
instead:

**Command:**

```bash
curl -s -H "Authorization: Bearer $(gcloud auth application-default print-access-token)" \
  "https://cloudtrace.googleapis.com/v1/projects/$PROJECT_ID/traces?filter=error.type:lookup_failed"
```

**Expected output:**

```console
{
  "traces": [
    {
      "projectId": "jwd-gcp-demos",
      "traceId": "92972bbfa279dff73a557b8aa0c6a036"
    }
  ]
}
```

> [!IMPORTANT]
> **What it means.** One trace in the window carries `error.type=lookup_failed`,
> on `execute_tool get_weather` alone; `call_llm`, `invoke_agent`, and
> `invocation` carry none. A `returned-error` turn without the hook
> (trace `a3439fbb…`, same Atlantis prompt, same WARNING) matched nothing here:
> its tool span is UNSET with no `error.type`. That is why 1.4 taught the hook.

**Step 4 — Read what the step said.** Replace the trace id with the one your
turn printed, here and in Step 5:

**Command:**

```bash
gcloud logging read 'trace="projects/'"$PROJECT_ID"'/traces/92972bbfa279dff73a557b8aa0c6a036" AND severity=WARNING' \
  --project="$PROJECT_ID"
```

**Expected output:** trimmed to the fields that matter:

```console
logName: projects/jwd-gcp-demos/logs/adk-tracing
severity: WARNING
spanId: cd7c72f2a7b0ab5c
textPayload: "weather lookup failed for 'Atlantis': no data"
trace: projects/jwd-gcp-demos/traces/92972bbfa279dff73a557b8aa0c6a036
traceSampled: true
```

> [!IMPORTANT]
> **What it means.** This is the WARNING 3.2 captured, under the same span name.
> `cd7c72f2a7b0ab5c` is `execute_tool get_weather`; the v1 API reports that span
> as decimal `14806836061408373596`, which is the same number. In the console,
> the selected span's **Logs & Events** tab lists entries whose trace and span
> ids match it ([docs](https://docs.cloud.google.com/trace/docs/viewing-details)),
> so the WARNING sits beside `error.type`.

**Step 5 — Read what the user was told.**

**Command:**

```bash
gcloud logging read 'trace="projects/'"$PROJECT_ID"'/traces/92972bbfa279dff73a557b8aa0c6a036" AND logName:"gen_ai.choice"' \
  --project="$PROJECT_ID"
```

**Expected output:** trimmed:

```console
jsonPayload:
  content: <elided>
  finish_reason: STOP
logName: projects/jwd-gcp-demos/logs/gen_ai.choice
spanId: 5072579ecc9b8c06
---
jsonPayload:
  content: <elided>
  finish_reason: STOP
logName: projects/jwd-gcp-demos/logs/gen_ai.choice
spanId: bf0a160bd3419992
```

> [!IMPORTANT]
> **What it means.** Two model calls, two choices. `5072579ecc9b8c06` is the
> second `generate_content`, the one after the tool, so it holds the reply. Its
> content is `<elided>` because log-event content is off by default (1.3). The
> words are on the span instead: the second `call_llm`'s
> `gcp.vertex.agent.llm_response` reads "I do not have weather data for
> Atlantis." The tool failed, and the model told the user so.

**Step 6 — Tear down.** Stop the server with Ctrl+C, then:

**Command:**

```bash
unset TUTORIAL_CLASSIFY_ERRORS
```

Before you change `get_weather`, save this trace as a reference for how the
failure should look. See
[How do I keep a failure as a reproduction?](#how-do-i-keep-a-failure-as-a-reproduction) Next, 4.4 explains the
read-back calls every capture in this tutorial used.

## Deep dives

### How do I keep a failure as a reproduction?

A diagnosed failure is worth keeping as a run record: the command that produced
it, the trace id, a filter that returns its evidence, and what the span should
say. This run's record is
[verification/classified-error-92972bbfa279dff73a557b8aa0c6a036.txt](../../verification/classified-error-92972bbfa279dff73a557b8aa0c6a036.txt).
Its filter adds the span id to the Step 4 filter, so it returns exactly the
WARNING under the failed span:

**Command:**

```bash
gcloud logging read 'trace="projects/'"$PROJECT_ID"'/traces/92972bbfa279dff73a557b8aa0c6a036" AND spanId="cd7c72f2a7b0ab5c" AND severity=WARNING' \
  --project="$PROJECT_ID" \
  --freshness=30d
```

**Expected output:** trimmed:

```console
severity: WARNING
spanId: cd7c72f2a7b0ab5c
textPayload: "weather lookup failed for 'Atlantis': no data"
```

After the next change to the tool, rerun `turns.sh classified-error 1` and
compare the new trace with the record: same status and `error.type` on
`execute_tool get_weather`, same WARNING under it. No harness, no framework.
The saved command names this run's trace and span ids, so it returns nothing
once they age out ([How long can you read a trace
back?](4.4-read-back-without-the-console.md#how-long-can-you-read-a-trace-back)).
Swap in the new ids each run; the expectations stay the same.
