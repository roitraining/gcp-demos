# 1.1 · Your first datapoint

*Part 1 · What a metric is*

> [!NOTE]
> **Why you are here.** ADK records metrics from the moment your agent runs, but
> nothing prints until you install a reader. This page installs the simplest one
> and shows you the first datapoint.

The `baseline` scenario is one weather question in a fresh session. The script
[examples/01_console_metrics.py](../../examples/01_console_metrics.py) installs a
console metric reader, asks it, and flushes. The reader prints every histogram
ADK recorded during the turn.

**👉 Do this.**

**Command:**

```bash
.venv/bin/python examples/01_console_metrics.py
```

The agent's answer prints to the console, and the script writes the metrics JSON
to `out/metrics.json`. Open it in your editor to read it; the dump is too long for
the terminal. In VS Code:

```bash
code out/metrics.json
```

**Expected output:** each metric carries `description`, timestamps,
`bucket_counts`, `explicit_bounds`, `min`, `max`, and more. Here is the first
metric with only the fields this page uses:

```console
AGENT: The weather in London is currently 15°C and drizzling.

{
    "resource_metrics": [
        {
            "resource": { "attributes": { "service.name": "adk-metrics" } },
            "scope_metrics": [
                {
                    "scope": { "name": "gcp.vertex.agent", "version": "2.8.0" },
                    "metrics": [
                        {
                            "name": "gen_ai.execute_tool.duration",
                            "unit": "s",
                            "data": { "data_points": [ {
                                "attributes": {
                                    "gen_ai.agent.name": "weather_agent",
                                    "gen_ai.tool.name": "get_weather",
                                    "gen_ai.tool.type": "StatusAwareTool"
                                },
                                "count": 1,
                                "sum": 0.002
                            } ] }
                        }
                    ]
                }
            ]
        }
    ]
}
```

Five more metrics follow in the same block, each with the same shape. Reading the
`count` and `sum` off all six gives this summary:

| Metric | count | sum |
|---|---|---|
| `gen_ai.execute_tool.duration` | 1 | 0.002 s |
| `gen_ai.client.operation.duration` | 2 | 3.22 s |
| `gen_ai.client.token.usage` (input) | 2 | 713 tokens |
| `gen_ai.client.token.usage` (output) | 2 | 94 tokens |
| `gen_ai.invoke_agent.duration` | 1 | 3.26 s |
| `gen_ai.invoke_agent.inference_calls` | 1 | 2 |
| `gen_ai.invoke_agent.tool_calls` | 1 | 1 |

> [!IMPORTANT]
> **What it means.** One turn recorded into six metric names. There is no
> `gen_ai.invoke_workflow.duration`: a single agent never invokes a workflow, so
> that seventh metric stays silent until [1.5](1.5-workflow-grain-metrics.md).
> `gen_ai.client.token.usage` appears twice, once for input and once for output,
> because the token type is an attribute that splits it into two series.

> [!NOTE]
> Token counts vary run to run because the model does, so your numbers will
> differ from these by a little.

## What you are looking at

Every datapoint has the same shape. Here is the input token-usage datapoint from
the summary above, with its full field set:

```console
{
  "name": "gen_ai.client.token.usage",
  "unit": "{token}",
  "data_points": [
    {
      "attributes": {
        "gen_ai.agent.name": "weather_agent",
        "gen_ai.request.model": "gemini-3.7-flash",
        "gen_ai.token.type": "input"
      },
      "count": 2,
      "sum": 713,
      "bucket_counts": [0, 0, 0, 0, 0, 0, 0, 0, 2, 0, 0, 0, 0, 0, 0, 0],
      "explicit_bounds": [0.0, 5.0, 10.0, 25.0, 50.0, 75.0, 100.0, 250.0,
                          500.0, 750.0, 1000.0, 2500.0, 5000.0, 7500.0, 10000.0]
    }
  ]
}
```

| field | value | what it is |
|---|---|---|
| `attributes` | agent, model, `token.type` | The dimensions that split this metric into separate series. Same metric, one datapoint per unique attribute set. |
| `count` | `2` | How many values were recorded into this series. Here, the two model calls in the turn. |
| `sum` | `713` | The values added up. For token usage, the tokens themselves. |
| `bucket_counts` | `[..., 2, ...]` | How many recorded values fell into each bucket. Both calls landed in one bucket, so it holds a `2`. This is what makes it a histogram, not a single number. |
| `explicit_bounds` | `[0.0, 5.0, ...]` | The bucket edges. The bucket holding the `2` spans 250 to 500 tokens. |

> [!IMPORTANT]
> **What it means: `count` and `sum` do not mean the same thing on every
> metric.** On `gen_ai.client.token.usage`, `sum` is the tokens (713) and `count`
> is the model calls that reported them (2), so `sum ÷ count` is tokens per call.
> On `gen_ai.invoke_agent.inference_calls`, `sum=2` is the model calls and
> `count=1` is the turn: this one turn ran the model twice, once to decide to call
> `get_weather` and once to phrase the answer from the result. Reach for `count`
> as a request denominator on the token metric and you would be counting model
> calls, not turns.

Each metric answers a different operator question. This mapping holds for the
rest of the tutorial:

| Metric | `count` is | `sum` is | Answers |
|---|---|---|---|
| `gen_ai.invoke_agent.duration` | turns | total turn seconds | How slow is a turn? |
| `gen_ai.client.operation.duration` | model calls | total model seconds | How slow is the model? |
| `gen_ai.execute_tool.duration` | tool calls | total tool seconds | How slow is a tool? |
| `gen_ai.client.token.usage` | model calls | tokens | How many tokens per call? |
| `gen_ai.invoke_agent.inference_calls` | turns | model calls | How many model calls per turn? |
| `gen_ai.invoke_agent.tool_calls` | turns | tool calls | How many tool calls per turn? |

`count` and `sum` give you totals and averages. The `bucket_counts` give you
something neither can: the shape of the values. [1.2](1.2-reading-a-histogram.md)
reads them.

## Deep dives

### Why does the script need to flush?

ADK installs the `MeterProvider` with `shutdown_on_exit=False` so that points are
not collected too close together (`telemetry/setup.py:96-103`). A script that
exits within the export interval of its last turn would export nothing. The
example calls `metrics.get_meter_provider().force_flush()` before returning,
which drains the reader and returns `True`. Without that line the console stays
empty even though every metric was recorded. A long-running server does not need
this; its reader keeps exporting on the interval.
