# 3.4 · Tokens and cost

*Part 3 · Consume — signals from histograms*

> [!NOTE]
> **Why you are here.** Tokens are the bill. This page reads token rate by type
> and watches input tokens climb across one session while output stays flat, then
> shows why the average hides the climb.

The `growing-context` scenario runs N turns in one session instead of N fresh
ones, so each model call carries the whole conversation so far. Input tokens per
call should rise turn over turn; output tokens should not. You read
`gen_ai.client.token.usage`, split by `gen_ai.token.type`, over PromQL. Queries
live in [queries/tokens.promql](../../queries/tokens.promql).

**Step 1 — Drive the scenario.**

**Command:**

```bash
load/turns.sh growing-context 20
```

**Expected output:**

```console
growing-context turn   1  http=200  3.79s
growing-context turn   2  http=200  2.95s
growing-context turn   3  http=200  3.61s
...
growing-context turn  19  http=200  2.93s
growing-context turn  20  http=200  3.13s
waiting 10s for the final export interval...
good to go — the series are in Cloud Monitoring
```

**Step 2 — Read token rate by type.** The `_sum` of the token histogram, split by
type, is total tokens; `rate() * 60` is tokens per minute:

```
sum by ("gen_ai.token.type") (
  rate({"gen_ai.client.token.usage_sum"}[5m])
) * 60
```

**Command:**

```bash
export PROJECT=jwd-gcp-demos
export TOKEN=$(gcloud auth application-default print-access-token)
export QUERY='sum by ("gen_ai.token.type") (rate({"gen_ai.client.token.usage_sum"}[5m])) * 60'
curl -s -H "Authorization: Bearer $TOKEN" \
  --data-urlencode "query=$QUERY" \
  "https://monitoring.googleapis.com/v1/projects/$PROJECT/location/global/prometheus/api/v1/query"
```

**Expected output:**

```console
gen_ai.token.type=input    14461.6
gen_ai.token.type=output     347.0
```

Input runs about **42×** output. Over the whole session the totals were 72,308
input tokens against 1,735 output, across 120 model calls.

**Step 3 — Read input tokens per call across the session.** The mean, `sum` ÷
`count`, flattens the climb into one number. Read the raw `_sum` and `_count` over
a short window stepped across the run to see input per call rise:

**Command:**

```bash
export QUERY='sum(rate({"gen_ai.client.token.usage_sum", "gen_ai.token.type"="input"}[1m])) / sum(rate({"gen_ai.client.token.usage_count", "gen_ai.token.type"="input"}[1m]))'
curl -s -H "Authorization: Bearer $TOKEN" \
  --data-urlencode "query=$QUERY" \
  "https://monitoring.googleapis.com/v1/projects/$PROJECT/location/global/prometheus/api/v1/query"
```

**Expected output:**

Stepped across the run with `query_range` (`step=30s`), input per call against
output per call:

```console
  time       input/call   output/call
  05:28:00        366.2          14.1
  05:28:30        381.8          14.3
  05:29:00        638.3          14.9
  05:29:30       1129.4          15.1
  05:30:00       1405.4          15.1
  05:30:30       1720.1          15.0
```

Input per call rises **4.7×** across twenty turns — 366 to 1720 — while output
per call sits flat at 14–15. The mean over the whole run is one number in the
middle of that climb, matching no individual turn.

> [!IMPORTANT]
> **What it means.** Input per call climbs because every turn re-sends the growing
> transcript; output stays flat because each answer is about the same size. The
> mean over the whole run would report one middling number and hide the climb, so
> read the rate over a short window when you want the trend. These are tokens, not
> dollars: multiply the per-type `sum` by your model's per-token price for a cost
> figure. Whether any of that input was served from cache is not in the metric;
> that shows up only in the rows (Part 4).

3.5 puts these four signals on a dashboard so you stop pasting queries.

## Deep dives

### Which scope emits which metric?

Every point carries an `otel_scope_name` label naming the instrumentation scope
that recorded it, and the `gen_ai.*` metrics arrive under two scopes, split by
family:

| Metric family | `otel_scope_name` |
|---|---|
| `gen_ai.client.*` (token usage, model duration) | `opentelemetry.instrumentation.google_genai` |
| `gen_ai.invoke_agent.*`, `gen_ai.execute_tool.*` (ADK's own meter) | `gcp.vertex.agent` |

Group by the scope to see the split:

**Command:**

```bash
export QUERY='count by (otel_scope_name) ({"gen_ai.client.token.usage_count"})'
curl -s -H "Authorization: Bearer $TOKEN" \
  --data-urlencode "query=$QUERY" \
  "https://monitoring.googleapis.com/v1/projects/$PROJECT/location/global/prometheus/api/v1/query"
```

**Expected output:**

```console
otel_scope_name=opentelemetry.instrumentation.google_genai    2
```

One scope, two series — the `input` and `output` token types. The same query
against ADK's own metric shows the other side of the split:

```console
$ ... 'count by (otel_scope_name) ({"gen_ai.invoke_agent.duration_count"})'
otel_scope_name=gcp.vertex.agent    1
```

The practical trap: a scope filter must match the metric's own scope. Filtering
the client token metric to `otel_scope_name="gcp.vertex.agent"` (ADK's meter)
returns zero series, because the client metrics belong to the genai
instrumentation scope. Do not assume one scope owns every `gen_ai.*` name.

Confirmed 2026-09-12: `{"gen_ai.client.token.usage_count", otel_scope_name="gcp.vertex.agent"}`
returns an empty result and **no error** — the same silent-zero failure mode as
the `_total` suffix on 3.7.
