# 3.4 · Tokens and cost

*Part 3 · Consume: signals from histograms*

> [!NOTE]
> **Why you are here.** Scenario `growing-context`: does accumulated context
> explain token growth? This page reads token rate by type, then steps input
> tokens per call across one session to see the climb an average hides.

The `growing-context` scenario runs N turns in one session instead of N fresh
ones, so each model call carries the whole conversation so far. Input tokens per
call should rise turn over turn; output tokens should not. You read
`gen_ai.client.token.usage`, split by `gen_ai.token.type`. Queries live in
[queries/tokens.promql](../../queries/tokens.promql).

**Step 1 — Restart the server under this page's name.** In the server terminal,
stop the server with `Ctrl+C` and start it again as `adk-metrics-3-4`, the
`job` every query below filters on.

**Command:**

```bash
source env.sh
export OTEL_SERVICE_NAME=adk-metrics-3-4
.venv/bin/adk web --otel_to_cloud ./
```

**Step 2 — Drive the scenario.** In the second terminal:

**Command:**

```bash
load/turns.sh growing-context 20
```

**Expected output** (turns 4 to 17 trimmed):

```console
growing-context turn   1  http=200  3.93s
growing-context turn   2  http=200  2.47s
growing-context turn   3  http=200  6.42s
...
growing-context turn  18  http=200  3.21s
growing-context turn  19  http=200  3.79s
growing-context turn  20  http=200  3.33s
waiting 10s for the final export interval...
good to go — the series are in Cloud Monitoring
```

**Step 3 — Read token rate by type.** The `_sum` of the token histogram, split by
type, is total tokens; `rate() * 60` is tokens per minute.

**Command:**

```bash
source env.sh
export TOKEN=$(gcloud auth application-default print-access-token)
export QUERY='sum by ("gen_ai.token.type") (rate({"gen_ai.client.token.usage_sum", job="adk-metrics-3-4"}[10m])) * 60'
curl -s -H "Authorization: Bearer $TOKEN" \
  --data-urlencode "query=$QUERY" \
  "https://monitoring.googleapis.com/v1/projects/$PROJECT_ID/location/global/prometheus/api/v1/query"
```

**Expected output:**

```console
{"status":"success","data":{"resultType":"vector","result":[{"metric":{"gen_ai.token.type":"input"},"value":[1791021690.326,"4757.1"]},{"metric":{"gen_ai.token.type":"output"},"value":[1791021690.326,"61.7"]}]}}
```

Input runs at 4,757 tokens a minute against 62 output, about **77×**.

**Step 4 — Step input tokens per call across the session.** The mean, `_sum` over
`_count`, flattens the climb into one number. An instant query returns that one
number; a range query evaluates the same ratio at every step. This one reads the
last 5 minutes every 15 seconds, over a 1-minute window. Run it right after
Step 2.

**Command:**

```bash
export END=$(date -u +%s)
export START=$((END - 300))
export QUERY='sum by ("gen_ai.token.type") (rate({"gen_ai.client.token.usage_sum", job="adk-metrics-3-4"}[1m])) / sum by ("gen_ai.token.type") (rate({"gen_ai.client.token.usage_count", job="adk-metrics-3-4"}[1m]))'
curl -s -H "Authorization: Bearer $TOKEN" \
  --data-urlencode "query=$QUERY" \
  --data-urlencode "start=$START" \
  --data-urlencode "end=$END" \
  --data-urlencode 'step=15' \
  "https://monitoring.googleapis.com/v1/projects/$PROJECT_ID/location/global/prometheus/api/v1/query_range"
```

**Expected output** (the `NaN` points before and after the run trimmed; each
point is the mean over the minute before it):

```console
{"status":"success","data":{"resultType":"matrix","result":[
{"metric":{"gen_ai.token.type":"input"},"values":[[1791021555,"439.59537951177936"],[1791021570,"623.952189661719"],[1791021585,"843.9059010038449"],[1791021600,"1011.9450576395648"],[1791021615,"1244.8981698787354"],[1791021630,"1431.719452797212"],[1791021645,"1643.5831234158281"],[1791021660,"1808.8482750164635"],[1791021675,"1975.999999999988"],...]},
{"metric":{"gen_ai.token.type":"output"},"values":[[1791021555,"15.470822785876948"],[1791021570,"15.33317621987876"],[1791021585,"15.38998694096649"],[1791021600,"15.409424061308737"],[1791021615,"15.428925591424306"],[1791021630,"15.464379564592386"],[1791021645,"15.471057152162125"],[1791021660,"15.479420788829822"],[1791021675,"14.999999999999961"],...]}
]}}
```

Input per call rises from 440 to 1,976 tokens, about **4.5×**, across the run,
while output per call sits flat at 15. The mean over the whole run is one number
in the middle of that climb, matching no individual turn.

> [!IMPORTANT]
> **What it means.** Input per call climbs because every turn re-sends the growing
> transcript; output stays flat because each answer is about the same size. The
> mean over the whole run would report one middling number and hide the climb, so
> step the ratio over a short window when you want the trend. These are tokens, not
> dollars: multiply the per-type `sum` by your model's per-token price for a cost
> figure. Whether any of that input was served from cache is not in the metric;
> that shows up only in the rows (Part 4).

3.5 puts these signals on a dashboard so you stop pasting queries.

## Deep dives

### Which scope emits which metric?

Every point carries an `otel_scope_name` label naming the instrumentation scope
that recorded it. For a Gemini agent with the genai instrumentation active, as
under `adk web`, the `gen_ai.*` metrics arrive under two scopes, split by family
(`telemetry/tracing.py:993-1001`):

| Metric family | `otel_scope_name` |
|---|---|
| `gen_ai.client.*` (token usage, model duration) | `opentelemetry.instrumentation.google_genai` |
| `gen_ai.invoke_agent.*`, `gen_ai.execute_tool.*` (ADK's own meter) | `gcp.vertex.agent` |

Count the series in each scope to see the split:

**Command:**

```bash
export QUERY='count by (otel_scope_name) ({"gen_ai.client.token.usage_count", job="adk-metrics-3-4"})'
curl -s -H "Authorization: Bearer $TOKEN" \
  --data-urlencode "query=$QUERY" \
  "https://monitoring.googleapis.com/v1/projects/$PROJECT_ID/location/global/prometheus/api/v1/query"
```

**Expected output:**

```console
{"status":"success","data":{"resultType":"vector","result":[{"metric":{"otel_scope_name":"opentelemetry.instrumentation.google_genai"},"value":[1791021690.865,"2"]}]}}
```

`count by` counts series, not calls: the value is the number of series in that
scope, here one each for the `input` and `output` token types. The same query on
ADK's own metric shows the other side of the split:

**Command:**

```bash
export QUERY='count by (otel_scope_name) ({"gen_ai.invoke_agent.duration_count", job="adk-metrics-3-4"})'
curl -s -H "Authorization: Bearer $TOKEN" \
  --data-urlencode "query=$QUERY" \
  "https://monitoring.googleapis.com/v1/projects/$PROJECT_ID/location/global/prometheus/api/v1/query"
```

**Expected output:**

```console
{"status":"success","data":{"resultType":"vector","result":[{"metric":{"otel_scope_name":"gcp.vertex.agent"},"value":[1791021691.132,"1"]}]}}
```

The practical trap: a scope filter must match the metric's own scope. Filtering
the client token metric to `otel_scope_name="gcp.vertex.agent"` (ADK's meter)
returns zero series and no error, because here the client metrics belong to the
genai instrumentation scope. Do not assume one scope owns every `gen_ai.*` name.
