# 3.7 · Task outcome

*Part 3 · Consume — signals from histograms*

> [!NOTE]
> **Why you are here.** 3.3 left a gap: the tool failed half the time, the
> invocation never did, and no framework metric could say whether the user got
> weather. This page adds the one custom instrument that can, and reads it beside
> those two ratios.

The framework measures execution: how fast, how many, how often the machinery
errored. It cannot measure the task, because a turn that answers "I do not have
data for Atlantis" is a clean invocation and an unmet request. To count that, the
demo adds one counter,
[tutorial.weather.requests](../../demo_agent/outcome.py), recorded in an
`after_tool_callback` with one attribute, `outcome`, taken from the tool's
returned `status`. The mapping is an allowlist, not model text:

| Tool `status` | `outcome` |
|---|---|
| `ok` | `answered` |
| anything else | `unavailable` |

The counter is gated on `TUTORIAL_OUTCOME_METRIC` so Parts 1 and 2 show only the
six framework metrics. Its meter resolves against the provider
`adk web --otel_to_cloud` installs, so it rides the same export path and arrives
as `.../tutorial.weather.requests/counter`.

**Step 1 — Restart the server with the flag.** Export the flag on its own line
before `adk web`, so the counter's callback is attached.

**Command:**

```bash
export TUTORIAL_OUTCOME_METRIC=1
adk web --otel_to_cloud
```

**Step 2 — Drive the scenario.**

**Command:**

```bash
load/turns.sh unknown-city 40
```

**Expected output:**

```console
unknown-city    turn   1  http=200  3.57s
unknown-city    turn   2  http=200  3.02s
unknown-city    turn   3  http=200  2.87s
...
unknown-city    turn  39  http=200  3.65s
unknown-city    turn  40  http=200  3.63s
waiting 10s for the final export interval...
good to go — the series are in Cloud Monitoring
```

**Step 3 — Read the outcome beside 3.3's ratios.** The queries are in
[queries/outcome.promql](../../queries/outcome.promql). The unavailable share is:

```
sum(rate({"tutorial.weather.requests", outcome="unavailable"}[5m]))
  /
sum(rate({"tutorial.weather.requests"}[5m]))
```

> [!WARNING]
> **No `_total` suffix here.** Prometheus convention appends `_total` to a
> counter, and Cloud Monitoring's PromQL surface does append `_count`/`_sum` to
> the histograms this tutorial has used so far. It does **not** do that to this
> counter: the series is `tutorial.weather.requests`, exactly as named in
> [outcome.py](../../demo_agent/outcome.py). Querying
> `tutorial.weather.requests_total` returns zero series and no error, which is
> the worst kind of wrong answer. Verified 2026-09-12 against all three
> candidate names.

**Command:**

```bash
export PROJECT=jwd-gcp-demos
export TOKEN=$(gcloud auth application-default print-access-token)
export QUERY='sum(rate({"tutorial.weather.requests", outcome="unavailable"}[5m])) / sum(rate({"tutorial.weather.requests"}[5m]))'
curl -s -H "Authorization: Bearer $TOKEN" \
  --data-urlencode "query=$QUERY" \
  "https://monitoring.googleapis.com/v1/projects/$PROJECT/location/global/prometheus/api/v1/query"
```

**Expected output:** the unavailable share tracks the Atlantis mix.

```console
{"status":"success","data":{"resultType":"vector","result":[
  {"metric":{},"value":[1789277310,"0.47619047619047616"]}]}}
```

Broken out by outcome, the same window:

```console
$ ... --data-urlencode 'query={"tutorial.weather.requests"}'
   outcome=answered      22
   outcome=unavailable   20
```

Beside 3.3's two framework ratios, read at the same instant:

| Number | Query | Value |
|---|---|---|
| Tool error ratio | `execute_tool.duration_count` with `error.type!=""` over all | **0.476** |
| Invocation error ratio | `invoke_agent.duration_count` with `error.type!=""` over all | **0** (no error series exists) |
| Tasks unaccomplished | `tutorial.weather.requests` `outcome="unavailable"` over all | **0.476** |

Coverage, the third query in `outcome.promql` — counter total ÷ turn count — is
**1.0** for this run: every turn called the tool exactly once.

> [!IMPORTANT]
> **What it means.** Three numbers, one run: invocation errors 0, tool errors
> about 0.5, tasks unaccomplished about 0.5. The first two are the framework's;
> the third is yours. The gap between "the run succeeded" and "the task got done"
> is real, and only an instrument that reads the task's own result can close it.
> This is the counter to alert on, not the tool error ratio from 3.6.

> [!NOTE]
> A turn whose model never called the tool records nothing on this counter, so
> its total can be lower than the `invoke_agent.duration` count. Missing is not
> zero: the third query in `outcome.promql` divides the counter total by the turn
> count so you know how much of the traffic the outcome even covers.

Part 4 leaves metrics behind: to see which session, which prompt, and at what
cost, you need one row per event, in BigQuery.
