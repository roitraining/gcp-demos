# 3.7 · Task outcome

*Part 3 · Consume: signals from histograms*

> [!NOTE]
> **Why you are here.** Scenario `unknown-city`: did execution complete without
> accomplishing the task? 3.3 left that gap open, so this page adds one custom
> counter and reads it beside 3.3's two ratios.

The framework measures execution: how fast, how many, how often the machinery
errored. It cannot measure the task, because a turn that answers "I do not have
data for Atlantis" is a clean invocation and an unmet request. The demo adds one
counter, [tutorial.weather.requests](../../demo_agent/outcome.py), recorded in an
`after_tool_callback` with one attribute, `outcome`, taken from the tool's
returned `status`. The mapping is an allowlist, not model text:

| Tool `status` | `outcome` |
|---|---|
| `ok` | `answered` |
| anything else | `unavailable` |

The counter is gated on `TUTORIAL_OUTCOME_METRIC`; any non-empty value turns it
on, even `0`. Parts 1 and 2 leave it unset so they show only the six framework
metrics. Its meter resolves against the provider `adk web --otel_to_cloud`
installs, so it rides the same export path and arrives as
`.../tutorial.weather.requests/counter`.

**Step 1 — Restart the server with the flag.** Stop the 3.1 server with `Ctrl+C`
in its terminal, then start it again with the flag exported, so the counter's
callback is attached.

**Command:**

```bash
source env.sh
export TUTORIAL_OUTCOME_METRIC=1
.venv/bin/adk web --otel_to_cloud ./
```

**Step 2 — Drive the scenario.** In the second terminal, wait 5 minutes after the
last page's load so the `[5m]` windows hold only this run.

**Command:**

```bash
load/turns.sh unknown-city 40
```

**Expected output** (turns 4 to 37 trimmed):

```console
unknown-city    turn   1  http=200  4.24s
unknown-city    turn   2  http=200  3.77s
unknown-city    turn   3  http=200  4.79s
...
unknown-city    turn  38  http=200  4.23s
unknown-city    turn  39  http=200  3.37s
unknown-city    turn  40  http=200  4.30s
waiting 10s for the final export interval...
good to go — the series are in Cloud Monitoring
```

**Step 3 — Read the outcome beside 3.3's ratios.** The queries are in
[queries/outcome.promql](../../queries/outcome.promql). This one reads the
unavailable share: unavailable requests over all requests.

> [!WARNING]
> The counter has no `_total` suffix in PromQL, so
> `tutorial.weather.requests_total` returns zero series and no error.

**Command:**

```bash
source env.sh
export TOKEN=$(gcloud auth application-default print-access-token)
export QUERY='sum(rate({"tutorial.weather.requests", outcome="unavailable"}[5m])) / sum(rate({"tutorial.weather.requests"}[5m]))'
curl -s -H "Authorization: Bearer $TOKEN" \
  --data-urlencode "query=$QUERY" \
  "https://monitoring.googleapis.com/v1/projects/$PROJECT_ID/location/global/prometheus/api/v1/query"
```

**Expected output:** the unavailable share tracks the Atlantis mix.

```console
{"status":"success","data":{"resultType":"vector","result":[{"metric":{},"value":[1790998385.265,"0.5"]}]}}
```

Beside 3.3's two framework ratios, read at the same time:

| Number | Query | Value |
|---|---|---|
| Tool error ratio | 3.3 Step 2 | **0.5** |
| Invocation error ratio | 3.3 Step 3, with `or vector(0)` | **0** |
| Requests unavailable | this page's query | **0.5** |

> [!IMPORTANT]
> **What it means.** Three numbers, one run: invocation errors 0, tool errors
> about 0.5, requests unavailable about 0.5. The first two are the framework's;
> the third is yours, and it names the user's outcome rather than the machinery's.
> Here it equals the tool error ratio, because it reads the same `status` field
> and counts per tool call, not per task (`demo_agent/outcome.py:62-64`). Treat it
> as an approximation of task outcome; a counter keyed to the task itself would
> diverge from the tool ratio when one turn calls the tool more than once.

Part 4 leaves metrics behind: to see which session, which prompt, and at what
cost, you need one row per event, in BigQuery. Stop the server and run
`unset TUTORIAL_OUTCOME_METRIC` first, so later servers emit only the six
framework metrics.

## Deep dives

### Why can the counter total be lower than the turn count?

A turn whose model never called the tool records nothing on this counter, so its
total can be lower than the `invoke_agent.duration` count. Such a turn is missing
from the outcome, not counted as a success or a failure. The third query in
`outcome.promql` divides the counter total by the turn count, so you know how
much of the traffic the outcome covers.

**Command:**

```bash
export QUERY='sum(rate({"tutorial.weather.requests"}[5m])) / sum(rate({"gen_ai.invoke_agent.duration_count"}[5m]))'
curl -s -H "Authorization: Bearer $TOKEN" \
  --data-urlencode "query=$QUERY" \
  "https://monitoring.googleapis.com/v1/projects/$PROJECT_ID/location/global/prometheus/api/v1/query"
```

**Expected output:** `1` means every turn called the tool exactly once.

```console
{"status":"success","data":{"resultType":"vector","result":[{"metric":{},"value":[1790998386.124,"1"]}]}}
```
