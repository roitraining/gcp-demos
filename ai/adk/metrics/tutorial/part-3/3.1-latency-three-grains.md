# 3.1 · Latency, three grains

*Part 3 · Consume: signals from histograms*

> [!NOTE]
> **Why you are here.** Scenario `slow-tool`: is the dependency responsible for
> the slowdown? Latency lives at three grains, the turn, the model call inside it,
> and the tool call inside that, and reading each tells you which layer owns the
> time.

Each grain has its own histogram: turn (`invoke_agent.duration`), model
(`client.operation.duration`), and tool (`execute_tool.duration`). All reads use
PromQL over `curl`, as in [2.1](../part-2/2.1-adk-web-otel-to-cloud.md).

**Step 1 — Start the server.** The same command as
[2.1](../part-2/2.1-adk-web-otel-to-cloud.md); `env.sh` must be sourced before
`adk web` starts.

**Command:**

```bash
source env.sh
.venv/bin/adk web --otel_to_cloud ./
```

Leave it running in this terminal for the rest of Part 3, and open a second one.

**Step 2 — Drive the scenario.** In the second terminal, point `HOST` at the local
server, so a value left over from 2.3 does not redirect the load, and fire thirty
`slow-tool` turns.

**Command:**

```bash
source env.sh
export HOST=http://localhost:8000
load/turns.sh slow-tool 30
```

**Expected output** (turns 4 to 27 trimmed): one line per turn, then a wait for
the final export:

```console
slow-tool       turn   1  http=200  5.73s
slow-tool       turn   2  http=200  6.55s
slow-tool       turn   3  http=200  4.72s
...
slow-tool       turn  28  http=200  5.11s
slow-tool       turn  29  http=200  4.64s
slow-tool       turn  30  http=200  6.74s
waiting 10s for the final export interval...
good to go — the series are in Cloud Monitoring
```

**Step 3 — Orient in Metrics Explorer.** The Console is for a first look; it is
described here, not captured.

- Open **Monitoring → Metrics Explorer**.
- Click the **`<> PromQL`** toggle on the query row.
- Set the time range to **15 minutes**.
- Paste the turn query from Step 4 and click **Run query**.

One line appears for `weather_agent`, rising as the turns land.

**Step 4 — Read the three grains.** Each `curl` sends the query with a bearer
token from your Application Default Credentials (ADC). Start with the turn p95.

**Command:**

```bash
export TOKEN=$(gcloud auth application-default print-access-token)
export QUERY='histogram_quantile(0.95, sum by (le, "gen_ai.agent.name") (rate({"gen_ai.invoke_agent.duration_bucket"}[5m])))'
curl -s -H "Authorization: Bearer $TOKEN" \
  --data-urlencode "query=$QUERY" \
  "https://monitoring.googleapis.com/v1/projects/$PROJECT_ID/location/global/prometheus/api/v1/query"
```

**Expected output:** the turn p95, one series per agent.

```console
{"status":"success","data":{"resultType":"vector","result":[{"metric":{"gen_ai.agent.name":"weather_agent"},"value":[1790994494.843,"11.200000000000001"]}]}}
```

The model grain reads the mean per call, `_sum` over `_count`, not a p95. See
[Why not a p95 for the model call?](#why-not-a-p95-for-the-model-call)

**Command:**

```bash
export QUERY='sum by ("gen_ai.request.model") (rate({"gen_ai.client.operation.duration_sum"}[5m])) / sum by ("gen_ai.request.model") (rate({"gen_ai.client.operation.duration_count"}[5m]))'
curl -s -H "Authorization: Bearer $TOKEN" \
  --data-urlencode "query=$QUERY" \
  "https://monitoring.googleapis.com/v1/projects/$PROJECT_ID/location/global/prometheus/api/v1/query"
```

**Expected output:** the mean model call, in seconds.

```console
{"status":"success","data":{"resultType":"vector","result":[{"metric":{"gen_ai.request.model":"gemini-3.7-flash"},"value":[1790994495.119,"2.2335257166666667"]}]}}
```

The tool grain is the p95 of `execute_tool.duration`, grouped by tool name:

**Command:**

```bash
export QUERY='histogram_quantile(0.95, sum by (le, "gen_ai.tool.name") (rate({"gen_ai.execute_tool.duration_bucket"}[5m])))'
curl -s -H "Authorization: Bearer $TOKEN" \
  --data-urlencode "query=$QUERY" \
  "https://monitoring.googleapis.com/v1/projects/$PROJECT_ID/location/global/prometheus/api/v1/query"
```

**Expected output:** one series per tool.

```console
{"status":"success","data":{"resultType":"vector","result":[{"metric":{"gen_ai.tool.name":"get_forecast"},"value":[1790994495.698,"2.3200000000000003"]},{"metric":{"gen_ai.tool.name":"get_weather"},"value":[1790994495.698,"0.01"]}]}}
```

> [!IMPORTANT]
> **What it means.** A turn is two model calls plus one tool call. The model
> averages 2.2 s a call, so about 4.5 s of every turn is the model. The tool grain
> isolates the slow dependency: `get_forecast` sits near 2.3 s while `get_weather`
> stays at 0.01 s. So `get_forecast` adds time to the forecast turns, but the
> model owns most of each turn. Percentiles are interpolated inside a bucket, so
> the 11.2 s turn p95 and the 2.3 s tool p95 exceed every real value (the slowest
> turn took 8.1 s; `get_forecast` sleeps at most 1.5 s). See
> [Why can a p95 exceed every real value?](#why-can-a-p95-exceed-every-real-value)

3.2 asks whether repeated work, not one slow tool, is the cost driver.

## Deep dives

### Why not a p95 for the model call?

ADK's own histograms set bucket bounds that fit their values: turns double from
0.1 s to 409.6 s, tools from 0.01 s to 81.92 s. Under `adk web`, the model-call
histogram comes from the genai instrumentation, with OpenTelemetry's default
bounds of 0, 5, 10, 25 and up. On this run 57 of 60 calls fell in the 0 to 5 s
bucket, so a model p95 reads exactly `5`, a bucket edge. The mean is exact.

### Why can a p95 exceed every real value?

A histogram stores counts per bucket, not values. `histogram_quantile` finds the
bucket the 95th percentile falls in and assumes values spread evenly across it.
The 95th-percentile turn falls in the 6.4 to 12.8 s bucket, so the answer lands at
11.2 s though no turn took longer than 8.1 s.

### Do overlapping turns contaminate each other's timers?

The `concurrent` scenario fires `slow-tool` and `baseline` turns in parallel
instead of in sequence. Wait at least 5 minutes after Step 2, so the `[5m]` window
holds only the concurrent turns, then fire ten of them. Keep it to ten: at 20,
`adk web`'s local SQLite session store failed 7 turns with `database is locked`.

**Command:**

```bash
load/turns.sh concurrent 10
```

Then rerun the three Step 4 queries.

**Expected output** (the three query results, in Step 4's order):

```console
{"status":"success","data":{"resultType":"vector","result":[{"metric":{"gen_ai.agent.name":"weather_agent"},"value":[1790996621.516,"12.36"]}]}}
{"status":"success","data":{"resultType":"vector","result":[{"metric":{"gen_ai.request.model":"gemini-3.7-flash"},"value":[1790996621.815,"2.729584181818182"]}]}}
{"status":"success","data":{"resultType":"vector","result":[{"metric":{"gen_ai.tool.name":"get_forecast"},"value":[1790996622.106,"2.48"]},{"metric":{"gen_ai.tool.name":"get_weather"},"value":[1790996622.106,"0.01"]}]}}
```

The tool p95s barely move (2.48 s against 2.32 s, the same bucket), because each
tool call is timed on its own span. The turn p95 and the model mean do rise, to
12.4 s and 2.7 s: overlapping turns made the model calls slower, and the timers
recorded that. Overlap changes the latency itself, not the accuracy of the
timers.
