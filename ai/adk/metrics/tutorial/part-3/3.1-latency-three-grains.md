# 3.1 · Latency, three grains

*Part 3 · Consume: signals from histograms*

> [!NOTE]
> **Why you are here.** Scenario `slow-tool`: is the dependency responsible for
> the slowdown? Latency lives at three grains, the turn, the model call inside it,
> and the tool call inside that, and reading each tells you which layer owns the
> time.

Each grain has its own histogram: turn (`invoke_agent.duration`), model
(`client.operation.duration`), and tool (`execute_tool.duration`). All reads use
PromQL over `curl`, as in [2.1](../part-2/2.1-adk-web-otel-to-cloud.md).

**Step 1 — Start the server under this page's name.** The same command as
[2.1](../part-2/2.1-adk-web-otel-to-cloud.md), with one change: every Part 3 page
starts its server under its own `OTEL_SERVICE_NAME`, which Cloud Monitoring
stores as the `job` label. Each query on the page filters on that `job`, so no
other page's turns leak into the reading and no page waits for the last one's
data to age out.

**Command:**

```bash
source env.sh
export OTEL_SERVICE_NAME=adk-metrics-3-1
.venv/bin/adk web --otel_to_cloud ./
```

Leave it running in this terminal, and open a second one.

**Step 2 — Drive the scenario.** In the second terminal, point `HOST` at the local
server, so a value left over from 2.3 does not redirect the load, and fire thirty
`slow-tool` turns.

**Command:**

```bash
source env.sh
export HOST=http://localhost:8000
load/turns.sh slow-tool 30
```

**Expected output** (turns 4 to 27 trimmed): one line per turn, then a wait for
the final export:

```console
slow-tool       turn   1  http=200  6.15s
slow-tool       turn   2  http=200  4.27s
slow-tool       turn   3  http=200  3.20s
...
slow-tool       turn  28  http=200  3.85s
slow-tool       turn  29  http=200  2.60s
slow-tool       turn  30  http=200  4.89s
waiting 10s for the final export interval...
good to go — the series are in Cloud Monitoring
```

**Step 3 — Orient in Metrics Explorer.** The Console is for a first look; it is
described here, not captured.

- Open **Monitoring → Metrics Explorer**.
- Click the **`<> PromQL`** toggle on the query row.
- Set the time range to **15 minutes**.
- Paste the turn query from Step 4 and click **Run query**.

One line appears for `weather_agent`, rising as the turns land.

**Step 4 — Read the three grains.** Each `curl` sends the query with a bearer
token from your Application Default Credentials (ADC). Start with the turn p95.

**Command:**

```bash
export TOKEN=$(gcloud auth application-default print-access-token)
export QUERY='histogram_quantile(0.95, sum by (le, "gen_ai.agent.name") (rate({"gen_ai.invoke_agent.duration_bucket", job="adk-metrics-3-1"}[10m])))'
curl -s -H "Authorization: Bearer $TOKEN" \
  --data-urlencode "query=$QUERY" \
  "https://monitoring.googleapis.com/v1/projects/$PROJECT_ID/location/global/prometheus/api/v1/query"
```

**Expected output:** the turn p95, one series per agent.

```console
{"status":"success","data":{"resultType":"vector","result":[{"metric":{"gen_ai.agent.name":"weather_agent"},"value":[1791021739.961,"6.133333333333334"]}]}}
```

The model grain reads the mean per call, `_sum` over `_count`, not a p95. See
[Why not a p95 for the model call?](#why-not-a-p95-for-the-model-call)

**Command:**

```bash
export QUERY='sum by ("gen_ai.request.model") (rate({"gen_ai.client.operation.duration_sum", job="adk-metrics-3-1"}[10m])) / sum by ("gen_ai.request.model") (rate({"gen_ai.client.operation.duration_count", job="adk-metrics-3-1"}[10m]))'
curl -s -H "Authorization: Bearer $TOKEN" \
  --data-urlencode "query=$QUERY" \
  "https://monitoring.googleapis.com/v1/projects/$PROJECT_ID/location/global/prometheus/api/v1/query"
```

**Expected output:** the mean model call, in seconds.

```console
{"status":"success","data":{"resultType":"vector","result":[{"metric":{"gen_ai.request.model":"gemini-3.7-flash"},"value":[1791021740.245,"1.5697405166666671"]}]}}
```

The tool grain is the p95 of `execute_tool.duration`, grouped by tool name:

**Command:**

```bash
export QUERY='histogram_quantile(0.95, sum by (le, "gen_ai.tool.name") (rate({"gen_ai.execute_tool.duration_bucket", job="adk-metrics-3-1"}[10m])))'
curl -s -H "Authorization: Bearer $TOKEN" \
  --data-urlencode "query=$QUERY" \
  "https://monitoring.googleapis.com/v1/projects/$PROJECT_ID/location/global/prometheus/api/v1/query"
```

**Expected output:** one series per tool.

```console
{"status":"success","data":{"resultType":"vector","result":[{"metric":{"gen_ai.tool.name":"get_forecast"},"value":[1791021740.522,"2.08"]},{"metric":{"gen_ai.tool.name":"get_weather"},"value":[1791021740.522,"0.01"]}]}}
```

> [!IMPORTANT]
> **What it means.** A turn is two model calls plus one tool call. The model
> averages 1.6 s a call, so about 3.1 s of every turn is the model. The tool grain
> isolates the slow dependency: `get_forecast` sits near 2.1 s while `get_weather`
> stays at 0.01 s. So `get_forecast` adds time to the forecast turns, but the
> model owns most of each turn. Percentiles are interpolated inside a bucket, so
> the 2.1 s tool p95 exceeds every real value (`get_forecast` sleeps at most
> 1.5 s), and the 6.1 s turn p95 sits at the slowest turn (6.2 s). See
> [Why can a p95 exceed every real value?](#why-can-a-p95-exceed-every-real-value)

3.2 asks whether repeated work, not one slow tool, is the cost driver.

## Deep dives

### Why not a p95 for the model call?

ADK's own histograms set bucket bounds that fit their values: turns double from
0.1 s to 409.6 s, tools from 0.01 s to 81.92 s. Under `adk web`, the model-call
histogram comes from the genai instrumentation, with OpenTelemetry's default
bounds of 0, 5, 10, 25 and up. On this run all 60 calls fell in the 0 to 5 s
bucket, so a model p95 reads exactly `5`, a bucket edge. The mean is exact.

### Why can a p95 exceed every real value?

A histogram stores counts per bucket, not values. `histogram_quantile` finds the
bucket the 95th percentile falls in and assumes values spread evenly across it.
The 95th-percentile tool call falls in the 1.28 to 2.56 s bucket, so the answer
lands at 2.1 s though `get_forecast` sleeps at most 1.5 s.

### Do overlapping turns contaminate each other's timers?

The `concurrent` scenario fires `slow-tool` and `baseline` turns in parallel
instead of in sequence. Give it its own `job`: in the server terminal, stop the
server with `Ctrl+C` and start it again under a new name.

**Command:**

```bash
export OTEL_SERVICE_NAME=adk-metrics-3-1c
.venv/bin/adk web --otel_to_cloud ./
```

In the second terminal, fire ten concurrent turns. Keep it to ten: at 20,
`adk web`'s local SQLite session store failed 7 turns with `database is locked`.

**Command:**

```bash
load/turns.sh concurrent 10
```

Then run Step 4's three queries again, filtered on the new `job`.

**Command:**

```bash
for QUERY in \
  'histogram_quantile(0.95, sum by (le, "gen_ai.agent.name") (rate({"gen_ai.invoke_agent.duration_bucket", job="adk-metrics-3-1c"}[10m])))' \
  'sum by ("gen_ai.request.model") (rate({"gen_ai.client.operation.duration_sum", job="adk-metrics-3-1c"}[10m])) / sum by ("gen_ai.request.model") (rate({"gen_ai.client.operation.duration_count", job="adk-metrics-3-1c"}[10m]))' \
  'histogram_quantile(0.95, sum by (le, "gen_ai.tool.name") (rate({"gen_ai.execute_tool.duration_bucket", job="adk-metrics-3-1c"}[10m])))'
do
  curl -s -H "Authorization: Bearer $TOKEN" \
    --data-urlencode "query=$QUERY" \
    "https://monitoring.googleapis.com/v1/projects/$PROJECT_ID/location/global/prometheus/api/v1/query"
  echo
done
```

**Expected output** (the three query results, in Step 4's order):

```console
{"status":"success","data":{"resultType":"vector","result":[{"metric":{"gen_ai.agent.name":"weather_agent"},"value":[1791021740.764,"11.733333333333334"]}]}}
{"status":"success","data":{"resultType":"vector","result":[{"metric":{"gen_ai.request.model":"gemini-3.7-flash"},"value":[1791021741.06,"2.1334115000000007"]}]}}
{"status":"success","data":{"resultType":"vector","result":[{"metric":{"gen_ai.tool.name":"get_forecast"},"value":[1791021741.467,"1.2266666666666666"]},{"metric":{"gen_ai.tool.name":"get_weather"},"value":[1791021741.467,"0.01"]}]}}
```

The tool p95 does not rise (1.2 s against 2.1 s), because each tool call is timed
on its own span. The turn p95 and the model mean do rise, to
11.7 s and 2.1 s: overlapping turns made the model calls slower, and the timers
recorded that. Overlap changes the latency itself, not the accuracy of the
timers.
