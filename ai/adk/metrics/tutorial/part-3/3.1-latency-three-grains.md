# 3.1 · Latency, three grains

*Part 3 · Consume — signals from histograms*

> [!NOTE]
> **Why you are here.** Latency is the first signal, and it lives at three grains:
> the whole turn, the model call inside it, and the tool call inside that. Reading
> the percentile at each grain tells you which layer owns a slowdown.

An operator's first question is "how slow?", and the answer is a percentile, not
an average (1.2). The signal is `histogram_quantile` over the `_bucket` series a
histogram exports, split by grain: turn (`invoke_agent.duration`), model
(`client.operation.duration`), and tool (`execute_tool.duration`). This page runs
the `slow-tool` scenario so the tool grain has shape, then reads the p95 at all
three. All reads use PromQL over `curl`, the path
[2.1](../part-2/2.1-adk-web-otel-to-cloud.md) settled on.

**Step 1 — Start the server.** Part 3 reads metrics that a running server exports,
so start one with the cloud flag, the same command as
[2.1](../part-2/2.1-adk-web-otel-to-cloud.md). `env.sh` sets the resource labels
the backend needs, and they must be in the shell before `adk web` starts.

**Command:**

```bash
source env.sh
adk web --otel_to_cloud ./
```

Leave it running in this terminal and open a second one for the rest of the page.

**Step 2 — Drive the scenario.** In the second terminal, point `HOST` at the local
server and fire thirty `slow-tool` turns at it. Setting `HOST` explicitly keeps a
value left over from another activity from redirecting the load.

**Command:**

```bash
export HOST=http://localhost:8000
load/turns.sh slow-tool 30
```

**Expected output** — one line per turn, forecast turns running seconds longer
than London turns, then a wait for the final export:

```console
slow-tool       turn   1  http=200  0.51s
slow-tool       turn   2  http=200  2.18s
slow-tool       turn   3  http=200  0.49s
slow-tool       turn   4  http=200  1.83s
...
slow-tool       turn  30  http=200  1.42s
waiting 10s for the final export interval...
good to go — the series are in Cloud Monitoring
```

**Step 3 — Orient in Metrics Explorer.** The Console is for a first look; it is
described here, not captured. Paste the turn p95 and watch the one line climb over
the run.

- Open **Monitoring → Metrics Explorer**.
- Click the **`<> PromQL`** toggle on the query row.
- Set the time range to **15 minutes** (the shortest preset; the query's own
  `[5m]` window is separate from the chart range).
- Paste the turn p95 below and click **Run query**.

```
histogram_quantile(0.95, sum by (le, "gen_ai.agent.name") (rate({"gen_ai.invoke_agent.duration_bucket"}[5m])))
```

**Step 4 — Read the three grains.** The rest of Part 3 reads from `curl`. POST the
urlencoded query with an ADC bearer token; the endpoint takes the query in the
request body. Run the turn grain first, then swap `QUERY` for the model and tool
grains.

**Command:**

```bash
export PROJECT=jwd-gcp-demos
export TOKEN=$(gcloud auth application-default print-access-token)
export QUERY='histogram_quantile(0.95, sum by (le, "gen_ai.agent.name") (rate({"gen_ai.invoke_agent.duration_bucket"}[5m])))'
curl -s -H "Authorization: Bearer $TOKEN" \
  --data-urlencode "query=$QUERY" \
  "https://monitoring.googleapis.com/v1/projects/$PROJECT/location/global/prometheus/api/v1/query"
```

**Expected output** — the turn p95, one line per agent:

```console
{ "data": { "resultType": "vector", "result": [
  { "metric": { "gen_ai.agent.name": "weather_agent" }, "value": [ ..., "7.84" ] }
] } }
```

The model grain is the same query over `client.operation.duration`, grouped by
model:

```bash
export QUERY='histogram_quantile(0.95, sum by (le, "gen_ai.request.model") (rate({"gen_ai.client.operation.duration_bucket"}[5m])))'
curl -s -H "Authorization: Bearer $TOKEN" \
  --data-urlencode "query=$QUERY" \
  "https://monitoring.googleapis.com/v1/projects/$PROJECT/location/global/prometheus/api/v1/query"
```

**Expected output** — the model p95, well under the turn:

```console
{ "data": { "resultType": "vector", "result": [
  { "metric": { "gen_ai.request.model": "gemini-3.7-flash" }, "value": [ ..., "4.828" ] }
] } }
```

The tool grain is `execute_tool.duration`, grouped by tool name:

```bash
export QUERY='histogram_quantile(0.95, sum by (le, "gen_ai.tool.name") (rate({"gen_ai.execute_tool.duration_bucket"}[5m])))'
curl -s -H "Authorization: Bearer $TOKEN" \
  --data-urlencode "query=$QUERY" \
  "https://monitoring.googleapis.com/v1/projects/$PROJECT/location/global/prometheus/api/v1/query"
```

**Expected output** — two tools, two grains apart:

```console
{ "data": { "resultType": "vector", "result": [
  { "metric": { "gen_ai.tool.name": "get_forecast" }, "value": [ ..., "2.163" ] },
  { "metric": { "gen_ai.tool.name": "get_weather"  }, "value": [ ..., "0.010" ] }
] } }
```

> [!IMPORTANT]
> **What it means.** All three read the same percentile off `_bucket` series with
> `le`; they differ only in which grain they group by. The turn p95 is 7.84 s
> while the model holds at 4.83 s, and `get_forecast` at 2.16 s carries the gap
> that `get_weather` at 0.01 s does not. The turn slows while the model stays flat
> and one tool owns the rise, so the dependency is responsible, not the model.

3.2 keeps to PromQL and asks whether repeated work, not one slow tool, is the cost
driver.

## Deep dives

### Do overlapping turns contaminate each other's timers?

Fire the `concurrent` scenario, which overlaps `slow-tool` and `baseline` turns in
parallel instead of in sequence, then re-read the per-tool and per-turn p95:

**Command:**

```bash
load/turns.sh concurrent 20
```

**Expected output** — the same p95 shape as the sequential run, within tolerance:

```console
get_forecast  p95  2.09s
get_weather   p95  0.011s
weather_agent p95  7.71s
```

The percentiles match the sequential run because each duration is measured per
invocation, from the span that wraps that one turn, not from a process-wide clock.
Overlapping turns raise throughput, not each other's recorded latency.
