# 3.1 · Latency, three grains

*Part 3 · Consume — signals from histograms*

> [!NOTE]
> **Why you are here.** Latency is the first signal, and it lives at three grains:
> the whole turn, the model call inside it, and the tool call inside that. The
> signal is a percentile, computed from the `_bucket` series a histogram exports.

An operator's first question is "how slow?", and the answer is a percentile,
not an average (1.2). [2.1](../part-2/2.1-adk-web-otel-to-cloud.md) already met the
three read doors and committed to PromQL; here you read latency through the same
doors once more, then use PromQL to split the percentile by grain — turn, model,
tool — so you can see which layer owns a slowdown. Run the `slow-tool` scenario
first so the tool latency has shape.

**Step 1 — Drive the scenario.**

**Command:**

```bash
load/turns.sh slow-tool 30
```

**Expected output:** one line per turn, then wait two export intervals.

```console
NEEDS-RUN: load/turns.sh slow-tool 30 — 30 lines (scenario, HTTP status, elapsed), a mix of London weather and three-day forecast turns
```

**Step 2 — Read the percentile in Metrics Explorer.** In the Console, open
**Monitoring → Metrics Explorer**, switch the editor to **PromQL**, and paste the
p95 block from [queries/latency.promql](../../queries/latency.promql). The Console
is for orientation; it is described here, not captured.

**Step 3 — Read it through the Monitoring API.** `timeSeries.list` aligns raw
points server-side; ask for the 95th percentile of `invoke_agent.duration`.

**Command:**

```bash
export PROJECT=jwd-gcp-demos
gcloud monitoring time-series list \
  --project="$PROJECT" \
  --filter='metric.type="prometheus.googleapis.com/gen_ai.invoke_agent.duration/histogram"' \
  --aggregation-alignment-period=300s \
  --aggregation-per-series-aligner=ALIGN_PERCENTILE_95
```

**Expected output:**

```console
NEEDS-RUN: timeSeries.list ALIGN_PERCENTILE_95 on invoke_agent.duration — p95 of the whole turn, slow-tool run
```

**Step 4 — Read it through the PromQL endpoint.** This is the path the rest of
Part 3 uses. POST the urlencoded query with an ADC bearer token. The query is the
p95 block from [queries/latency.promql](../../queries/latency.promql):

```
histogram_quantile(
  0.95,
  sum by (le, "gen_ai.agent.name") (
    rate({"gen_ai.invoke_agent.duration_bucket"}[5m])
  )
)
```

Put that query in `QUERY`, then POST it. The endpoint takes the query in the
request body, urlencoded, with an ADC bearer token.

**Command:**

```bash
export PROJECT=jwd-gcp-demos
export TOKEN=$(gcloud auth application-default print-access-token)
export QUERY='histogram_quantile(0.95, sum by (le, "gen_ai.agent.name") (rate({"gen_ai.invoke_agent.duration_bucket"}[5m])))'
curl -s -H "Authorization: Bearer $TOKEN" \
  --data-urlencode "query=$QUERY" \
  "https://monitoring.googleapis.com/v1/projects/$PROJECT/location/global/prometheus/api/v1/query"
```

**Expected output:**

```console
NEEDS-RUN: PromQL p95 of invoke_agent.duration by gen_ai.agent.name — slow-tool run
```

> [!IMPORTANT]
> **What it means.** All three read the same percentile off the same `_bucket`
> series; they differ only in interface. Compare the turn p95 with the model p95
> (`client.operation.duration`, also in the query file) and the tool p95 by name.
> If the turn slows while the model stays flat and `get_forecast` carries the
> rise, the dependency is responsible, not the model. PromQL wins for the rest of
> Part 3 because it expresses ratios and multi-series math the aligners cannot.

3.2 keeps to PromQL and asks whether repeated work, not one slow tool, is the
cost driver.

## Deep dives

### Do overlapping turns contaminate each other's timers?

Fire the `concurrent` scenario, which overlaps `slow-tool` and `baseline` turns
in parallel instead of in sequence, then re-read the per-tool and per-turn p95:

**Command:**

```bash
load/turns.sh concurrent 20
```

**Expected output:**

```console
NEEDS-RUN: concurrent per-tool p95 and per-turn p95 vs the sequential slow-tool run — within tolerance
```

The percentiles match the sequential run because each duration is measured per
invocation, from the span that wraps that one turn, not from a process-wide
clock. Overlapping turns raise throughput, not each other's recorded latency.
