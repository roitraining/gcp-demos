# 2.4 · Your own server

*Part 2 · Collect*

> [!NOTE]
> **Why you are here.** The CLI installed the exporters in 2.1 to 2.3. A server
> you wrote has no CLI, so the metrics are recorded but never leave the process.
> This page adds the two lines that export them, and confirms your server produces
> the same six series as `adk web`.

The two calls are the same shape as the logging tutorial's own-server page, with
one flag changed: `enable_cloud_metrics=True` instead of the logging flag.
[examples/03_metrics_server.py](../../examples/03_metrics_server.py) runs them
before it builds the `Runner`:

```python
from google.adk.telemetry.google_cloud import get_gcp_exporters
from google.adk.telemetry.setup import maybe_set_otel_providers

hooks = get_gcp_exporters(enable_cloud_metrics=True)
maybe_set_otel_providers([hooks])
```

`get_gcp_exporters` reads the project and credentials from ADC.
`OTEL_SERVICE_NAME` becomes the series' `job` label. Because your server loads
`.env` before it builds the exporters, every `OTEL_*` variable can live in `.env`
here, unlike the CLI routes. One label is not optional: a standalone script must
put `gcp.project_id` in `OTEL_RESOURCE_ATTRIBUTES`, which `adk web` injects for
you but a bare process does not. See
[Why the script needs `gcp.project_id`](#why-the-script-needs-gcpprojectid).

**Step 1 — Add `gcp.project_id` to the resource, then run the server.** `env.sh`
sets `OTEL_SERVICE_NAME` and the laptop resource labels, but a standalone script
also needs `gcp.project_id` in `OTEL_RESOURCE_ATTRIBUTES`. Add it in this shell
before starting the server.

**Command:**

```bash
source env.sh
export OTEL_RESOURCE_ATTRIBUTES="${OTEL_RESOURCE_ATTRIBUTES},gcp.project_id=${PROJECT_ID}"
.venv/bin/python examples/03_metrics_server.py
```

**Step 2 — Drive baseline load.** This server exposes a single `/chat` endpoint,
not the full `adk web` run API, so drive it with a plain curl loop rather than
`load/turns.sh` (which targets the CLI server's `/run`). In a second terminal:

**Command:**

```bash
for i in $(seq 20); do
  curl -s -X POST localhost:8080/chat \
    -H 'content-type: application/json' \
    -d '{"message": "What'\''s the weather in London?"}' >/dev/null
done
```

**Expected output:** no output; each turn is answered and the server logs it.
The metrics leave the process every 5 s. Wait about 10 s, then read the series
back in Step 3.

**Step 3 — Read the series back by `job`.** Wait about 10 s, then filter the token
count to your service name.

**Command:**

```bash
curl -s \
  "https://monitoring.googleapis.com/v1/projects/${PROJECT_ID}/location/global/prometheus/api/v1/query" \
  -H "Authorization: Bearer $(gcloud auth print-access-token)" \
  --data-urlencode 'query=count by (job) ({"gen_ai.client.token.usage_count", job="adk-metrics"})'
```

**Expected output** — one series, tagged with your `OTEL_SERVICE_NAME`:

```console
{"job":"adk-metrics"}  1
```

> [!IMPORTANT]
> **What it means.** Your own server exports the same six metrics as `adk web`,
> distinguished only by the `job` label you set. The exporter is ADK's; the two
> lines wire it in. Nothing about the metrics themselves depends on the CLI.

[2.5](2.5-agent-runtime.md) asks whether a request-driven runtime, with no export
daemon at all, exports metrics.

## Deep dives

### What is the export interval, and why does it matter?

The `PeriodicExportingMetricReader` sends a batch on a fixed interval, and the
interval differs by route:

| Route | Interval | Set by |
|---|---|---|
| `--otel_to_cloud` (2.1 to 2.3) | 5 s | `MIN_EXPORT_INTERVAL_MS` |
| `get_gcp_exporters` (this page) | 5 s | `MIN_EXPORT_INTERVAL_MS` |
| OTLP env-var route ([2.6](2.6-other-backends.md)) | 60 s | `OTEL_METRIC_EXPORT_INTERVAL` |

That is why every read-back on the Google path waits about 10 s, two intervals,
before querying: one to fire and one for margin. On the env-var route you would
wait past 60 s instead. And on any route, a process that exits inside the interval
of its last turn exports nothing, because ADK installs the `MeterProvider` with
`shutdown_on_exit=False`. A long-running server never hits this; its reader keeps
firing on the interval. A short script does, which is why the Part 1 examples call
`force_flush()` ([1.1](../part-1/1.1-your-first-datapoint.md)) instead of relying
on the interval.

### Why the script needs `gcp.project_id`

Off Agent Engine, `get_gcp_exporters` builds the resource by merging two
detectors: the OTel detector reads `OTEL_RESOURCE_ATTRIBUTES` and
`OTEL_SERVICE_NAME`, and the Google Cloud detector reads the metadata server. A
laptop has no metadata server, so the Google Cloud detector contributes nothing,
and the project id has to come from `OTEL_RESOURCE_ATTRIBUTES`. Without it every
batch is a `400` whose body reads `Resource is missing required attribute
"gcp.project_id"`. `adk web --otel_to_cloud` sets this attribute internally, so
2.1 did not need it; a standalone script does, which is why Step 1 appends it to
`OTEL_RESOURCE_ATTRIBUTES` before starting the server.
