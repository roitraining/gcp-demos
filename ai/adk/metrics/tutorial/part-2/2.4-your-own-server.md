# 2.4 · Your own server

*Part 2 · Collect*

> [!NOTE]
> **Why you are here.** Scenario `baseline`: does my own server export the same
> series? A server you wrote has no CLI, so nothing installs a `MeterProvider` and
> the metrics are never recorded until you add the two calls this page shows.

The two calls are the same shape as the
[logging tutorial's own-server page](../../../logging/tutorial/part-5/5.5-your-own-server.md),
with one flag changed: `enable_cloud_metrics=True` instead of the logging flag.
[examples/03_metrics_server.py](../../examples/03_metrics_server.py) runs them
before it builds the `Runner`:

```python
resource = Resource.create(
    {
        "gcp.project_id": project,
        "service.name": os.environ["OTEL_SERVICE_NAME"],
    }
)

hooks = get_gcp_exporters(enable_cloud_metrics=True)
maybe_set_otel_providers([hooks], otel_resource=resource)
```

`get_gcp_exporters` reads the project and credentials from Application Default
Credentials. `OTEL_SERVICE_NAME` becomes the series' `job` label. Because your
server loads `.env` before it builds the exporters, every `OTEL_*` variable can
live in `.env` here, unlike the CLI routes; if the variable is already exported
in your shell, the shell value wins. The resource carries `gcp.project_id`,
which `adk web` injects for you but a bare process does not. See
[Why does a script need `gcp.project_id`?](#why-does-a-script-need-gcpproject_id)

**Step 1 — Run the server under its own service name.** `env.sh` sets the laptop
resource labels and `OTEL_SERVICE_NAME=adk-metrics`, the name 2.1's `adk web`
used. Give this server its own name so its series stay apart from 2.1's.

**Command:**

```bash
source env.sh
export OTEL_SERVICE_NAME=adk-metrics-server
.venv/bin/python examples/03_metrics_server.py
```

**Expected output** (Uvicorn's startup lines trimmed):

```console
Exporting gen_ai.* metrics to Cloud Monitoring in project 'jwd-gcp-demos' every 5 s.
```

**Step 2 — Drive baseline load.** This server exposes a single `/chat` endpoint,
not the full `adk web` run API, so drive it with a plain curl loop rather than
`load/turns.sh` (which targets the CLI server's `/run`). In a second terminal:

**Command:**

```bash
for i in $(seq 20); do
  curl -s -o /dev/null -w "chat            turn $i  http=%{http_code}  %{time_total}s\n" \
    -X POST localhost:8080/chat \
    -H 'content-type: application/json' \
    -d '{"message": "What'\''s the weather in London?"}'
done
```

**Expected output** (turns 4 to 17 trimmed) — twenty answered turns, one line
each:

```console
chat            turn 1  http=200  5.197151s
chat            turn 2  http=200  6.287735s
chat            turn 3  http=200  3.515728s
...
chat            turn 18  http=200  3.528682s
chat            turn 19  http=200  4.202833s
chat            turn 20  http=200  4.342023s
```

The metrics leave the process every 5 s. Wait about 10 s, then plot the series
in Step 3.

**Step 3 — Plot the server's work profile in Metrics Explorer.** The chart is
described here, not captured.

- Wait about 10 s for the last export interval.
- Open **Monitoring → Metrics Explorer**.
- Click the **`<> PromQL`** toggle on the query row.
- Set the time range to **5 minutes**.
- Paste the query below and click **Run query**.

The query plots the server's per-turn work profile: turns, model calls, and
tool calls, each per minute. All three are `_count` rates of the same shape, so
they share a Y axis and track together. Each block filters on
`job="adk-metrics-server"`, the `OTEL_SERVICE_NAME` your server set, so only
your own server appears, not 2.1's `adk web` or the Cloud Run service from 2.3.
The `label_replace` names each line for the legend, and `or` returns all three
from one query.

```
label_replace(sum(rate({"gen_ai.invoke_agent.duration_count", job="adk-metrics-server"}[10m])) * 60, "series", "turns/min", "", "")
or
label_replace(sum(rate({"gen_ai.client.operation.duration_count", job="adk-metrics-server"}[10m])) * 60, "series", "model calls/min", "", "")
or
label_replace(sum(rate({"gen_ai.execute_tool.duration_count", job="adk-metrics-server"}[10m])) * 60, "series", "tool calls/min", "", "")
```

**Expected output** (illustrative; the same query through the API read these
values) — three lines that rise as the twenty turns land and fall once they stop,
peaking near:

```console
series=model calls/min   ~4
series=turns/min         ~2
series=tool calls/min    ~2
```

Model calls run about double turns because a baseline turn makes two model calls
and one tool call.

> [!IMPORTANT]
> **What it means.** Your own server exports the same six metric names as `adk web`
> and the Cloud Run service, and the identical work-profile query reads them
> back, distinguished by the `job` label you set. The two `client.*` metrics
> differ: with no genai instrumentation installed, they carry ADK's labels and the
> `gcp.vertex.agent` scope. The exporter is ADK's;
> the two lines wire it in. Nothing about the metrics themselves depends on the
> CLI.

[2.5](2.5-agent-runtime.md) asks whether a request-driven runtime, with no export
daemon at all, exports metrics.

## Deep dives

### What is the export interval, and why does it matter?

The `PeriodicExportingMetricReader` sends a batch on a fixed interval, and the
interval differs by route:

| Route | Interval | Set by |
|---|---|---|
| `--otel_to_cloud` (2.1 to 2.3) | 5 s | `MIN_EXPORT_INTERVAL_MS` |
| `get_gcp_exporters` (this page) | 5 s | `MIN_EXPORT_INTERVAL_MS` |
| OTLP env-var route ([2.6](2.6-other-backends.md)) | 60 s | `OTEL_METRIC_EXPORT_INTERVAL` |

That is why every read-back on the Google path waits about 10 s, two intervals,
before querying: one to fire and one for margin. On the env-var route you would
wait past 60 s instead. And on any route, a process that exits inside the interval
of its last turn exports nothing, because ADK installs the `MeterProvider` with
`shutdown_on_exit=False`. A long-running server never hits this; its reader keeps
firing on the interval. A short script does, which is why the Part 1 examples call
`force_flush()` ([1.1](../part-1/1.1-your-first-datapoint.md)) instead of relying
on the interval.

### Why does a script need `gcp.project_id`?

The CLI builds its resource with `get_gcp_resource` (`telemetry/google_cloud.py:298-352`),
which only the CLI calls (`cli/api_server.py:712`). Off Agent Runtime, it merges
two detectors: the OTel detector reads `OTEL_RESOURCE_ATTRIBUTES` and
`OTEL_SERVICE_NAME`, and the Google Cloud detector reads the metadata server,
and it adds `gcp.project_id`. `get_gcp_exporters` builds exporters only. A
standalone script that skips `get_gcp_resource` has no `gcp.project_id`, and
every batch is a `400` whose body reads `Resource is missing required attribute
"gcp.project_id"`. That is why the script passes its own resource with
`gcp.project_id` to `maybe_set_otel_providers`.
