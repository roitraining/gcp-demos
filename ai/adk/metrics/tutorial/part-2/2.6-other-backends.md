# 2.6 · Other backends

*Part 2 · Collect*

> [!NOTE]
> **Why you are here.** The same six metrics can go to any OTLP backend, not only
> Cloud Monitoring; only the exporter target changes. This is a reference page.
> Nothing here was run against a non-Google backend, and the rest of the tutorial
> stays on the Google path.

The reader is written to talk OTLP over HTTP. Cloud Monitoring is one OTLP
endpoint; Prometheus, Datadog, SigNoz, or any collector is another. You do not
touch the flag or the code, only the endpoint variables.

## CLI-launched servers: env vars replace the flag

For `adk web` and `adk api_server`, drop `--otel_to_cloud` and set the OTLP
metric endpoint instead. ADK uses the generic OTLP exporter whenever the flag is
absent and an endpoint variable is present.

| Variable | What it sets | Default |
|---|---|---|
| `OTEL_EXPORTER_OTLP_METRICS_ENDPOINT` | the metrics endpoint (or use the base var for all signals) | none |
| `OTEL_EXPORTER_OTLP_ENDPOINT` | one base endpoint for every signal | none |
| `OTEL_EXPORTER_OTLP_HEADERS` | auth or tenant headers, e.g. `signoz-access-token=…` | none |
| `OTEL_METRIC_EXPORT_INTERVAL` | export interval, milliseconds | 60000 |
| `OTEL_SERVICE_NAME` / `OTEL_RESOURCE_ATTRIBUTES` | resource identity on every signal | none |

Two limits carry over from the Google path:

- **Shell exports, not `.env`**, for CLI-launched servers, the same startup-order
  reason as 2.1. On your own server ([2.4](2.4-your-own-server.md)) they can live
  in `.env`.
- **HTTP/protobuf only.** ADK imports the `http/protobuf` OTLP exporter and no
  gRPC exporter, so `OTEL_EXPORTER_OTLP_PROTOCOL=grpc` has no effect.

Note the interval: the env-var route defaults to 60 s, not the 5 s of
`--otel_to_cloud`, so a read-back waits past a minute. `OTEL_METRIC_EXPORT_INTERVAL`
changes it.

## Your own server: the no-arg call

On the server from [2.4](2.4-your-own-server.md), set the same env vars in the
process, then call `maybe_set_otel_providers()` with no arguments instead of
passing the GCP hooks. It appends the generic OTLP exporter from those variables:

```python
from google.adk.telemetry.setup import maybe_set_otel_providers
maybe_set_otel_providers()          # reads the OTEL_* vars from the environment
```

## SigNoz, as one documented example

SigNoz accepts OTLP directly. Point the endpoint at your SigNoz collector and pass
the ingestion key as a header:

```bash
export OTEL_EXPORTER_OTLP_METRICS_ENDPOINT=https://ingest.<region>.signoz.cloud:443/v1/metrics
export OTEL_EXPORTER_OTLP_HEADERS="signoz-access-token=<your-key>"
adk web ./
```

SigNoz ships a Google-ADK dashboard (token usage split and over time, error rate,
p95 latency, request duration, model and agent distribution). That panel list is a
good target for the Cloud Monitoring dashboard [Part 3](../part-3/index.md) builds
from these same metrics. The ADK docs keep the current backend list on their
observability pages.
