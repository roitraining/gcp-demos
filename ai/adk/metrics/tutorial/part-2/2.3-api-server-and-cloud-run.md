# 2.3 · `adk api_server` and Cloud Run

*Part 2 · Collect*

> [!NOTE]
> **Why you are here.** 2.1 needed `OTEL_RESOURCE_ATTRIBUTES` because a laptop has
> no metadata server. This page deploys the same flag to Cloud Run, where the
> resource detector fills `location` in for you, then plots the Cloud Run
> service's per-turn work profile in the Console, with the region set by the
> platform, not you.

`adk api_server` is the same server `adk web` wraps, without the dev UI, and
`adk deploy cloud_run --otel_to_cloud` bakes the flag into the container's start
command. The process inside Cloud Run installs the same exporters, and its
resource detector reads the region and instance from the metadata server. You set
no `OTEL_RESOURCE_ATTRIBUTES` in the deploy.

**Step 1 — Deploy.** `--otel_to_cloud` sets up the Cloud exporters at startup, so
the container needs them installed. ADK's generated Dockerfile installs only the
base `google-adk`, so a `requirements.txt` in the agent directory
([demo_agent/requirements.txt](../../demo_agent/requirements.txt)) lists the
exporter packages; `adk deploy` installs it into the image. Without it the
revision crashes on boot with `ModuleNotFoundError: No module named
'opentelemetry.exporter'` and the deploy fails the health check.

**Command:**

```bash
.venv/bin/adk deploy cloud_run \
  --project="$PROJECT_ID" \
  --region="$REGION" \
  --service_name=adk-metrics-otel \
  --otel_to_cloud \
  ./demo_agent \
  -- \
  --allow-unauthenticated \
  --set-env-vars="GOOGLE_GENAI_USE_VERTEXAI=TRUE,GOOGLE_CLOUD_PROJECT=$PROJECT_ID,GOOGLE_CLOUD_LOCATION=global"
```

Everything after `--` passes straight to `gcloud run deploy`.
`GOOGLE_CLOUD_LOCATION=global` is repeated here because ADK's generated Dockerfile
sets it to the service region, which is wrong for the model; the explicit env var
wins. `adk deploy` can exit `0` on a failed build, so the curl in Step 2 is the
real check.

**Step 2 — Drive turns against the URL.** Grab the service URL, create a session,
and fire baseline load at it.

**Command:**

```bash
export HOST=$(gcloud run services describe adk-metrics-otel \
  --project="$PROJECT_ID" --region="$REGION" --format='value(status.url)')
load/turns.sh baseline 20
```

`load/turns.sh` reads the server base URL from `HOST` (default the local
server), so exporting `HOST` points the same script at Cloud Run. Each turn
prints its status and elapsed time.

**Expected output** — twenty answered turns from Cloud Run:

```console
baseline        turn   1  http=200  3.41s
baseline        turn   2  http=200  2.98s
...
baseline        turn  20  http=200  3.04s
```

**Step 3 — Plot the service's work profile in Metrics Explorer.** The chart is
described here, not captured.

- Wait about 10 s for the last export interval.
- Open **Monitoring → Metrics Explorer**.
- Click the **`<> PromQL`** toggle on the query row.
- Set the time range to **5 minutes**.
- Paste the query below and click **Run query**.

The query plots the service's per-turn work profile: turns, model calls, and
tool calls, each per minute. All three are `_count` rates of the same shape, so
they share a Y axis and track together. Each block filters on
`job="adk-metrics-otel"`, the service name you passed to `--service_name`, so
only the Cloud Run service appears, not the laptop from 2.1. The `label_replace`
names each line for the legend, and `or` returns all three from one query.

```
label_replace(sum(rate({"gen_ai.invoke_agent.duration_count", job="adk-metrics-otel"}[5m])) * 60, "series", "turns/min", "", "")
or
label_replace(sum(rate({"gen_ai.client.operation.duration_count", job="adk-metrics-otel"}[5m])) * 60, "series", "model calls/min", "", "")
or
label_replace(sum(rate({"gen_ai.execute_tool.duration_count", job="adk-metrics-otel"}[5m])) * 60, "series", "tool calls/min", "", "")
```

**Expected output** — three lines that rise as the twenty turns land and fall
once they stop:

```console
series=model calls/min   ~10
series=turns/min         ~5
series=tool calls/min    ~5
```

Model calls run about double turns because a baseline turn is two model calls
and one tool call; the gaps between the lines are that 2:1:1 profile.

> [!IMPORTANT]
> **What it means.** The `job` filter came from the service name you chose, but
> `location` you never set: the resource detector read the real region from the
> metadata server and stamped it on every series. That is why the `400` that hit
> the laptop in 2.1 cannot happen here, where the laptop had no metadata server
> to supply `location`. A deployed ADK service needs the flag and nothing else
> to land metrics correctly. Part 3 reads these same `_count` rates, plus
> `_bucket` quantiles and `_sum` rates, one signal at a time.

**Step 4 — Tear down.**

**Command:**

```bash
gcloud run services delete adk-metrics-otel \
  --project="$PROJECT_ID" --region="$REGION" --quiet
```

[2.4](2.4-your-own-server.md) is the one route where the CLI does not start the
process, so you install the exporters yourself.
