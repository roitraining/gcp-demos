# 2.1 · `adk web --otel_to_cloud`

*Part 2 · Collect*

> [!NOTE]
> **Why you are here.** One flag turns the console reader from Part 1 into a
> cloud exporter. This page runs `baseline` under load through `adk web
> --otel_to_cloud` and confirms the series reached Cloud Monitoring. How to read
> a metric well is [Part 3](../part-3/index.md); this page only asks whether it
> landed.

`adk web --otel_to_cloud` installs the same `PeriodicExportingMetricReader` you
saw in Part 1, pointed at `telemetry.googleapis.com` instead of the console. No
agent code changes. Two things must be set in the shell first: a service name and
the resource labels the metrics backend requires. See
[Why metrics need OTEL_RESOURCE_ATTRIBUTES](#why-metrics-need-otel_resource_attributes).

**Step 1 — Start the dev UI with the flag.**

**Command:**

```bash
source env.sh
adk web --otel_to_cloud ./
```

`env.sh` already exports `OTEL_SERVICE_NAME` and `OTEL_RESOURCE_ATTRIBUTES`
([00-setup](../00-setup.md)). They must be in the shell before `adk web` starts;
the agent's `.env` is read too late to set them, the same timing rule the logging
tutorial documents in its 5.2. Leave the server running.

**Step 2 — Drive twenty baseline turns.** In a second terminal, source the same
variables and fire the load.

**Command:**

```bash
source env.sh
load/turns.sh baseline 20
```

`load/turns.sh <scenario> [N]` sends N turns of the named scenario against the
running server and prints one line per turn, so you can count answered turns
against exported points. After the last turn it waits 10 s and then prints `good
to go`, so you read the series back only once the final batch has left the
process.

**Expected output** — one line per turn, all HTTP 200 (elapsed times vary), then
the wait and the go-ahead:

```console
baseline        turn   1  http=200  3.95s
baseline        turn   2  http=200  3.74s
...
baseline        turn  19  http=200  3.80s
baseline        turn  20  http=200  3.54s
waiting 10s for the final export interval...
good to go — the series are in Cloud Monitoring
```

> [!NOTE]
> **Why the wait.** The reader exports every 5 s ([2.4](2.4-your-own-server.md)
> explains the interval), so when the last turn returns its batch has not left the
> process yet. `turns.sh` waits past one more interval before printing `good to
> go`; set `EXPORT_WAIT=0` to skip it.

**Step 3 — Read the series back two ways.** This is your first read from Cloud
Monitoring, so you meet the same token-usage series through two front doors: the
Console and the PromQL API. Both run the same query and produce the same chart,
differing only in how you ask. Part 3 uses the PromQL API for the rest.

**Door 1 — Metrics Explorer Console.** The orientation view: confirm the series
landed and see it split by token type. In the Cloud console, open **Monitoring →
Metrics Explorer**, click the **`<> PromQL`** toggle on the query row, and paste
the tokens-per-type block from [queries/tokens.promql](../../queries/tokens.promql):

```
sum by ("gen_ai.token.type") (
  rate({"gen_ai.client.token.usage_sum"}[5m])
) * 60
```

Two lines appear, one per token type: input tokens run well above output. That
gap is the whole point. Door 2 runs this same query over the API and draws the
same two lines.

**Door 2 — PromQL endpoint.** The same query Door 1 pasted, now over the API. Ask
the `query_range` endpoint for the same window and write the response to
`out/metrics.json`.

**Command:**

```bash
export START=$(date -u -v-30M +%s)
export END=$(date -u +%s)
curl -s \
  "https://monitoring.googleapis.com/v1/projects/${PROJECT_ID}/location/global/prometheus/api/v1/query_range" \
  -H "Authorization: Bearer $(gcloud auth print-access-token)" \
  --data-urlencode 'query=sum by ("gen_ai.token.type") (rate({"gen_ai.client.token.usage_sum"}[5m])) * 60' \
  --data-urlencode "start=${START}" \
  --data-urlencode "end=${END}" \
  --data-urlencode 'step=60' \
  > out/metrics.json
```

The response writes to `out/metrics.json`. Open it in your editor to read it; in
VS Code:

```bash
code out/metrics.json
```

Both the metric name and the label keep their dots in the UTF-8 brace form, so
each is quoted; the unquoted `gen_ai_token_type` matches nothing. Part 3 covers
this addressing.

**Expected output** — two series, each a list of `[timestamp, value]` points over
the window (the same two lines Door 1 plotted):

```console
{ "data": { "resultType": "matrix", "result": [
  { "metric": { "gen_ai.token.type": "input"  }, "values": [ [..., "2888.4"], [..., "3375.4"], ... ] },
  { "metric": { "gen_ai.token.type": "output" }, "values": [ [..., "121.8"],  [..., "142.8"],  ... ] }
] } }
```

Now draw those two series as a chart, so you can set it beside Door 1's lines and
see they are the same data.

**Command:**

```bash
.venv/bin/python examples/plot_tokens.py
code out/tokens.png
```

**Expected output** — a two-line chart written to `out/tokens.png`: input runs
well above output, the same two lines Door 1 drew in the Console.

> [!IMPORTANT]
> **What it means.** Both doors ran the same query on one series. The Console drew
> it as two lines; the API returned the same points as JSON, which you rendered as
> the same two lines. Same data, two tools. The flag did the whole job: your
> process writes metrics to a backend, unchanged from Part 1 except for where the
> reader points.

[2.2](2.2-the-metric-catalog.md) lists every descriptor that arrived and names the
labels Cloud Monitoring gave them.

## Deep dives

### Why metrics need OTEL_RESOURCE_ATTRIBUTES

The Telemetry API stores OTLP metrics on the `prometheus_target` monitored
resource, which requires an `instance` and a real `location`. It derives them
from `service.instance.id` and `cloud.region` in `OTEL_RESOURCE_ATTRIBUTES`. On a
laptop, without those, every 5 s batch is rejected with a `400`, while the agent
keeps answering. `cloud.region` must be a real region, not `global`. On Cloud Run
and Agent Runtime the resource detector supplies both from the metadata server,
so the variable is not needed there ([2.3](2.3-api-server-and-cloud-run.md)). The
logging tutorial's 5.2 deep dive has the byte-level `400` body and the
attribute-by-attribute narrowing.

### What does an export outage look like?

The `export-outage` scenario is 2.1 run wrong on purpose: a healthy agent whose
telemetry is silently incomplete. Stop the server, clear the resource labels, and
restart the flag without them.

**Command:**

```bash
unset OTEL_RESOURCE_ATTRIBUTES
adk web --otel_to_cloud ./
```

Fire five baseline turns against it.

**Command:**

```bash
load/turns.sh baseline 5
```

Every turn answers. But terminal 1 now prints one `400` per batch, every 5 s, for
as long as the server runs:

**Expected output** — the repeating export error:

```console
ERROR - Failed to export metrics batch code: 400, reason: Bad Request
ERROR - Failed to export metrics batch code: 400, reason: Bad Request
ERROR - Failed to export metrics batch code: 400, reason: Bad Request
```

Read the token series back over the outage window and you get no new points: the
turns were answered, the numbers were recorded in process, and every batch that
tried to carry them out was rejected. Fixing it means restarting with the labels,
which discards the process totals accumulated so far.

> [!IMPORTANT]
> **What it means.** A healthy agent and complete telemetry are two different
> facts. Five answered turns and zero exported points can be true at the same
> time. Count answered turns (from `load/turns.sh`) against exported points before
> you conclude the agent is broken; here the agent was fine and only the export
> was failing.
