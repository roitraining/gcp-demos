# 2.1 · `adk web --otel_to_cloud`

*Part 2 · Collect*

> [!NOTE]
> **Why you are here.** Scenario `baseline`: did the metrics land? One flag turns
> Part 1's console reader into a cloud exporter, and this page confirms the series
> reached Cloud Monitoring.

`adk web --otel_to_cloud` installs a `PeriodicExportingMetricReader` pointed at
`telemetry.googleapis.com`. No agent code changes. The shell must first set a
service name and the resource labels the metrics backend requires. See
[Why do metrics need `OTEL_RESOURCE_ATTRIBUTES`?](#why-do-metrics-need-otel_resource_attributes)

**Step 1 — Start the dev UI with the flag.**

**Command:**

```bash
source env.sh
.venv/bin/adk web --otel_to_cloud ./
```

`env.sh` already exports `OTEL_SERVICE_NAME` and `OTEL_RESOURCE_ATTRIBUTES`
([00-setup](../00-setup.md)). They must be in the shell before `adk web` starts,
because the CLI builds the exporters before it reads the agent's `.env`. Leave the
server running.

**Step 2 — Drive twenty baseline turns.** In a second terminal, source the same
variables and fire the load.

**Command:**

```bash
source env.sh
load/turns.sh baseline 20
```

`load/turns.sh <scenario> [N]` sends N turns of the named scenario and prints one
line per turn. The reader exports every 5 s, so after the last turn the script
waits 10 s for the final batch before it prints `good to go`; set `EXPORT_WAIT=0`
to skip the wait.

**Expected output** — one line per turn, all HTTP 200 (elapsed times vary), then
the wait and the go-ahead:

```console
baseline        turn   1  http=200  3.95s
baseline        turn   2  http=200  3.74s
...
baseline        turn  19  http=200  3.80s
baseline        turn  20  http=200  3.54s
waiting 10s for the final export interval...
good to go — the series are in Cloud Monitoring
```

**Step 3 — Read the series back two ways.** Read the same token-usage query in the
Console and through the PromQL API. Part 3 uses the API.

**Option A, Metrics Explorer.**

- Open **Monitoring → Metrics Explorer**.
- Click the **`<> PromQL`** toggle on the query row.
- Paste the tokens-per-type block from
  [queries/tokens.promql](../../queries/tokens.promql) below.

```
sum by ("gen_ai.token.type") (
  rate({"gen_ai.client.token.usage_sum"}[5m])
) * 60
```

Two lines appear, one per token type: input tokens run well above output.

**Option B, PromQL API.** The same query, now over the API. Ask the `query_range`
endpoint for the last 30 minutes and write the response to `out/tokens.json`.

**Command:**

```bash
export END=$(date -u +%s)
export START=$((END - 1800))
curl -s \
  "https://monitoring.googleapis.com/v1/projects/${PROJECT_ID}/location/global/prometheus/api/v1/query_range" \
  -H "Authorization: Bearer $(gcloud auth print-access-token)" \
  --data-urlencode 'query=sum by ("gen_ai.token.type") (rate({"gen_ai.client.token.usage_sum"}[5m])) * 60' \
  --data-urlencode "start=${START}" \
  --data-urlencode "end=${END}" \
  --data-urlencode 'step=60' \
  > out/tokens.json
```

Open `out/tokens.json` in your editor to read it; in VS Code:

```bash
code out/tokens.json
```

The metric name and the label keep their dots, so each is quoted; the unquoted
`gen_ai_token_type` matches nothing.

**Expected output** — two series, each a list of `[timestamp, value]` points over
the window (the same two lines Option A plotted):

```console
{ "data": { "resultType": "matrix", "result": [
  { "metric": { "gen_ai.token.type": "input"  }, "values": [ [..., "2888.4"], [..., "3375.4"], ... ] },
  { "metric": { "gen_ai.token.type": "output" }, "values": [ [..., "121.8"],  [..., "142.8"],  ... ] }
] } }
```

> [!IMPORTANT]
> **What it means.** Both options ran the same query on one series. The Console
> drew it as two lines; the API returned the same points as JSON. The flag did the
> whole job: your process writes metrics to a backend, unchanged from Part 1
> except for where the reader points. To draw the JSON as a chart, see
> [How do I chart the API response?](#how-do-i-chart-the-api-response)

[2.2](2.2-the-metric-catalog.md) lists every descriptor that arrived and names the
labels Cloud Monitoring gave them.

## Deep dives

### How do I chart the API response?

[examples/plot_tokens.py](../../examples/plot_tokens.py) draws the two series in
`out/tokens.json` as a chart, so you can set it beside Option A's lines.

**Command:**

```bash
.venv/bin/python examples/plot_tokens.py
code out/tokens.png
```

**Expected output** — a two-line chart written to `out/tokens.png`: input runs
well above output, the same two lines Option A drew in the Console.

### Why do metrics need `OTEL_RESOURCE_ATTRIBUTES`?

The Telemetry API stores OTLP metrics on the `prometheus_target` monitored
resource, which requires an `instance` and a real `location`. It derives them
from `service.instance.id` and `cloud.region` in `OTEL_RESOURCE_ATTRIBUTES`. On a
laptop, without those, every 5 s batch is rejected with a `400`, while the agent
keeps answering. `cloud.region` must be a real region, not `global`. On Cloud Run,
the resource detector reads both from the metadata server
([2.3](2.3-api-server-and-cloud-run.md)). On Agent Runtime, ADK builds the
resource from the runtime's environment variables. The logging tutorial's
[5.2](../../../logging/tutorial/part-5/5.2-otel-to-cloud.md) shows the full `400`
body.

### What does an export outage look like?

The `export-outage` scenario runs 2.1 wrong on purpose. Stop the server with
`Ctrl+C` and restart it without the resource labels.

**Command:**

```bash
unset OTEL_RESOURCE_ATTRIBUTES
.venv/bin/adk web --otel_to_cloud ./
```

In the second terminal, fire five baseline turns against it.

**Command:**

```bash
load/turns.sh baseline 5
```

**Expected output** — five answered turns, and the usual go-ahead:

```console
baseline        turn   1  http=200  4.70s
baseline        turn   2  http=200  3.54s
baseline        turn   3  http=200  3.51s
baseline        turn   4  http=200  4.21s
baseline        turn   5  http=200  3.34s
waiting 10s for the final export interval...
good to go — the series are in Cloud Monitoring
```

> [!WARNING]
> `turns.sh` prints `good to go` because every turn answered, but here Cloud
> Monitoring rejected every batch.

Terminal 1 shows one `400` per batch, every 5 s.

**Expected output** — the repeating export error:

```console
2026-10-02 20:44:21,106 - ERROR - __init__.py:294 - Failed to export metrics batch code: 400, reason: Bad Request
2026-10-02 20:44:26,181 - ERROR - __init__.py:294 - Failed to export metrics batch code: 400, reason: Bad Request
2026-10-02 20:44:31,243 - ERROR - __init__.py:294 - Failed to export metrics batch code: 400, reason: Bad Request
```

Read the turn count back.

**Command:**

```bash
curl -s \
  "https://monitoring.googleapis.com/v1/projects/${PROJECT_ID}/location/global/prometheus/api/v1/query" \
  -H "Authorization: Bearer $(gcloud auth print-access-token)" \
  --data-urlencode 'query=sum({"gen_ai.invoke_agent.duration_count", job="adk-metrics"})'
```

**Expected output** — still the twenty turns from Step 2:

```console
{"status":"success","data":{"resultType":"vector","result":[{"metric":{},"value":[1790999089.41,"20"]}]}}
```

Fixing it means restarting with the labels, which discards the process totals
accumulated so far.

> [!IMPORTANT]
> **What it means.** A healthy agent and complete telemetry are different facts:
> five answered turns and zero exported points. Count answered turns against
> exported points before you conclude the agent is broken.
