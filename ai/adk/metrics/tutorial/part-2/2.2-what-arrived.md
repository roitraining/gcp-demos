# 2.2 · What arrived

*Part 2 · Collect*

> [!NOTE]
> **Why you are here.** 2.1 confirmed one series landed. This page lists every
> descriptor Cloud Monitoring created from the `baseline` run, so you can check
> that all six Part 1 metrics made it and learn what they are called here. No
> query language yet.

A descriptor is Cloud Monitoring's record of a metric's existence: its name,
kind, and labels. Listing them is the way to discover what a run created without
querying any values. The PromQL proxy has no `/series` endpoint, so the
Monitoring API `metricDescriptors.list` is the tool for this.

**👉 Do this.** List the descriptors under the `gen_ai` prefix.

**Command:**

```bash
export TOKEN=$(gcloud auth print-access-token)
curl -s -H "Authorization: Bearer $TOKEN" \
  "https://monitoring.googleapis.com/v3/projects/$PROJECT_ID/metricDescriptors?filter=metric.type=starts_with(%22prometheus.googleapis.com/gen_ai%22)" \
  | python3 -c 'import json,sys;[print(m["type"]) for m in sorted(json.load(sys.stdin)["metricDescriptors"],key=lambda m:m["type"])]'
```

**Expected output** — one descriptor per metric that arrived, each ending
`/histogram`:

```console
prometheus.googleapis.com/gen_ai.client.operation.duration/histogram
prometheus.googleapis.com/gen_ai.client.token.usage/histogram
prometheus.googleapis.com/gen_ai.execute_tool.duration/histogram
prometheus.googleapis.com/gen_ai.invoke_agent.duration/histogram
prometheus.googleapis.com/gen_ai.invoke_agent.inference_calls/histogram
prometheus.googleapis.com/gen_ai.invoke_agent.tool_calls/histogram
prometheus.googleapis.com/gen_ai.invoke_workflow.duration/histogram
```

> [!IMPORTANT]
> **What it means.** All six single-agent metrics from Part 1 crossed the wire.
> The seventh, `gen_ai.invoke_workflow.duration`, is present only because an
> earlier workflow run ([1.5](../part-1/1.5-workflow-grain-metrics.md)) created
> its descriptor and descriptors persist once created; a single `baseline` run
> writes to six of these, not seven. No `adk.experimental.*`, because the flag
> that emits them was off ([1.4](../part-1/1.4-the-experimental-family.md)). The
> descriptor list is the catalog a dashboard or an alert picks metrics from.

Each series carries the labels the run stamped. Read one metric's live series to
see them.

**Command:**

```bash
curl -s -H "Authorization: Bearer $TOKEN" \
  --data-urlencode 'query={"gen_ai.client.token.usage_count"}' \
  "https://monitoring.googleapis.com/v1/projects/$PROJECT_ID/location/global/prometheus/api/v1/query" \
  | python3 -c 'import json,sys;r=json.load(sys.stdin)["data"]["result"];print("\n".join(sorted(r[0]["metric"])))'
```

**Expected output** — the label keys on the token series (metric labels plus the
resource and `otel_scope_*` labels Cloud Monitoring adds):

```console
gen_ai.operation.name
gen_ai.request.model
gen_ai.system
gen_ai.token.type
instance
job
location
otel_scope_gcp.client.name
otel_scope_gcp.client.repo
otel_scope_gcp.client.version
otel_scope_name
otel_scope_pypi.package.name
otel_scope_version
project_id
```

There is no `gen_ai.agent.name` here: the client metrics come from the genai
instrumentation scope, not ADK's meter, so they do not carry the agent label
that `execute_tool.duration` and `invoke_agent.duration` do.

The metrics and the labels beyond the resource and `otel_scope_*` set that each
carries here. The two scopes matter: the `client.*` metrics come from the genai
instrumentation scope and carry no `gen_ai.agent.name`, while ADK's own metrics
do (see [3.4](../part-3/3.4-tokens-and-cost.md)):

| Cloud Monitoring metric | `otel_scope_name` | Labels beyond `otel_scope_*` |
|---|---|---|
| `.../gen_ai.client.operation.duration/histogram` | `opentelemetry.instrumentation.google_genai` | `gen_ai.operation.name`, `gen_ai.system`, `gen_ai.request.model`, `gen_ai.response.model`, `error.type` |
| `.../gen_ai.client.token.usage/histogram` | `opentelemetry.instrumentation.google_genai` | same, plus `gen_ai.token.type` |
| `.../gen_ai.execute_tool.duration/histogram` | `gcp.vertex.agent` | `gen_ai.agent.name`, `gen_ai.tool.name`, `gen_ai.tool.type`, `error.type` |
| `.../gen_ai.invoke_agent.duration/histogram` | `gcp.vertex.agent` | `gen_ai.agent.name`, `error.type` |
| `.../gen_ai.invoke_agent.inference_calls/histogram` | `gen_ai.agent.name` |
| `.../gen_ai.invoke_agent.tool_calls/histogram` | `gen_ai.agent.name` |

> [!NOTE]
> Every descriptor also carries `otel_scope_name` and `otel_scope_version`, the
> instrumentation scope that recorded it (`gcp.vertex.agent`). They matter when
> you sum across series; [3.4](../part-3/index.md) uses them.

instance and checks that its resource labels fill themselves in.

## Deep dives

### Why is there a `/histogram` on every name?

Cloud Monitoring's OTLP ingestion renames every metric to
`prometheus.googleapis.com/<otlp name>/<point kind>`. The prefix marks the
Prometheus-compatible store; the dots in the original name survive; and the
trailing segment is the point kind. All six Part 1 metrics are histograms, so all
six end in `/histogram`. The one custom instrument in [3.7](../part-3/index.md) is
a `Counter`, so it arrives as `.../tutorial.weather.requests/counter`. The suffix
is the point kind, not part of the name you chose. Because the name keeps its
dots, PromQL cannot address it in the bare form; it needs the UTF-8 brace form
with a `_sum` / `_count` / `_bucket` suffix, which is why the 2.1 query looked the
way it did. Part 3 works entirely in that form.
