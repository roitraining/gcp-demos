# 2.2 · What arrived

*Part 2 · Collect*

> [!NOTE]
> **Why you are here.** 2.1 confirmed one series landed. This page lists every
> descriptor Cloud Monitoring created from the `baseline` run, so you can check
> that all six Part 1 metrics made it and learn what they are called here. No
> query language yet.

A descriptor is Cloud Monitoring's record of a metric's existence: its name,
kind, and labels. Listing them is the way to discover what a run created without
querying any values. The PromQL proxy has no `/series` endpoint, so the
Monitoring API `metricDescriptors.list` is the tool for this.

**👉 Do this.** List the descriptors under the `gen_ai` prefix.

**Command:**

```bash
gcloud monitoring metrics-descriptors list \
  --project="$PROJECT_ID" \
  --filter='metric.type=starts_with("prometheus.googleapis.com/gen_ai")' \
  --format='value(type)'
```

**Expected output** — one descriptor per metric that arrived:

```console
NEEDS-RUN: metricDescriptors.list on jwd-gcp-demos filtered to prometheus.googleapis.com/gen_ai — six descriptors, one per single-agent metric, each ending /histogram: gen_ai.client.operation.duration, gen_ai.client.token.usage, gen_ai.execute_tool.duration, gen_ai.invoke_agent.duration, gen_ai.invoke_agent.inference_calls, gen_ai.invoke_agent.tool_calls
```

> [!IMPORTANT]
> **What it means.** All six single-agent metrics from Part 1 crossed the wire.
> No `gen_ai.invoke_workflow.duration`, because `baseline` runs a single agent and
> never invokes a workflow ([1.5](../part-1/1.5-workflow-grain-metrics.md)). No
> `adk.experimental.*`, because the flag that emits them was off
> ([1.4](../part-1/1.4-the-experimental-family.md)). The descriptor list is the
> catalog: it is what a dashboard or an alert picks metrics from.

Each descriptor carries the labels the run stamped. Read one descriptor in full
to see them.

**Command:**

```bash
gcloud monitoring metrics-descriptors describe \
  "prometheus.googleapis.com/gen_ai.client.token.usage/histogram" \
  --project="$PROJECT_ID"
```

**Expected output** — the descriptor's kind, value type, and labels:

```console
NEEDS-RUN: describe prometheus.googleapis.com/gen_ai.client.token.usage/histogram — metricKind CUMULATIVE, valueType DISTRIBUTION, labels incl gen_ai.agent.name, gen_ai.request.model, gen_ai.response.model, gen_ai.provider.name, gen_ai.operation.name, gen_ai.system, gen_ai.token.type, error.type, and otel_scope_name/otel_scope_version
```

The six metrics and the labels beyond `otel_scope_*` that each carries here:

| Cloud Monitoring metric | Labels beyond `otel_scope_*` |
|---|---|
| `.../gen_ai.client.operation.duration/histogram` | `gen_ai.agent.name`, `gen_ai.operation.name`, `gen_ai.provider.name`, `gen_ai.system`, `gen_ai.request.model`, `gen_ai.response.model`, `error.type` |
| `.../gen_ai.client.token.usage/histogram` | same, plus `gen_ai.token.type` |
| `.../gen_ai.execute_tool.duration/histogram` | `gen_ai.agent.name`, `gen_ai.tool.name`, `gen_ai.tool.type` |
| `.../gen_ai.invoke_agent.duration/histogram` | `gen_ai.agent.name`, `error.type` |
| `.../gen_ai.invoke_agent.inference_calls/histogram` | `gen_ai.agent.name` |
| `.../gen_ai.invoke_agent.tool_calls/histogram` | `gen_ai.agent.name` |

> [!NOTE]
> Every descriptor also carries `otel_scope_name` and `otel_scope_version`, the
> instrumentation scope that recorded it (`gcp.vertex.agent`). They matter when
> you sum across series; [3.4](../part-3/index.md) uses them.

[2.3](2.3-api-server-and-cloud-run.md) sends the same metrics from a deployed
instance and checks that its resource labels fill themselves in.

## Deep dives

### Why is there a `/histogram` on every name?

Cloud Monitoring's OTLP ingestion renames every metric to
`prometheus.googleapis.com/<otlp name>/<point kind>`. The prefix marks the
Prometheus-compatible store; the dots in the original name survive; and the
trailing segment is the point kind. All six Part 1 metrics are histograms, so all
six end in `/histogram`. The one custom instrument in [3.7](../part-3/index.md) is
a `Counter`, so it arrives as `.../tutorial.weather.requests/counter`. The suffix
is the point kind, not part of the name you chose. Because the name keeps its
dots, PromQL cannot address it in the bare form; it needs the UTF-8 brace form
with a `_sum` / `_count` / `_bucket` suffix, which is why the 2.1 query looked the
way it did. Part 3 works entirely in that form.
