# 2.5 · Agent Runtime

*Part 2 · Collect*

> [!NOTE]
> **Why you are here.** Cloud Run ran a long-lived process with a 5 s export
> daemon. Agent Runtime bills only during a request, so that daemon would be
> frozen between turns. This page deploys there and checks whether the same six
> series still land.

`adk deploy agent_engine --otel_to_cloud` packages the agent, builds a container,
and runs it on Agent Runtime. Two things about this deploy are unlike Cloud Run,
and both bite before any metric is emitted.

**Step 1 — Install the deploy SDK locally.** `deploy agent_engine` drives the
deployment from your machine by calling the Reasoning Engine API through the
Vertex AI SDK (`vertexai`), so that SDK must be in your own venv. This is unlike
`deploy cloud_run`, which shells out to `gcloud` and needs no extra Python
package. Without it the deploy fails with `No module named 'vertexai'` before any
resource is created.

**Command:**

```bash
.venv/bin/pip install "google-cloud-aiplatform[agent-engines]"
```

**Step 2 — Point the model at the global endpoint.** Agent Runtime must deploy to
a region, but `GOOGLE_CLOUD_LOCATION` sets both the deploy region and the model
endpoint, and `gemini-3.7-flash` is served only on `global`. A regional deploy
then 404s on the first model call. Cloud Run solved this by overriding the env var
([2.3](2.3-api-server-and-cloud-run.md)); here the runtime needs the region, so
override only the model's client instead. The shared agent already does this in
[demo_agent/agent.py](../../demo_agent/agent.py):

```python
model=Gemini(model="gemini-3.7-flash", client_kwargs={"location": "global"})
```

`client_kwargs` passes straight to the model's `google.genai.Client`
(`google/adk/models/google_llm.py:415`), so only the model call goes to `global`
while the deploy stays regional.

**Step 3 — Deploy.** As with Cloud Run, `--otel_to_cloud` sets up the exporters at
startup, so the container needs them installed. ADK's generated Dockerfile
installs only base `google-adk`, so the exporter packages come from
[demo_agent/requirements.txt](../../demo_agent/requirements.txt), same as 2.3.

**Command:**

```bash
.venv/bin/adk deploy agent_engine \
  --project="$PROJECT_ID" \
  --region="$REGION" \
  --display_name=adk-metrics-ae \
  --otel_to_cloud \
  ./demo_agent
```

Note the reasoning-engine id it prints (a long number); the next step needs it.

**Step 4 — Drive turns and wait.** Agent Runtime is not an HTTP server, so you
invoke the deployed engine through the SDK, not `load/turns.sh`.
[load/ae_turns.py](../../load/ae_turns.py) finds the engine by the
`adk-metrics-ae` display name you deployed, drives ten turns, and sleeps for the
export margin, so you never copy the reasoning-engine id and can go straight to
the Console.

**Command:**

```bash
.venv/bin/python load/ae_turns.py
```

**Expected output** — the id it found, ten answered turns, then the wait (a cold
engine may throw a transient `FailedPrecondition` on the first turn or two; the
script retries):

```console
using adk-metrics-ae: 976002936872108032
turn 1 ok
turn 2 ok
...
turn 10 ok
answered 10 of 10; waiting 15s for export...
```

**Step 5 — Plot the work profile in Metrics Explorer.** Same three-line work
profile as 2.3 and 2.4, filtered on the reasoning-engine id as `job` instead of a
name you chose. The chart is described here, not captured.

- Open **Monitoring → Metrics Explorer**.
- Click the **`<> PromQL`** toggle on the query row.
- Set the time range to **5 minutes**.
- Replace `<reasoning-engine-id>` in each block with the id Step 4 printed.
- Paste the query below and click **Run query**.

```
label_replace(sum(rate({"gen_ai.invoke_agent.duration_count", job="<reasoning-engine-id>"}[5m])) * 60, "series", "turns/min", "", "")
or
label_replace(sum(rate({"gen_ai.client.operation.duration_count", job="<reasoning-engine-id>"}[5m])) * 60, "series", "model calls/min", "", "")
or
label_replace(sum(rate({"gen_ai.execute_tool.duration_count", job="<reasoning-engine-id>"}[5m])) * 60, "series", "tool calls/min", "", "")
```

**Expected output** — the same 2:1:1 profile, three lines that rise and fall with
the ten turns. The per-minute rates are lower than 2.3 and 2.4 because this page
drives ten turns, not twenty:

```console
series=model calls/min   ~3.6
series=turns/min         ~1.8
series=tool calls/min    ~1.8
```

> [!IMPORTANT]
> **What it means.** Agent Runtime exports the same six `gen_ai.*` series as every
> other route, so the identical work-profile query reads them back. The result is
> positive, unlike the logging tutorial's negative for logs and traces on the same
> runtime. Two labels differ: `job` is the numeric reasoning-engine id, not a name
> you set, and `instance` is a runtime-supplied id. These sit beside Agent
> Runtime's own built-in service metrics, which Step 6 reads.

**Step 6 — Read the built-in service metrics.** The six `gen_ai.*` series are your
application's, exported by ADK. Agent Runtime also emits its own infrastructure
metrics with no setup, on the `aiplatform.googleapis.com/ReasoningEngine`
resource: request count, request latencies, and container CPU and memory. They
answer "is the service healthy," where the `gen_ai.*` series answer "what is the
agent doing." Read one with PromQL, the same way as Step 5; the builder tab's
metric list hides these until they have recent data.

- Open **Monitoring → Metrics Explorer**.
- Click the **`<> PromQL`** toggle on the query row.
- Set the time range to **5 minutes**.
- Paste the query below and click **Run query**.

```
{"aiplatform.googleapis.com/reasoning_engine/request_count"}
```

**Expected output** — one series on the `ReasoningEngine` resource, keyed by
`reasoning_engine_id` (not `job`), that tracks your turns:

```console
{reasoning_engine_id="4264756564759412736", location="us-central1"}   12
```

> [!IMPORTANT]
> **What it means.** This metric comes from the platform, not your code: Agent
> Runtime meters every deployed engine the way Cloud Run meters a service. Health
> lives here on the `ReasoningEngine` resource, keyed by `reasoning_engine_id`;
> agent behavior lives in the `gen_ai.*` series from Step 5, keyed by `job`. Both
> describe the same turns from opposite sides.

**Step 7 — Tear down.** [load/ae_delete.py](../../load/ae_delete.py) deletes the
engine it finds by display name, so no id is needed here either.

**Command:**

```bash
.venv/bin/python load/ae_delete.py
```

[2.6](2.6-other-backends.md) points the same metrics at a non-Google backend.

## Deep dives

### How does the request-driven reader work, and why is it different?

Every other route installs a `PeriodicExportingMetricReader` that flushes on a 5 s
daemon thread ([2.4](2.4-your-own-server.md#what-is-the-export-interval-and-why-does-it-matter)).
Agent Runtime installs a `_RequestDrivenMetricReader` instead
(`google/adk/telemetry/_agent_engine_metric_exporter.py:192`), selected when
`GOOGLE_CLOUD_AGENT_ENGINE_ID` is set (`google/adk/telemetry/google_cloud.py:244`).

The swap is not cosmetic. Agent Runtime bills and schedules CPU only while a
request is in flight, so a background daemon would be frozen between turns and its
5 s tick would rarely fire. The request-driven reader collects from the request
lifecycle instead: a baseline flush after each response is sent, plus a
mid-request catch-up if a long turn runs past 1.5× the interval
(`_agent_engine_metric_exporter.py:295-337`). That is why the wait in Step 4
lives in the script rather than being a fixed
interval you count off: the points leave as the turns complete, not on a clock.
