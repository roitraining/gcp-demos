# 2.5 · Agent Runtime

*Part 2 · Collect*

> [!NOTE]
> **Why you are here.** Cloud Run runs a long-lived process with a background
> export thread. Agent Runtime does not: it exports on the request lifecycle
> instead. This page deploys there and checks whether metrics surface at all.

Agent Runtime installs a `_RequestDrivenMetricReader` rather than the periodic
reader. When `GOOGLE_CLOUD_AGENT_ENGINE_ID` is set, ADK swaps the background
export thread for one that collects and flushes on the request lifecycle, so
there is no 5 s daemon. Whether metrics reach Cloud Monitoring through that path
is the open question this page answers with a real run; the logging tutorial found
a negative for logs and traces on Agent Runtime, and metrics use a different
reader, so the result could differ.

**Step 1 — Deploy to Agent Runtime with the flag.** The deploy packages and
pushes from your machine, so it needs the Agent Engine SDK installed locally:
`.venv/bin/pip install "google-cloud-aiplatform[agent-engines]"`. Without it the
deploy fails with `No module named 'vertexai'` before any resource is created.
The agent's container deps come from
[demo_agent/requirements.txt](../../demo_agent/requirements.txt), same as Cloud
Run.

**Command:**

```bash
.venv/bin/adk deploy agent_engine \
  --project="$PROJECT_ID" \
  --region="$REGION" \
  --display_name=adk-metrics-ae \
  --otel_to_cloud \
  ./demo_agent
```

Note the reasoning-engine resource name it prints; you invoke that in Step 2.

**Step 2 — Drive turns.** Agent Runtime is not an HTTP server you can point
`load/turns.sh` at; you invoke the deployed engine through the Agent Engine SDK.
Set `RESOURCE` to the name from Step 1.

**Command:**

```bash
.venv/bin/python -c '
import vertexai
from vertexai import agent_engines
import os
vertexai.init(project=os.environ["PROJECT_ID"], location=os.environ["REGION"])
ae = agent_engines.get(os.environ["RESOURCE"])
for i in range(10):
    s = ae.create_session(user_id="load-user")
    sid = s["id"] if isinstance(s, dict) else s.id
    for _ in ae.stream_query(user_id="load-user", session_id=sid,
                             message="What'\''s the weather in London?"):
        pass
    print("turn", i + 1, "ok")
'
```

**Expected output:** ten answered turns (a cold engine may throw a transient
`FailedPrecondition` on the first one or two; rerun those):

```console
turn 1 ok
turn 2 ok
...
turn 10 ok
```

**Step 3 — Read the series back.** Wait about 20 s, then look for a series whose
`job` is the reasoning-engine id.

**Command:**

```bash
curl -s \
  "https://monitoring.googleapis.com/v1/projects/${PROJECT_ID}/location/global/prometheus/api/v1/query" \
  -H "Authorization: Bearer $(gcloud auth print-access-token)" \
  --data-urlencode 'query={"gen_ai.invoke_agent.duration_count"}'
```

**Expected output** — a new series carrying the reasoning-engine id as `job` and
a runtime-supplied `instance`, alongside any earlier laptop series:

```console
{"job":"3223862100883406848","location":"us-central1","instance":"8f0494286f12..."}  <count>
```

> [!IMPORTANT]
> **What it means.** Agent Runtime exports metrics. The request-driven reader
> (`_RequestDrivenMetricReader`) collects on the request lifecycle rather than a
> daemon interval, and the points reach Cloud Monitoring as the same series as
> every other route, tagged with the reasoning-engine id. This is a positive
> result, unlike the logging tutorial's negative for logs and traces on the same
> runtime: metrics differ from those signals, so this route lands the same
> `gen_ai.*` series you read on every other page in this part.

**Step 4 — Tear down.** Delete the reasoning engine through the SDK, using the
resource name from Step 1.

**Command:**

```bash
.venv/bin/python -c '
import vertexai, os
from vertexai import agent_engines
vertexai.init(project=os.environ["PROJECT_ID"], location=os.environ["REGION"])
agent_engines.get(os.environ["RESOURCE"]).delete(force=True)
print("deleted", os.environ["RESOURCE"])
'
```
