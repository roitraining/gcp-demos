# 2.5 · Agent Runtime

*Part 2 · Collect*

> [!NOTE]
> **Why you are here.** Scenario `baseline`: does a request-driven runtime export
> at all? Agent Runtime bills only during a request, so Cloud Run's 5 s export
> daemon would be frozen between turns; this page checks whether the same six
> series still land.

`adk deploy agent_engine --otel_to_cloud` packages the agent, builds a container,
and runs it on Agent Runtime. The shared agent already pins its model client to
the `global` endpoint while the deploy stays regional. See
[Why does the agent pin its model to `global`?](#why-does-the-agent-pin-its-model-to-global)

**Step 1 — Install the deploy SDK locally.** `deploy agent_engine` calls the
Reasoning Engine API from your machine through the Vertex AI SDK, so that SDK must
be in your venv. Without it the deploy fails with `No module named 'vertexai'`.

**Command:**

```bash
.venv/bin/pip install "google-cloud-aiplatform[agent-engines]"
```

**Step 2 — Deploy.** The exporter packages come from
[demo_agent/requirements.txt](../../demo_agent/requirements.txt), as in 2.3. The
deploy takes several minutes.

**Command:**

```bash
source env.sh
.venv/bin/adk deploy agent_engine \
  --project="$PROJECT_ID" \
  --region="$REGION" \
  --display_name=adk-metrics-ae \
  --otel_to_cloud \
  ./demo_agent
```

**Expected output** (trimmed) — the deploy has finished when it prints the new
engine's resource name:

```console
Copying agent source code...
...
Deploying to Agent Platform...
Created a new instance: projects/376236993953/locations/us-central1/reasoningEngines/6828072211849412608
...
Deployed to Agent Platform: projects/376236993953/locations/us-central1/reasoningEngines/6828072211849412608
```

**Step 3 — Drive turns and wait.** Agent Runtime is not an HTTP server, so
[load/ae_turns.py](../../load/ae_turns.py) drives it through the SDK: it finds the
engine by its `adk-metrics-ae` display name, prints its id, drives ten turns, and
waits for the export.

**Command:**

```bash
.venv/bin/python load/ae_turns.py
```

**Expected output** (turns 3 to 9 trimmed; the script retries a transient
`FailedPrecondition` from a cold engine):

```console
using adk-metrics-ae: 6828072211849412608
turn 1 ok
turn 2 ok
...
turn 10 ok
answered 10 of 10; waiting 15s for export...
```

**Step 4 — Plot the work profile in Metrics Explorer.** Same work profile as 2.3
and 2.4, filtered on the reasoning-engine id as `job`. The chart is described
here, not captured.

- Open **Monitoring → Metrics Explorer**.
- Click the **`<> PromQL`** toggle on the query row.
- Set the time range to **5 minutes**.
- Replace `<reasoning-engine-id>` in each block with the id Step 3 printed.
- Paste the query below and click **Run query**.

```
label_replace(sum(rate({"gen_ai.invoke_agent.duration_count", job="<reasoning-engine-id>"}[10m])) * 60, "series", "turns/min", "", "")
or
label_replace(sum(rate({"gen_ai.client.operation.duration_count", job="<reasoning-engine-id>"}[10m])) * 60, "series", "model calls/min", "", "")
or
label_replace(sum(rate({"gen_ai.execute_tool.duration_count", job="<reasoning-engine-id>"}[10m])) * 60, "series", "tool calls/min", "", "")
```

**Expected output** — three lines that rise and fall with the ten turns, lower
than 2.3 and 2.4 because this page drives ten turns, not twenty:

```console
series=model calls/min   ~1.8
series=turns/min         ~0.9
series=tool calls/min    ~0.9
```

> [!IMPORTANT]
> **What it means.** Agent Runtime exports the same six `gen_ai.*` series as every
> other route, unlike logs and traces in the logging tutorial. Two labels differ: `job` is the numeric reasoning-engine id, not a name
> you set, and `instance` is an id ADK generates for each process
> (`telemetry/google_cloud.py:317`). The last turn's points may be missing; see
> the first deep dive.

**Step 5 — Tear down.** [load/ae_delete.py](../../load/ae_delete.py) deletes the
engine it finds by display name, so no id is needed here.

**Command:**

```bash
.venv/bin/python load/ae_delete.py
```

**Expected output:**

```console
Delete Agent Engine backing LRO: projects/376236993953/locations/us-central1/operations/6489975397080367104
Agent Engine deleted. Resource name: projects/376236993953/locations/us-central1/reasoningEngines/6828072211849412608
deleted 6828072211849412608
```

## Deep dives

### How does the request-driven reader work, and why is it different?

Every other Google route installs a `PeriodicExportingMetricReader` that flushes
on a 5 s daemon thread
([2.4](2.4-your-own-server.md#what-is-the-export-interval-and-why-does-it-matter)).
Agent Runtime installs a `_RequestDrivenMetricReader` instead
(`telemetry/_agent_engine_metric_exporter.py:192`), built by
`telemetry/_agent_engine.py:251-257` and selected from
`telemetry/google_cloud.py:253` when `GOOGLE_CLOUD_AGENT_ENGINE_ID` is set.

A background daemon would be frozen between requests, so this reader collects
from the request lifecycle instead: a flush after each response, plus a
mid-request catch-up if a long turn runs past 1.5× the interval
(`_agent_engine_metric_exporter.py:262-337`). Every flush waits at least 5 s
after the previous one (`:162`, `:256-260`). A response that ends sooner skips its
flush, so the points of a run's last turn can stay in the process with no later
request to carry them out. The review's rerun exported 9 of 10 turns; this
capture exported all 10.

### What do Agent Runtime's own service metrics show?

Agent Runtime also emits its own infrastructure metrics with no setup, on the
`aiplatform.googleapis.com/ReasoningEngine` resource: request count, request
latencies, and container CPU and memory. They answer "is the service healthy",
where the `gen_ai.*` series answer "what is the agent doing". They take several
minutes to appear. Read one in Metrics Explorer, as in Step 4, before Step 5's
teardown:

```
sum by (response_code) (sum_over_time({"aiplatform.googleapis.com/reasoning_engine/request_count"}[30m]))
```

**Expected output** (the same query through the API; the series appeared about
4 minutes after the turns):

```console
{"status":"success","data":{"resultType":"vector","result":[{"metric":{"response_code":"200"},"value":[1790998789.084,"20"]}]}}
```

Each of the ten turns made two requests, `create_session` and the query. The
series carries `reasoning_engine_id`, `response_code` and
`response_code_class` labels, not `job`.

### Why does the agent pin its model to `global`?

`GOOGLE_CLOUD_LOCATION` sets both the deploy region and the model endpoint, and
`gemini-3.7-flash` is served only on `global`, so a regional deploy 404s on the
first model call. The shared agent overrides only the model's client in
[demo_agent/agent.py](../../demo_agent/agent.py):

```python
model=Gemini(model="gemini-3.7-flash", client_kwargs={"location": "global"})
```

`client_kwargs` passes straight to the model's `google.genai.Client`
(`models/google_llm.py:415`), so only the model call goes to `global`.
