# 4.3 · Cost per session and per user

*Part 4 · Consume — rows in BigQuery*

> [!NOTE]
> **Why you are here.** This is the query a metric structurally cannot run:
> group by an unbounded id. Because `session_id` and `user_id` are columns, not
> attributes, you can rank sessions and users by cost and read back the exact
> prompt that drove the top one.

Run the `multi-city` scenario, where one turn in four names three cities in a
single prompt. Those turns do three times the work, so they should rise to the top
of a per-session ranking.

**Step 1 — Rank sessions by total tokens.**

Group the model-call rows by `session_id` and `user_id` and sum their tokens. This
is the aggregation a histogram cannot do, because it never stored the id to group
on.

**Command:**

```bash
bq query \
  --use_legacy_sql=false \
  "SELECT session_id, user_id, COUNT(*) AS calls, SUM(usage_total_tokens) AS total_tokens FROM \`${GOOGLE_CLOUD_PROJECT}.${BQ_ANALYTICS_DATASET_ID}.v_llm_response\` GROUP BY session_id, user_id ORDER BY total_tokens DESC LIMIT 5"
```

**Expected output:**

```console
+--------------------------------------+-----------+-------+--------------+
|              session_id              |  user_id  | calls | total_tokens |
+--------------------------------------+-----------+-------+--------------+
| f6ac01cb-6aa9-4cbb-a2d5-8355873e4430 | load-user |    20 |        16350 |
| aba54705-777c-4815-b20b-8526c95e9489 | load-user |     2 |          969 |
| aa77f9be-1954-4182-a249-02b3cb38526b | load-user |     2 |          956 |
| eefcef71-8c00-44e7-8db8-5916d087eccb | load-user |     2 |          954 |
| bcf8b583-c5e5-4398-a7b8-96a46d74810a | load-user |     2 |          920 |
+--------------------------------------+-----------+-------+--------------+
```

> [!IMPORTANT]
> **What it means.** The top session is 4.2's: ten turns in one session, 20 model
> calls, and a context that grew each turn. Below it, the one-turn sessions that
> cost the most are three-city prompts, each one fanning out to three tool calls;
> a London turn costs about 850 tokens. You found both by grouping on an id a
> metric may never carry ([1.3](../part-1/1.3-attributes-and-cardinality.md)).
> That is the query Part 4 exists for.

**Step 2 — Read the prompt behind the most expensive turn.**

Now go back to the user message of the costliest one-turn session, the second row
above, and read what was asked. The prompt text lives in the `content` JSON
column, under `text_summary`. Set `TOP_SESSION` to the second `session_id` in your
own Step 1 output.

**Command:**

```bash
export TOP_SESSION=aba54705-777c-4815-b20b-8526c95e9489
bq query \
  --use_legacy_sql=false \
  "SELECT invocation_id, trace_id, JSON_VALUE(content, '\$.text_summary') AS prompt FROM \`${GOOGLE_CLOUD_PROJECT}.${BQ_ANALYTICS_DATASET_ID}.agent_events\` WHERE event_type = 'USER_MESSAGE_RECEIVED' AND session_id = '${TOP_SESSION}'"
```

**Expected output:**

```console
+----------------------------------------+----------------------------------+----------------------------------------------------+
|             invocation_id              |             trace_id             |                       prompt                       |
+----------------------------------------+----------------------------------+----------------------------------------------------+
| e-e1969fca-1209-439b-bec9-f3dbf02377de | 45c1abe0134ba37b66a4e1e582bc10a5 | What's the weather in London, Tokyo, and New York? |
+----------------------------------------+----------------------------------+----------------------------------------------------+
```

> [!IMPORTANT]
> **What it means.** The row carries the prompt itself, so "which turn cost the
> most" resolves all the way to the words the user typed. A metric stops at
> "tokens rose in this window"; the row names the turn and quotes it. The
> `trace_id` beside it is the turn's id in Cloud Trace, which
> [4.6](4.6-metrics-or-rows.md) opens.

> [!WARNING]
> The `content` column stores prompts and responses verbatim, including anything a
> user typed. Treat the dataset as containing user content: restrict access, set a
> retention policy, and redact before sharing.

[4.4](4.4-the-sdk.md) uses the SDK to replay one whole invocation, step by step,
instead of querying a column at a time.

## Deep dives

### How do I keep content out of the table?

The plugin truncates long content and flags it with `is_truncated`, but it stores
what fits by default. If you need the ids and costs without the text, drop or hash
the `content` column in a view your analysts query, and grant them the view rather
than the base table. The base `agent_events` table keeps the two IAM roles from
[4.1](4.1-one-line-one-table.md); a content-free view can be shared more widely.
