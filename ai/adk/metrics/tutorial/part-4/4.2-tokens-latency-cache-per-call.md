# 4.2 · Tokens, latency, cache per call

*Part 4 · Consume — rows in BigQuery*

> [!NOTE]
> **Why you are here.** A token histogram gives you the sum over a window; it
> cannot say which model call in a session was the expensive one. The
> `v_llm_response` view keeps one row per model call, so you can rank them and see
> whether any of it was cached.

Run the `growing-context` scenario: N turns in one session, so the context grows
turn by turn. Fire ten turns into the same session, then read the per-call view.

**Command:**

```bash
load/turns.sh growing-context 10
```

**Expected output:**

```console
NEEDS-RUN: turns.sh printing ten growing-context turns, each HTTP 200, one reused session
```

**Step 1 — Rank the model calls in the session by cost.**

`v_llm_response` projects one row per `LLM_RESPONSE` event with tokens, latency,
and cache columns pulled out of the JSON. Order the calls by total tokens.

**Command:**

```bash
bq query \
  --use_legacy_sql=false \
  "SELECT session_id, invocation_id, usage_prompt_tokens, usage_completion_tokens, usage_total_tokens, usage_cached_tokens, context_cache_hit_rate, ttft_ms, total_ms FROM \`${GOOGLE_CLOUD_PROJECT}.${BQ_ANALYTICS_DATASET_ID}.v_llm_response\` ORDER BY usage_total_tokens DESC"
```

**Expected output:**

```console
NEEDS-RUN: v_llm_response rows ordered by usage_total_tokens; prompt tokens climb across the session, completion tokens roughly flat, cached tokens and cache hit rate where the context repeats
```

> [!IMPORTANT]
> **What it means.** Prompt tokens climb call by call as the session's context
> accumulates, while completion tokens stay roughly flat. A histogram summed both
> into one number per window; here you see the growth per call and which
> invocation carried it. Where the repeated context is served from cache,
> `usage_cached_tokens` and `context_cache_hit_rate` are non-zero, a saving no
> metric in Parts 1 through 3 could show.

**What you are looking at.** The columns `v_llm_response` adds beyond the raw
event:

| Column | What it is |
|---|---|
| `usage_prompt_tokens`, `usage_completion_tokens`, `usage_total_tokens` | Tokens for this one model call |
| `usage_cached_tokens` | Prompt tokens served from context cache |
| `usage_thinking_tokens` | Reasoning tokens, inside completion |
| `context_cache_hit_rate` | Fraction of the prompt served from cache |
| `ttft_ms`, `total_ms` | Time to first token, and total call latency |
| `model_version` | The model as the response reported it |

**Step 2 — Reconcile the total with the Part 3 histogram.**

The rows are the same model calls the token histogram counted. Sum
`usage_prompt_tokens` over the run window and it should match the histogram `sum`
for `gen_ai.client.token.usage` with `gen_ai.token.type=input` over the same
window, within run-to-run variance.

**Command:**

```bash
bq query \
  --use_legacy_sql=false \
  "SELECT SUM(usage_prompt_tokens) AS input_tokens, SUM(usage_completion_tokens) AS output_tokens FROM \`${GOOGLE_CLOUD_PROJECT}.${BQ_ANALYTICS_DATASET_ID}.v_llm_response\`"
```

**Expected output:**

```console
NEEDS-RUN: SUM of input and output tokens from v_llm_response, to compare with the Part 3 gen_ai.client.token.usage sum by token type for the same run window
```

> [!IMPORTANT]
> **What it means.** Two stores, one truth. The histogram `sum` and the row `SUM`
> agree because they count the same model calls; the rows just keep each call
> whole. When they disagree, one store dropped points: a rejected export batch on
> the metric side, or a failed write on the row side.

[4.3](4.3-cost-per-session-and-user.md) groups these rows by session and user to
find the most expensive turn and the prompt behind it.

## Deep dives

### Where do tool latency and errors live?

The same per-event views cover tools. `v_tool_completed` has one row per finished
tool call with its `latency_ms`, and `v_tool_error` has one row per tool that
returned an error status, each keyed by `invocation_id`. That is the row-grain
version of 1.3's split: instead of two histogram series, you get the individual
failing calls with their session and prompt attached.
