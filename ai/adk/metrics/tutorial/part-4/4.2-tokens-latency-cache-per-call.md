# 4.2 · Tokens, latency, cache per call

*Part 4 · Consume: rows in BigQuery*

> [!NOTE]
> **Why you are here.** A token histogram gives you the sum over a window; it
> cannot say which model call in a session was the expensive one. The
> `v_llm_response` view keeps one row per model call, so you can rank them and see
> whether any of it was cached.

Run the `growing-context` scenario: N turns in one session, so the context grows
turn by turn. Fire ten turns into the same session, then read the per-call view.

**Command:**

```bash
load/turns.sh growing-context 10
```

**Step 1 — Read the session's model calls in order.**

`v_llm_response` projects one row per `LLM_RESPONSE` event with tokens, latency,
and cache columns pulled out of the JSON. The subquery picks this run's session,
the one with the most model calls; earlier pages' sessions have two each.

**Command:**

```bash
bq query \
  --use_legacy_sql=false \
  "SELECT invocation_id, usage_prompt_tokens, usage_completion_tokens, usage_total_tokens, usage_cached_tokens, context_cache_hit_rate, ttft_ms, total_ms FROM \`${GOOGLE_CLOUD_PROJECT}.${BQ_ANALYTICS_DATASET_ID}.v_llm_response\` WHERE session_id = (SELECT session_id FROM \`${GOOGLE_CLOUD_PROJECT}.${BQ_ANALYTICS_DATASET_ID}.v_llm_response\` GROUP BY session_id ORDER BY COUNT(*) DESC LIMIT 1) ORDER BY timestamp"
```

> [!IMPORTANT]
> **What it means.** Prompt tokens climb call by call as the session's context
> accumulates, from 323 on its first call to 1,113 on its last, while completion
> tokens hold at 14 to 16. A histogram summed both into one number per window;
> here you see the growth per call and which invocation carried it. No call on
> this run was served from cache, so `usage_cached_tokens` and
> `context_cache_hit_rate` read `NULL`. When the model does report cached tokens,
> these columns show a saving no metric in Parts 1 through 3 could show.

**What you are looking at.** The columns `v_llm_response` adds beyond the raw
event:

| Column | What it is |
|---|---|
| `usage_prompt_tokens`, `usage_completion_tokens`, `usage_total_tokens` | Tokens for this one model call |
| `usage_cached_tokens` | Prompt tokens served from context cache |
| `usage_thinking_tokens` | Reasoning tokens, counted apart from completion; `usage_total_tokens` is prompt plus completion plus thinking |
| `context_cache_hit_rate` | Fraction of the prompt served from cache |
| `ttft_ms`, `total_ms` | Time to first token, and total call latency; equal here, because the demo does not stream |
| `model_version` | The model as the response reported it |

**Step 2 — Reconcile the total with the Part 3 histogram.**

The rows are the same model calls the token histogram counted. Sum the token
columns over the table, which holds the 20 turns of 4.1 and this page, and compare
them with the histogram `sum` for `gen_ai.client.token.usage` by `gen_ai.token.type`
([3.4](../part-3/3.4-tokens-and-cost.md)) for the same server process.

**Command:**

```bash
bq query \
  --use_legacy_sql=false \
  "SELECT SUM(usage_prompt_tokens) AS input_tokens, SUM(usage_completion_tokens) AS output_tokens, SUM(usage_thinking_tokens) AS thinking_tokens FROM \`${GOOGLE_CLOUD_PROJECT}.${BQ_ANALYTICS_DATASET_ID}.v_llm_response\`"
```

**Expected output:**

```console
+--------------+---------------+-----------------+
| input_tokens | output_tokens | thinking_tokens |
+--------------+---------------+-----------------+
|        22093 |           608 |            1037 |
+--------------+---------------+-----------------+
```

> [!IMPORTANT]
> **What it means.** Two stores, one truth. On this run the histogram read 22,093
> input tokens, the same as the rows, and 1,645 output tokens, which is 608
> completion plus 1,037 thinking: the metric counts thinking as output, and the
> row splits it out. Compare like with like and the stores agree, because they
> count the same model calls. When they still disagree, one store dropped points:
> a rejected export batch on the metric side, or a failed write on the row side.

[4.3](4.3-cost-per-session-and-user.md) groups these rows by session and user to
find the most expensive turn and the prompt behind it.

## Deep dives

### Where do tool latency and errors live?

The same per-event views cover tools. `v_tool_completed` has one row per finished
tool call with its `total_ms`, keyed by `invocation_id`. `v_tool_error` gets a row
only when a tool raises an exception (`on_tool_error_callback`,
`plugins/bigquery_agent_analytics_plugin.py:7419-7458`). A tool that returns an
error status, like `get_weather` for Atlantis, lands in `v_tool_completed`, with
the status inside its `tool_result`. To find those calls, filter on it, as
[4.4](4.4-the-sdk.md) shows.
