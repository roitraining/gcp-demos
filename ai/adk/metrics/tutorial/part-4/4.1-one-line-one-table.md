# 4.1 · One line, one table

*Part 4 · Consume — rows in BigQuery*

> [!NOTE]
> **Why you are here.** You attach one plugin and every lifecycle event becomes a
> BigQuery row. This page runs ten `baseline` turns through it and counts the
> rows, so you see the grain a histogram threw away.

The plugin needs the dataset to exist first; it creates the table and the views
itself. Attaching it needs two IAM roles, `roles/bigquery.jobUser` on the project
and `roles/bigquery.dataEditor` on the dataset. Grant those to your ADC identity
before you start. [examples/04_bq_plugin.py](../../examples/04_bq_plugin.py) is the
`03` metrics server with `BigQueryAgentAnalyticsPlugin` added to the `App`.

**Step 1 — Create the dataset.**

The plugin will not create the dataset, only the table inside it. Set the id once,
then make it in the `US` multi-region.

**Command:**

```bash
export BQ_ANALYTICS_DATASET_ID=agent_analytics
bq mk \
  --location=US \
  --dataset \
  "${GOOGLE_CLOUD_PROJECT}:${BQ_ANALYTICS_DATASET_ID}"
```

**Expected output:**

```console
NEEDS-RUN: bq mk confirmation that dataset agent_analytics was created in the US location
```

**Step 2 — Run ten baseline turns through the plugin.**

Start the server, then fire ten `baseline` turns. The plugin batches with
`batch_size=1` and flushes on each run end, so rows land within about a second of
each turn.

**Command:**

```bash
.venv/bin/python examples/04_bq_plugin.py
```

Then, in a second shell, drive the turns:

**Command:**

```bash
load/turns.sh baseline 10
```

**Expected output:**

```console
NEEDS-RUN: turns.sh printing ten baseline turns, each with HTTP 200 and elapsed time
```

**Step 3 — List what the plugin built.**

The plugin created one table, `agent_events`, and (with `create_views=True`) one
`v_<event_type>` view per event type it has seen.

**Command:**

```bash
bq ls "${GOOGLE_CLOUD_PROJECT}:${BQ_ANALYTICS_DATASET_ID}"
```

**Expected output:**

```console
NEEDS-RUN: bq ls showing the agent_events table plus the v_llm_response, v_tool_completed, and other v_* views
```

> [!IMPORTANT]
> **What it means.** The table is the raw event log; each `v_*` view is a typed
> projection of one event type. You did not run any DDL. The plugin created the
> table on first write and a view the first time it saw each event type.

**Step 4 — Count the rows by event type.**

One turn is many events: a user message, an invocation, agent starts and
responses, model requests and responses, tool starts and completions. Count them.

**Command:**

```bash
bq query \
  --use_legacy_sql=false \
  "SELECT event_type, COUNT(*) AS rows FROM \`${GOOGLE_CLOUD_PROJECT}.${BQ_ANALYTICS_DATASET_ID}.agent_events\` GROUP BY event_type ORDER BY rows DESC"
```

**Expected output:**

```console
NEEDS-RUN: bq query count by event_type after 10 baseline turns, e.g. LLM_RESPONSE, TOOL_COMPLETED, AGENT_RESPONSE counts
```

> [!IMPORTANT]
> **What it means.** Ten turns produced dozens of rows, not ten. A histogram
> would have folded all of this into a `count` and a `sum`; here every event is
> its own row, keyed by `session_id`, `invocation_id`, and `trace_id`. That grain
> is the whole point of Part 4.

**What you are looking at.** The columns every row carries:

| Column | Type | What it is |
|---|---|---|
| `timestamp` | TIMESTAMP | When the event fired |
| `event_type` | STRING | Which lifecycle moment, e.g. `LLM_RESPONSE` |
| `session_id`, `user_id` | STRING | The unbounded ids a metric may not carry |
| `invocation_id` | STRING | One turn's id, joining its events |
| `trace_id`, `span_id` | STRING | The Cloud Trace join keys (see [4.6](4.6-metrics-or-rows.md)) |
| `content` | JSON | The prompt or response text |
| `attributes`, `latency_ms` | JSON | Per-event detail |
| `status` | STRING | Success or error for the event |

The dataset stays up for the rest of Part 4; [4.6](4.6-metrics-or-rows.md) tears
it down. [4.2](4.2-tokens-latency-cache-per-call.md) reads per-call tokens and
cache hits from the `v_llm_response` view.

## Deep dives

### How does a row reach BigQuery?

The plugin writes through the BigQuery Storage Write API, not streaming inserts or
load jobs. Its `BigQueryLoggerConfig` defaults to `batch_size=1`,
`batch_flush_interval=1.0` s, and `flush_on_run_end=True`, so a row is committed
within about a second of the event and always by the end of a run. Storage Write
API ingestion is billed by volume, so a chatty agent under heavy load is a cost to
watch, not a free side channel. Raising `batch_size` trades latency-to-visibility
for fewer write calls.

### Why does the plugin need two roles?

`roles/bigquery.jobUser` on the project lets it run the query and metadata jobs
that create the table and views. `roles/bigquery.dataEditor` on the dataset lets
it write rows into the table. Granting `dataEditor` at the dataset scope, not the
project, keeps the plugin's write reach to this one dataset.
